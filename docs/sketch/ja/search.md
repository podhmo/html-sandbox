# スケッチ: ブログの全文検索（実験）

## 目的

ブログの記事とリポジトリの文書を、ブラウザーで全文検索できるようにする実験
（issue #41）。まだマージするかは決めていない。ここでは Go 版
（`go/examples/blog`）だけを実装し、品質・大きさ・時間を測った。MoonBit 版
（`moonbit/`）と TS 版（`ts/`）には移植していない。

## 方針

- 検索対象は記事（`/posts/`）と文書（`/docs/`）の両方。ベクトル検索ではなく、
  単語の完全一致・前方一致・あいまい一致による全文検索にする。
- 検索はブラウザーで行い、サーバーはデータを配るだけにする。ビルド工程は
  増やさず、Go の標準ライブラリだけで作る。データは検索ページを開いた
  だけでは取らず、最初の入力か `q` 付きの URL で読み込む。
- `/search.json` は、起動時に読み込んだ `site` からリクエストごとに組み立てる。
  別のビルド手順を持たないので、`-watch` で内容を変えてもそのまま追従する。
- 検索ライブラリは MiniSearch を jsDelivr から読み込む。バージョンは pico.css
  と同じようにメジャー固定（`minisearch@7`）。
- JavaScript を動かすのは `/search` のページだけ。ほかのページはヘッダーに
  `search` のリンクを 1 つ足すだけにする。

## 実装

### `/search.json`

`[{url, kind: "post" | "doc", title, date?, text}]` を返す。記事は `/` と同じ
新しい順、文書は `/docs/` と同じ順に並べる。`date` は記事だけで `YYYY-MM-DD`、
文書では省略する。`text` は本文のプレーンテキストで、`tinymarkdown.Document`
の見出し・段落・箇条書き（入れ子を含む）・引用・表・コードブロックをたどって
組み立てる。リンクとコードスパンは文字だけを残し、強調の `**` も落とす。
バンドルは面の文書に加えて、Markdown のメンバーの文書とメンバー名を含める。
Markdown でないメンバーは文章ではないので飛ばす。

`encoding/json` の `SetEscapeHTML(false)` を使い、`<` や `&` をそのまま出す。
JSON はブラウザーが読むだけで、`textContent` しかしないので安全である。

### `/search` と `/search.js`

`/search` は既存のレイアウトで、検索フォーム、状態表示、結果の `<ul>` を
サーバー側で描く。`<noscript>` では JavaScript が必要だと説明する。
MiniSearch と `/search.js?v=<hash>` を `defer` で読み込む。`/search.js` は
`go:embed` した `internal/site/search.js` を、`site.css` と同じハッシュ付きの
URL と長期キャッシュで配る。

クライアント側は次のように動く。

1. `/search.json` は、最初の入力、送信、または `q` 付きで開いたときに
   1 回だけ取得する。`/search` を開いただけでは取らない。
2. `title` と `text` をフィールドに、`title` を 2 倍に重み付けして
   MiniSearch のインデックスを作る。`prefix: true`、`fuzzy: 0.2` を使い、
   複数語はまず `combineWith: "AND"` で全部を含むページに絞る。0 件なら
   `OR` でもう一度探す。
3. トークン化には `Intl.Segmenter("ja", {granularity: "word"})` を使い、
   英字は小文字にそろえる。`Intl.Segmenter` がない環境では空白で分割する。
4. URL の `q` から初期値を読み、入力中は 100 ms だけ待って検索し、
   `history.replaceState` で URL を同期する。
5. 結果はリンク、種別（`post · 2026-10-21` など）、最初の一致の前後
   約 110 文字の抜粋を並べる。抜粋の一致部分は `<mark>` にする。
   DOM は `textContent` と `createElement` だけで組み、`innerHTML` は使わない。
6. 0 件なら `No results for "..."`、取得に失敗したらエラーを状態行に出す。

### ヘッダーと CSS

全ページのヘッダーで `docs` と `github` のあいだに `search` を置く。
`site.css` に検索フォーム、状態行、結果リスト、`<mark>` の最小限の規則を足す。
既存の pico の変数だけを使い、独自のクラスは増やさない。

## 測ったこと

環境は Linux（Ubuntu 26.04）、Go 1.27.1、Node.js 26。この環境には
ブラウザーがないので、ページとスクリプトは jsdom 27 で動かして確かめた。
ローカルの `localhost` で測った値で、ネットワーク越しの CDN の時間は
含まない（MiniSearch 自体は jsDelivr から実際に読み込ませた）。

### コーパス

| 項目 | 値 |
| --- | --- |
| 件数 | 31（記事 10、文書 21。この文書を足す前は 30） |
| `text` の合計 | 約 394 KB |
| `/search.json` | 約 404 KB（gzip -9 で約 132 KB） |
| MiniSearch 7.2.0（UMD、minified） | 18,556 B（gzip -9 で 6,144 B） |
| `search.js` | 8,664 B（gzip -9 で 3,166 B） |
| `/search` の HTML | 1,665 B（gzip -9 で 757 B） |
| pico.css v2 | 83,319 B（gzip -9 で 11,626 B） |
| `/search` を開いただけ（gzip） | 約 22 KB（HTML、pico.css、MiniSearch、`search.js`） |
| 検索したときの追加（gzip） | 約 132 KB（`/search.json`。合計 約 154 KB） |

issue にはコーパスが約 134 KB とあったが、このリポジトリの記事と文書を
そのまま入れると約 390 KB になった。文書（`docs/`）が記事よりずっと大きい。

### 時間

| 項目 | 値 |
| --- | --- |
| `/search.json` のサーバー応答 | 6〜10 ms（curl、5 回） |
| `/search` のサーバー応答 | 約 1.2 ms（curl） |
| Node でのインデックス構築 | 66〜84 ms（31 件、ウォーム後 5 回） |
| Node での 1 クエリ | 0.01〜0.22 ms（100 回の平均） |
| jsdom で `?q=Wasm` を開いて結果が出るまで | 約 220〜480 ms（描画は含まない） |
| 最初の入力から結果まで | 約 200〜240 ms（jsdom、100 ms の debounce を含む） |

インデックス構築が大半を占める。31 件では問題にならないが、記事が数百件に
増えると、検索を始めてから結果が出るまでの待ちが目に見えるようになる可能性が
ある。jsdom の値は DOM とスクリプトの実行を含むだけで、ブラウザーの描画時間
ではない。

### 検索の例

jsdom で `/search?q=...` を開いて実際に描画された結果（先頭のみ）。
検索の質は、この文書を足す前の 30 件で測った。この文書自身が「検索」や
「プロファイラ」を含み、件数を増やしてしまうため。大きさの表はこの文書を
含む 31 件である。

| 検索語 | 件数 | 先頭の結果 |
| --- | --- | --- |
| `検索` | 2 | 調査メモ: moon run --profile を WSL2 で動かす（環境のセットアップ） |
| `Wasm` | 20 | 探索メモ: wasm-gc の Wasm だけで、ブラウザーの tinymarkdown と el を動かす |
| `プロファイラ` | 1 | ガイド: moon run --profile / moon test --profile でプロファイルして改善する |
| `Static Assets` | 11 | 調査レポート: MoonBit 版のブログの文章を Wasm の外に出す |
| `profiler` | 6 | 調査メモ: profiler で pkg/el と pkg/tinymarkdown のどこが重いか見る |
| `検索 画像` | 5（AND 0 件 → OR） | TODO |
| 意味のない文字列 | 0 | なし |

`検索` は検索機能そのものの文書がまだ無い時点なので、プロファイルの
環境のメモが先頭に来た。`Wasm` と `Static Assets` はタイトルに語を含む
文書が上位に来た。`プロファイラ` は正しいガイドだけが残った。`検索 画像` は
AND では 0 件なので OR に落ち、5 件が返る。

### 日本語のトークン化で分かったこと

`Intl.Segmenter` は日本語を単語に分けるが、カタカナ語を細かく分割する。
たとえば `プロファイラ` は `プロ`、`ファ`、`イラ` の 3 つになる。素朴に
OR 検索すると `プロ` を含むページまで当たり、21 件のうち大半が無関係だった。
`combineWith: "AND"` にしてすべての断片を含むページだけに絞ると 1 件になり、
正しいガイドが先頭に来た。

ただし AND だけだと、`検索 画像` のように片方の語しか無いページをすべて
落として 0 件になる。そこで AND で 0 件のときだけ OR でもう一度探すように
した。`プロファイラ` は 1 件のまま、`検索 画像` は 5 件になる。抜粋の位置と `<mark>` も、断片ではなく元の検索語
（`プロファイラ`）を優先して探すようにした。

それでも、検索語を分割した結果が利用者の意図とずれることはある。英語の
複数形や語形変化も MiniSearch の `fuzzy` だけでは吸収しきれない。日本語の
語形（`検索する`、`検索した`）や、カタカナの表記ゆれ（`プロファイラ` と
`プロファイラー`）は、今後の課題である。

## ライブラリの選択

MiniSearch を第一候補として試した。決め手は次のとおり。

- ブラウザーだけで動き、ビルド工程が要らない。UMD を 1 つ読み込むだけで使える。
- フィールドごとの重み付け、前方一致、あいまい一致、AND/OR の指定がある。
- 31 件・約 400 KB 程度ならインデックス構築が数十 ms に収まる。
- 依存がなく、ライセンスも扱いやすい。

代わりに検討したもの:

- Fuse.js: あいまい一致は強いが、日本語の単語分割は自前で行う必要があり、
  フィールドの重み付けと前方一致の調整は MiniSearch のほうが素直だった。
- Pagefind: 静的なサイト向けに作られていて、ビルド時にインデックスを作る。
  このブログは `-watch` で内容が変わることと、Go の標準ライブラリだけで
  完結させたいことから、別のビルド工程を持ち込む点が合わなかった。

## 魅力的でない点

- **検索を始めるときの重さ。** `/search.json` が約 404 KB（gzip で約 132 KB）
  ある。`/search` を開いただけなら gzip 約 22 KB で済むが、最初の入力で
  この JSON を読むので、合計は gzip 約 154 KB になる。モバイル回線では
  無視できない重さで、記事を増やすほど大きくなる。
- **CDN への依存。** MiniSearch を jsDelivr から読む。CDN が落ちると検索は
  動かない（ページ自体はエラーを表示して壊れない）。自前で配る選択肢もある。
- **JavaScript が必須。** 検索ページだけは JavaScript がないと何もできない。
  `<noscript>` で説明するが、サーバー側検索ではないので、クローラーや
  テキストブラウザーには結果が見えない。
- **全ページのヘッダーが変わる。** `search` のリンクを足すと、Go 版と
  MoonBit 版の HTML が変わる。このブランチでは `make compare` が差分を
  報告する（Go 版だけを変えたため）。マージするなら MoonBit 版も同時に
  変えるか、比較の基準を更新する必要がある。
- **MoonBit 版への移植。** `/search.json` の組み立て（`tinymarkdown` の木を
  たどる処理）、`search.js` の埋め込み、ハッシュ付きの配信、テストを
  もう一度書く必要がある。Go 版の実装は数百行なので、移植自体は難しくないが、
  2 実装を同じ品質で保つコストはかかる。
- **検索品質の調整。** 日本語の分割、AND/OR、タイトルの重み、抜粋の長さは、
  コーパスが変わると見直しになる。今の値はこの 31 件で決めた暫定値である。

## 未解決の問い

- コーパスが増えたとき、毎回 `/search.json` を組み立てる方式で足りるか。
  今はリクエストごとに作っているが、`site` の更新時に 1 回だけ作って
  使い回すこともできる。
- `/search.json` を記事ごと、または記事と文書で分けて、必要な分だけ取る形に
  できるか。全文検索には結局すべての本文が要るので、今は最初の入力で
  全部取っている。
- AND と OR のどちらを既定にするか。今は精度を優先して AND にし、0 件の
  ときだけ OR に落としている。複数語の検索では、最初から OR のほうが
  期待に合う場合もある。
- `title` の重みを 2 のままでよいか。`moonbit` のような語では、本文に
  多く出てくる文書が上に来る。4 や 6 にするとタイトルに語を持つ文書が
  上がるが、どの程度がよいかは主観的である。
- コードブロックを `text` に含め続けるか。検索には役立つが、JSON が大きく
  なり、記号だけの一致も増える。
- MoonBit 版と TS 版に移植するか。移植するなら、`/search.json` の形と
  検索語の扱いを 2 実装でそろえる必要がある。
- ヘッダーの `search` リンクを全ページに置くことを受け入れるか。ページの
  一部だけに置くと、検索への入口が分かりにくくなる。

## 確かめ方

この環境にはブラウザーがないので、Node.js 26 の jsdom 27 で実際の
`/search` を開き、ページの `<script>`（jsDelivr の MiniSearch と
`/search.js`）をそのまま実行した。jsdom は `fetch` を持たないので、
`beforeParse` で Node の `fetch` を相対 URL 対応にして渡す。

```js
const dom = await JSDOM.fromURL("http://localhost:18080/search?q=Wasm", {
  runScripts: "dangerously",
  resources: "usable",
  beforeParse(window) {
    window.fetch = (input, init) =>
      fetch(new URL(input, window.location.href), init);
  },
});
// #search-status が "Loading" でなくなるまで待ち、#search-results を読む。
```

これで、初期表示、入力による再検索（`input` イベント）、URL の同期、
0 件の表示、`/search.json` を 500 にしたときのエラー表示を確認した。
`window.fetch` を包んで記録し、`/search` を開いただけでは `/search.json` を
取らず、最初の入力で 1 回だけ取ることも確かめた。ヘッダーの `search` リンクは
全ページにあり、検索結果のリンク先は `/posts/...` と `/docs/...` になっている。pico.css は jsdom の CSS
パーサーが読めない規則を含むため `Could not parse CSS stylesheet` が出るが、
検索の動作には関係しない。ブラウザーでの見た目と描画時間はこの方法では
分からない。

## 再現

```sh
cd go
make check
make build

# 別のターミナルで
go run ./examples/blog -addr localhost:18080

curl -s http://localhost:18080/search.json | python3 -m json.tool | head
curl -s http://localhost:18080/search | head
curl -sI 'http://localhost:18080/search.js?v=...'
```

ブラウザーがあれば `http://localhost:18080/search?q=Wasm` を開く。なければ
上の jsdom の方法で、`#search-status` が `Loading` でなくなるまで待って
`#search-results` を読む。MiniSearch は CDN から読むので、ネットワークが
要る。

この実験は Go 版だけなので、`go/` の `make compare` は MoonBit 版との
ヘッダーの差分を報告する。それは想定どおりで、このブランチでは比較を
緑にしていない。
