# 調査レポート: スマホで記事を RSVP で読む（`/skim`）

[issue #101](https://github.com/podhmo/html-sandbox/issues/101)「記事を手軽に早く読みたい」の調査と実装の記録。
RSVP（Rapid Serial Visual Presentation）は、文を小さな塊（以下「コマ」）に区切り、画面の中央に 1 つずつ出して読む方法だ。
`/preview` や `/listen` と同じく「more tools」から開くページとして、`/listen` と同じやり方で文書を受け取り、スマホで使えるようにした。
不確定なことは、試作のページを Playwright で 3 つのエンジンで動かして確かめた。

- Chromium：Pixel 7 のエミュレーション
- WebKit：iPhone SE / iPhone 15 のエミュレーション
- Firefox：幅 375px

実機では試していない。

## 結論

- **作れる。文書の受け取り方は `/listen` と同じでよい。** 記事を `fetch` して `main > article` を取り出すか、貼った Markdown を `preview.wasm` で描画し、`BLOCKS` / `SKIP` でブロックを集める。新しく要るのは、日本語をコマに区切る処理と、表示とタイマーの部分だけだった。
- **日本語は BudouX の文節で区切り、BudouX が取りこぼすところをつなぎ直す。** `Intl.Segmenter` の単語は細かすぎ、エンジンによって結果も違う。単語をつなぎ直す方法と BudouX だけの方法も比べたが、この組み合わせが一番自然だった。
- **BudouX は esm.sh から、パーサーと日本語モデルだけを読み込む。** 合わせて約 27KB（gzip で約 10KB）。読み込めないときは、`Intl.Segmenter` の単語をつなぎ直す区切り方に戻す。
- **スマホでは、長い英数字と画面のスリープに気をつける。** パスや URL は `/` や `.` のところで分ける。画面が消えないようにする Wake Lock は、HTTPS か localhost でしか使えない。
- **タイマーは `setTimeout` を順につなぐだけでよい。** 予定とのずれは最大 6ms で、1 コマの表示時間（100〜400ms）に比べて十分小さい。

## 1. 日本語をどう区切るか

### `Intl.Segmenter` の単語をそのまま 1 コマにできるか

できない。細かすぎるうえに、エンジンによって結果が違う。確かめ方は、同じ文を 3 つのエンジンで `granularity: "word"` に区切って比べた。

```
Chromium / WebKit: …|含|め|て|決まって|ない|こと|を|…|言|っ|た|。
Firefox:           …|やや|る|…|決め|てか|ら|…|言|った|。
Chromium だけ:      listen|.|js   Intl|.|Segmenter
```

Node（ICU 78）の結果も、Chromium とほぼ同じだった。

### 単語をつなぎ直せば使えるか

おおむね使える。つなぎ方の規則は次のとおり。

- ひらがなだけの単語（助詞や送り仮名）と、閉じ括弧や句読点は、前のコマにつなげる
- 漢字・カタカナが続くところはつなげる
- 開き括弧は次のコマにつなげる
- 間に空白がない ASCII 同士はつなげる
- 空白のところと「、。！？」の後ろで切る。コマが 10 文字を超えるところでも切る

この規則で区切ると、例文の結果は 3 つのエンジンで同じになった。記事 1 本（workers-subrequest-limit）のコマ数も、3 つとも 982 で一致した。

ただし、長いひらがなの並びは 10 文字の上限で適当に切ることになる。「入れ | 方は」のように誤って切ることもある。

### BudouX と比べてどうか

BudouX だけで区切った場合と、BudouX につなぎ直しを足した場合を比べた。確かめ方は、記事 4 本（slops の 3 本と `docs/sketch/ja/profiling.md`、合わせて 196 ブロック）を 3 通りに区切り、数を数えて、区切った結果を並べて読んだ。

| 区切り方 | コマ数 | 中央値 | 90 パーセンタイル | 最長 | 1 文字のコマ | 11 文字以上 |
| - | - | - | - | - | - | - |
| `Intl.Segmenter`＋つなぎ直し | 3029 | 4 | 9 | 26 | 71 | 120 |
| BudouX だけ | 3463 | 4 | 7 | 49 | 329 | 84 |
| BudouX＋つなぎ直し（採用） | 3141 | 4 | 8 | 26 | 15 | 130 |

- BudouX は、長いひらがなの並びを正しく切れる（「入れ方は」「決まってない \| ことを」「位置は \| ずれない」）
- BudouX だけだと、空白の後ろの助詞が 1 コマになる（「TTS \| で」「Code \| が」）。また、1 文字のコマが多い
- 採用した組み合わせでは、次のものを前のコマにつなげる。空白の後ろの 1〜2 文字のひらがな（`TTS で`）、数字の後ろの助数詞（`2 つある。`）、閉じる記号、1 文字だけのひらがな。ASCII だけの部分は BudouX に渡さない

区切る時間は、196 ブロックを 1 回区切るのに `Intl.Segmenter` 版が 3.7ms、BudouX 版が 5.4ms だった（Node で計測）。どちらも問題にならない。

## 2. スマホの画面に収まるか

日本語のコマはほぼ収まる。長い英数字は収まらない。確かめ方は、文字の大きさを 38px にして幅に収まらないときだけ縮める処理を入れ、iPhone SE の幅（320px）で記事 4 本のすべてのコマを並べた。

- 24px より小さくなったコマは、記事 1 本あたり 0〜5 個だった。どれもパスか URL だった（`slops/2026-10-28-workers-subrequest-limit.md` は 14px）
- そこで、16 文字を超えるコマは `/ . - _ ? & = #` の後ろで分けるようにした（`slops/2026-10- | 28-workers- | subrequest- | limit.md を`）。それでも収まらないものだけを縮める

## 3. 表示の間隔は正確か

正確だった。`setTimeout` を順につないだときの、予定の間隔とのずれを測った。

| エンジン | ずれの中央値 | 最大 |
| - | - | - |
| Chromium（CPU を 6 倍遅くした） | 1.4ms | 2.6ms |
| WebKit | 2.0ms | 4.0ms |
| Firefox | 5.0ms | 6.0ms |

1 コマの表示時間は「文字数（3 文字以上）× 60000 / 毎分の文字数」とした。句点の後ろは 1.8 倍、読点の後ろは 1.3 倍に延ばし、ブロックの終わりに 300ms、見出しの後に 700ms を足す。毎分 600 文字で流すと、slops の記事 1 本（4,300〜4,900 文字）がおよそ 9〜11 分かかる。

## 4. 画面が消えないようにできるか

`navigator.wakeLock.request("screen")` で止められる。ただし HTTPS か localhost のときだけ使える。

確かめ方は、Playwright の route で、外に何も公開せずに架空の `http://lan.test/` と `https://lan.test/` にページを返して比べた。

| オリジン | Chromium | WebKit | Firefox |
| - | - | - | - |
| `http://lan.test/` | `navigator.wakeLock` がない | ない | ない |
| `https://lan.test/` | ある | ある | ある |
| localhost で `request()` | 権限を与えれば成功（与えないと NotAllowedError） | 成功 | 成功 |

スマホから LAN 内の Go のサーバーに `http://192.168.x.x` で開くと、Wake Lock は使えない。Workers にデプロイした HTTPS のサイトなら使える。使えないときも再生は止めず、画面の上に一言出すだけにした。

## 5. BudouX をどう読み込むか

esm.sh から、パーサーと日本語モデルだけを `import()` する。確かめ方は、esm.sh の応答の大きさを測り、3 つのエンジンで実際に読み込んで区切った。

| 読み込むもの | 大きさ | gzip 後 |
| - | - | - |
| `budoux@0.10.0/module/parser.js` | 2,064 B | 972 B |
| `budoux@0.10.0/module/data/models/ja.js` | 25,162 B | 8,619 B |
| （参考）`budoux@0.10.0` の index 全体 | 228,549 B | 83,260 B |

- `budoux` を丸ごと読み込むと、中国語やタイ語のモデルと HTML を扱う部分まで入る。そのため 2 ファイルを個別に読み込む
- 読み込みにかかった時間は、Chromium で 268ms、WebKit で 81ms、Firefox で 88ms だった（1 回だけ測った値で、ネットワークによって変わる）。3 つのエンジンで、区切った結果は同じだった
- esm.sh は `access-control-allow-origin: *` と、1 年間キャッシュしてよいという `cache-control` を返す。このブログは CSP を付けていないので、外から読み込んでも妨げられない
- esm.sh を通さない（ネットワークを遮断した）状態でも、`Intl.Segmenter` の区切りで読み込み・再生できることを確かめた。どちらで区切ったかは、状態の行に「by BudouX」「by Intl.Segmenter」と出る
- 版は 0.10.0 に固定した。npm の最新は 0.10.2 だが、手元の npm の設定で、公開から日が浅い版を入れられなかった。0.10.0 は参考にしたページ（下記）が同梱している版と同じだ

## 6. 前後のコマをどう見せるか

狭い画面では、前のコマを上、次のコマを下に半透明で出す。幅 768px 以上では、左右に並べる。

参考にしたページは、前後のコマを左右に並べていた。iPhone SE の幅（320px）では、中央のコマだけで 4 文字×38px ≒ 150px（コマの長さの中央値の場合）を使う。左右に残るのは各 80px ほどで、小さい字でも 2〜3 文字しか見えない。そのため狭い画面では上下にした。

スマホでは邪魔になるかもしれないので、表示は on/off できるようにした。タップとスワイプは、前後のコマを含む表示の領域全体で受ける。

## 7. `/listen` と何を共有するか

何も共有しない。ユーザーが、`skim.js` を `listen.js` とは別にすると決めた。

ページの選び方（パスでの fuzzy 絞り込み）、貼った Markdown の描画、ブロックの集め方は、`listen.js` から写して持っている。サーバーに足したのは、ページを返すことと `skim.js` を配信することだけで、Go 版と MoonBit 版の両方に入れた。

MoonBit 版では `assets/moon.pkg` の監視対象に `listen.js` と `skim.js` を足した。それまでは `listen.js` を変えても、埋め込み直されなかった。

## 8. 再生中にブラウザーの負担が大きすぎないか

最初の実装には無駄が 2 つあった。どちらも直した。

確かめ方は、Chromium（Pixel 7 のエミュレーション）で CDP の `Performance.getMetrics` を使い、レイアウトとスタイルの再計算の回数、処理時間を測った。1 回目の測り方では、記事 1 本を毎分 1500 文字で、CPU を 4 倍遅くして 10 秒（34 コマ）流した。2 回目の測り方では、状態ごとに 3 秒ずつ回数を数えた。

### `<progress>` の値の更新が、レイアウトを何度も起こしていた

2 回目の測り方で、表示する要素を 1 つずつ外して数えると、原因は `<progress>` だった。

| 状態 | レイアウト / 秒 |
| - | - |
| 再生中 | 17.7 |
| 一時停止中 | 0 |
| 再生中、`<progress>` を外す | 4.7 |
| 再生中、前後のコマを外す | 17.0 |

進み具合のバーを、`transform: scaleX()` で伸ばす `div` に替えた。`transform` はレイアウトを起こさない。

| 1 回目の測り方 | 直す前 | 直した後 |
| - | - | - |
| レイアウト | 393 回 | 66 回 |
| スタイルの再計算 | 411 回 | 79 回 |
| 処理時間の合計 | 201ms | 87ms |
| 再生中のレイアウト / 秒（2 回目の測り方） | 17.7 | 2.7 |

直した後は 1 コマあたり約 2 回になった。コマを入れ替えたあと、幅に収まるかを測るために 1 回、描くために 1 回、レイアウトが起きる。

### タブを裏に回しても、再生が止まらなかった

ブラウザーは、隠れたページのタイマーを遅らせるだけで止めはしない。そのため、見えないところでコマが進み、戻ったときに読んでいた位置が分からなくなっていた。

`/skim` のページが隠れたら（ほかのタブやアプリに切り替えた、スマホの画面が消えた）、`visibilitychange` で一時停止するようにした。テストでは、`document.visibilityState` を書き換えてイベントを送って確かめた。実際にタブを切り替えては確かめていない。

### もともと問題がなかったこと

- 一時停止中は、レイアウトもスタイルの再計算も 0 回だった
- 長い処理（50ms 超、`longtask`）は一度もなかった。JS ヒープは 4.5MB だった
- 再生を始めるときに記事全体（約 900 コマ）を区切る処理は、CPU を 4 倍遅くしても 12.9ms だった
- 画面を点けたままにするロック（Wake Lock）は、再生中だけかける。一時停止したとき、閉じたとき、ページが隠れたときに外す

### そのままにしたこと

BudouX は、`/skim` を開いた時点で esm.sh から取ってくる（約 10KB、gzip 後）。区切った結果を使わなくても取りにいくが、1 年間キャッシュされる。取りにいくのは `skim.js` を読み込む `/skim` だけで、ほかのページは取りにいかない。このままでよいとユーザーと決めた。

## 決めたこと

ユーザーと決めたことは次のとおり。

- 名前は `/skim`
- 速さは「毎分の文字数」で、300〜1500、初期値 600。再生の前に決められ、再生中も変えられる（ステージのスライダーと ↑↓ キー）。値は `localStorage` に残る
- 長い英数字は分ける
- 操作はボタンと、タップ（一時停止）・スワイプ（左で次の文、右で前の文）の両方を用意する。邪魔になったら、どちらかを消す
- 前後のコマの表示は on/off できる

## 参考にしたもの

- [quanon.github.io/rsvp](https://quanon.github.io/rsvp/)（ユーザーが教えてくれたもの。`index.html`、`segment.js`、`app.js` を読んだ）
  - 前後のコマを中央の左右に `opacity-25` で出し、中央の上下に注視点の印を付ける
  - BudouX 0.10.0 を同梱して区切り、助詞や 1 文字のひらがなをつなぎ直す後処理を足す。BudouX がないときは `Intl.Segmenter` で区切る
  - 速さの単位は「文節/分」（100〜1000）。読んだ位置と速さを `localStorage` に残す。コードブロックは「〔コード省略〕」の 1 コマにする
  - ここから取り入れたのは、前後のコマの表示と、BudouX＋つなぎ直しという考え方だ

## まだ確かめていないこと

- 実機（iPhone の Safari、Android の Chrome）での表示と操作、Wake Lock。調べたのは、デスクトップの 3 つのエンジンでのエミュレーションだけ
- タブを裏に回したときに Wake Lock が外れ、戻ったときにかけ直す必要があるか。仕様ではそうなっていて、`skim.js` は `visibilitychange` でかけ直しているが、動きは確かめていない
- 読みやすい速さ。体感で調整する必要がある
- MoonBit 版を Worker（`make dev`）で動かしたときの `/skim`。テストと `make check` は通っている
- 参考にしたページにある、読んだ位置の保存と「〔コード省略〕」の表示は取り入れていない
- 実機での電池の減り具合

実験に使った試作とスクリプトは `/tmp/html-sandbox/rsvp/` に置いていて、リポジトリには入れていない。
