# 技術調査の記事を書くスキルを、三つの試作から一本にするまで

> [!NOTE]
> 執筆: Claude Code（モデル名・effort の指定なし）。
>
> 三つの試作それぞれの記事（Claude Code、Codex、Gemini が各自で書いたもの）と、それらを一本のスキルにした経緯の記事を、この一本にまとめ直したもの。試作も統合も、この記事を書いたセッションでしたことではない。四本の記事と git の履歴から書いているので、記事に理由が書かれていない判断は、理由は不明と書く。本文で、試作や比較の書き手として出てくる「Claude Code」は、PR #138 のエージェントのこと。統合を行ったのも Claude Code だが、同じセッションかどうかは記録にない。元の三本は slops/ から外し、各 PR のコミットに残してある（場所は、後半の「できたスキルと、残った問い」の節に書いた）。

## 依頼と、始めた時点の材料

起点は、2026-11-06 に依頼した人が [issue #133](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903) に書いたコメント。技術的な備忘録を slops の用途の一つとして置いてみるとよいかもしれない、というもので、技術調査の記事の指示で起きていた課題の整理と、`write-slops-investigation-notes` という名前の SKILL.md の下書きが付いていた。

整理されていた課題は四つ。エージェントが一般論やディベートに脱線する。調査時の環境でだけ要った回避策が、無条件の規則として記録される。自律的に回避して動かしたとき、どの代替案をなぜ捨てたかが残らない。振り返りを求めると自己反省に終始して、最初の問いへの答えが抜ける。依頼した人が記事に求めているのは、「人間に聞くべきだった」という反省ではなく、どの選択肢をどの制約で捨てたか、のほうだった。下書きは、依頼と前提、試行と判断、最初の問いへの答え、余談の 4 節で、冒頭に、淡々と書くこと、ペダンティックな分析や鋭さの誇示をしないこと、を置いていた。

依頼は、この用途のスキルを write-slops の上に作り、そのスキル自身で作った経緯を記事にすること。同じ依頼を、三つのエージェントにそれぞれ出し、別々の PR にしてもらった。Codex と Gemini は専用の worktree で作業し、互いの PR は参照しない条件だった（どちらも自分の記事にそう書いている）。

| 試作 | 書き手（モデル名・effort は依頼者指定） | PR | 試作時のスキル名 | 今の名前 |
| --- | --- | --- | --- | --- |
| Claude Code | `Opus 5.5 effort=middle` | #138 | `write-slops-investigation-notes` | `write-slops-investigation-note--claude` |
| Codex | `GPT-6.1 Sol effort=middle` | #139 | `write-slops-exploration-notes` | `write-slops-investigation-note--gpt` |
| Gemini（Antigravity） | `gemini-3.8-flash effort=high` | #140 | `write-slops-investigation-notes` | `write-slops-investigation-note--gemini` |

三つが最初に読めたのは、このコメントと、11-05 の slops 5 本、既存の [write-slops](../.agents/skills/write-slops/SKILL.md)。コメントには下書きの元になった対話（Google Drive と AI Studio）へのリンクも付いていたが、認証が要るので誰も開けなかった。対話そのものを受け取ったのは、三つとも最初の版を作ったあとになる。この記事を書くのに使った記録にも対話そのものはないので、以下で対話の中身として書くことは、三つの試作の記事と統合の記事が書き写した範囲に限る。

作業を始めた時点で、スキルは `.claude/skills/` にあり（write-slops と todo-md）、`.opencode/skills` はそこへのシンボリックリンクだった。Antigravity（agy）用のパスはまだなく、Codex は `.agents/skills/` を読む。

この記事が追うのは、三つの試作と調整を経て、`write-slops-investigation-note` が今の形になるまでに、何が試され、何が残り、何が外されたか。

## 試行と判断

### 同じ下書きから、三つが別々に始めた

三つとも、下書きの 4 節の並びと、年表にせず因果でつなぐ散文という方針は変えなかった。write-slops の扱いは分かれた。Claude Code と Codex は、派生スキルの冒頭で write-slops を先に読ませるだけにして、記法や図の規則を写さなかった。写すと、write-slops 側の変更（たとえば [PR #132](https://github.com/podhmo/html-sandbox/pull/132) のアスタリスク強調の禁止）に追従が漏れる、というのが Claude Code の理由で、Codex も追従する場所が増えることを挙げた。Gemini は末尾に write-slops の要約を残した。Claude Code の比較は、このとき write-slops と食い違ってはいなかったが、write-slops が変わると古くなる、と書いている。

Claude Code は、下書きを直近の記事に照らして直した。変えるたびに、理由を 11-05 の記事のどれかに求めている。

- 冒頭の「淡々と」を削った。[記事を書く目的で分けて、依頼をテンプレートにする](2026-11-05-slops-use-case-templates.md)に、文体の条件に応えるために観察ではない文が入っていたことが表になっていて、トーンの指定は同じことを起こすと考えた。
- 調査についての解釈は書いてよい、と足した。issue の「起きたことの記録と解釈はあってほしい」から。
- 回避策に加えて、計測値にも条件を付けさせた。[答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md)では、ドライバ 573.22 のために入れた cu128 の固定が「重要」という無条件の規則として残り、Piper の RTF 0.13 は測り直すと 0.07 だった。
- 「作業したセッションで書く」を足した。[forkで書き比べた記事](2026-11-05-skill-for-new-articles.md)の一回目の却下が、この前提の取り違えだったから。
- `docs/sketch/` との分担（手順と事実は sketch、どう辿り着いたかは記事）と、余談の各項目への確認済みかの付記を足し、下書きの末尾にあった write-slops の要約を削った。

名前は下書きのままにして、この形で PR にした。

Codex は、開始時のチェックアウトに同種の investigation-notes というスキルがすでにあったが、その実装も付随する記事も読まず、別名の `write-slops-exploration-notes` を作った。Claude Code の比較によると、依頼した人から、Codex からは main が見えていた、と聞いている。Claude Code は一度 main に直接コミットしてから PR のブランチへ移したので、見えていたのはその間の Claude Code のスキルだったのではないか、というのが Claude Code の推測だ。名前を変えた理由は Codex の記事に書かれていない。Claude Code の比較は、investigation という語が呼ぶ語り口を、名前の側で避けたとも読める、としている。

Codex が最初の版で、下書きにないものとして入れたのは、重要な判断ごとに観測・採用案・代替案・見送った理由・結果を取り出させること、代替案を「失敗した試行」「検討したが実行しなかった案」「あとから気づいた可能性」に分けること、過去の理由が記録になければ不明と書き、考えたことを作らないこと。後の二つが対話を受ける前の版にすでにあったことは、Claude Code の比較が指摘していて、コミット履歴でも確かめられる。回避策の条件を、その段落のそばに書かせる指定は、TTS の記事、[issue #128](https://github.com/podhmo/html-sandbox/issues/128)、[調査メモ](../docs/sketch/ja/tts-wsl2.md)を材料にした。ただし、このセッションで TTS を動かしてはいない。

Gemini の最初の版は、下書きにいちばん近い形だった（Claude Code の比較による）。4 節を必須とし、年表やコミットログにしないこと、捨てた代替案と理由、回避策を条件付きで書くこと、途中の転換を経緯に入れること、反省で締めないことを短く言い換えた。名前は下書きの Q4 にある理屈をなぞっている（tech-notes は一般的な解説記事に、trial-log は奮闘記の感情に寄りかねないので、investigation-notes にペダンティックの禁止を付ける）。スキルは、このあとの調整を経ても 38 行と短い。

### スキルの外側でしたこと: リンクと図

Codex と Gemini は、スキルを他のエージェントからも読めるようにするために、リンクを足した。選んだ形も捨てた形も別々だった。

Codex は、実体を `.claude/skills/` に置き、`.agents/skills/` に write-slops と派生スキルの両方への相対シンボリックリンクを作った。グローバルへのインストールではこのマシンだけの設定になり、コピーでは編集する場所が増える。リポジトリ内の相対リンクなら、チェックアウトと一緒に持ち運べて、派生スキルから隣の write-slops を読む相対参照も保てる。`AGENTS.md` にも、この用途のとき派生側も読む案内を足した。リンク先が実体と一致することと、リンク越しでも相対参照が解決することは確かめている。

Gemini は、agy がプロジェクトの `.agents/` 配下の `skills/<名前>/SKILL.md` をワークスペースのスキルとして探す、というガイドの記述から、`.agents/skills` 自体を `.claude/skills` へのリンクにする案と、`.agents/skills/` の中に個別のリンクを置く案を比べて、後者にした。理由は、ディレクトリのシンボリックリンクの走査はツールによって挙動が違うかもしれないから、というもので、確かめた記録はない。Codex の比較は、個別のリンクもディレクトリのシンボリックリンクなので、この理由だけでは堅牢さは言えない、と指摘している。write-slops、派生スキル、todo-md の三つのリンクのほか、単数形の `.agent` から `.agents` へのリンクも作った。agy が実際にこれらを読み込んだ記録はなく、Gemini の記事の「読み込み可能になった」は動作未確認として扱うことになる。

この二つの形は、どちらも最終的には残らなかった。統合の前に、スキルの実体を `.agents/skills/` へ移し、`.claude/skills` をそこへのディレクトリリンクにする整理が入った（コミット `cadb3df`）。コミットメッセージによると、`.agents/skills` は Codex、OpenCode、Devin CLI、Gemini CLI、Antigravity が直接読み、Claude Code だけが `.claude/skills` しか読まないから、これを実体の置き場にした。`.opencode/skills` のリンクは、OpenCode が `.agents/skills` を直接見るので外した。

図でも一つずつ躓いた。Codex の最初の図は幅が約 680 の横長で、svg-gen の検査も原寸の PNG も問題なかったが、ブログの狭い画面では記事幅への縮小でラベルが読みにくくなった。縦向きの矢印を使った小さな配置に描き直し、短いラベルにして、正式名は本文に残した。この種の失敗は、座標の検査では拾えないので、[SVG の落とし穴](2026-10-27-writing-slops.md/03-svg-pitfalls.md)にも追記した。Gemini は、svg-gen のラベルに改行 `\n` を直接渡したため文字列幅の計算が崩れて失敗し、`labelLines` の配列（`["1行目", "2行目"]`）に直して、lint を 0 errors / 0 warnings で通した。スキルの形式検査では、Codex の環境のシステム Python に PyYAML がなかったので、その依存だけを入れた分離した uv 環境で validator を実行している。

### 元の対話を受け取って、三つの調整が分かれた

最初の版ができたあと、依頼した人が、三つのエージェントに下書きの元の対話を見せた。三つの記事と統合の記事が書き写している限りで、対話にあったのは次のこと。

- 欲しいのは、どの選択肢をどの制約で捨てたかであり、「なぜホスト側のドライバ更新を人間に頼まなかったか」ではない。後者を是とすると、人間に聞きすぎる逆の失敗が起きる。自律的に進めること自体は悪くない。
- 完全なトレースは要らない。知見や手順を再現できれば足りる。
- 冒頭の依頼は書き直してよい。理由は二つあって、記事を「依頼とその確認結果」の形にするため、そして、途中の方針転換を経緯に書くなら、依頼の全文を冒頭に置くと重複して読みにくいため。
- ペダンティックの禁止は、名前の候補（tech-notes、investigation-notes、trial-log）から選ぶとき、investigation という語が学者ぶった論述を呼びそうだ、という懸念への防波堤として入れた。
- 不要なものを必須にして、作業を縛りたくない。
- 余談は、結びのあとに別の章として置くほうが「うれしいかも」。
- 対話の中のシミュレーションは、事後に代替案を書く前提があると、作業中に除外した選択肢をメモに残すようになる、と予測し、捨てた案として、ホスト側のドライバ更新、VOICEVOX、Fish Speech を挙げていた。

同じ材料から、三つは別々の調整をした。

| 論点 | Claude Code | Codex | Gemini |
| --- | --- | --- | --- |
| ペダンティックの禁止 | 理由（名前の副作用への手当て）ごと戻す。語り口の形容は戻さない | 名前を exploration にし、一般論や鋭さの披露をしない、は残す | 外して、「意図と環境の具体的な摩擦に焦点を当てる」に置き換える |
| 依頼を書き直してよい理由 | 二つとも書く | 理由は書かず、後から加わった条件を最初から分かっていたように書かない、を足す | 理由は外し、「第 3 節で答える技術的な問いと成果物」に再構成する、とする |
| 残す代替案 | 実際に検討して進路を変えたもの | 結果の条件・限界・再現に関係するもの。三分類。理由が記録になければ不明 | 退けられるたびに、迂回を強いた環境の制約（コマンド失敗、root 不在、ドライバ不一致、パッケージの大きさ）を書く |
| 変えられない範囲の選択肢 | 環境の境界として書く。人間に頼むべきだったとは書かない | 自律作業中にすべての分岐を人間に確かめる必要はない | スキルには書かず、記事に書く |
| 途中の変更 | 次にしたことを変えたもの | 選択、または結果の評価のしかたを変えたもの | 転換点として書く |
| 回避策 | 条件付きで書く | 条件付きで書く。環境依存の選択を一律に暫定としない | 条件付きで書く |
| 余談 | 必須 | 任意 | 必須 |
| docs/sketch との分担 | あり | なし | なし |

Claude Code は、対話を読んで、一回目の直しのうち二つが、理由を知らずに削ったものだったと気づいた。「淡々と」の行は、名前の副作用への手当てであって、文体の指定ではなかった。依頼を書き直してよい許可に付いていた二つの理由も、許可だけを残して落としていた。逆に、一回目で足したものの一部は、「不要なものを必須にして作業を縛りたくない」に反していた。計測値の条件に回数やウォームかを挙げたのは TTS の例に寄りすぎで、余談に確認済みかを付けさせるのは write-slops 本体の「試したことと試していないことを区別する」と重なる。「作業したセッションで書く」は、スキルを読み込んだエージェントの側では守りようのない運用の前提だった。そこで、削ったものを戻し（禁止は、investigation は題材の話で語り口の話ではない、と添えて）、足したものを減らして、「作業したセッションで書く」は、記録だけから書いているならそう言い、記録にない代替案や理由を補わない、という条件付きの指示に置き換えた。

代替案の書き方も直した。対話の「どの選択肢を捨てたか」を、Claude Code は、そのとき実際に検討して進路を変えたものだけを書く、と読んだ。シミュレーションが予測した、作業中に除外した選択肢をメモに残すようになる、という振る舞いは、書く段階で読み込まれるスキルでは変えられない。起こりうるのは、節を埋めるために、候補をあとから並べることのほうだと考えた。VOICEVOX や Fish Speech は Grok の候補リストにあったもので、作業中に検討されたかは分からない。一回目の「捨てた道すべてについて」は、それを後押しする書き方だった。また、一回目の「原因が変えられない場所にあったなら、どこにあったかを書く」は、書き方次第で「人間に頼むべきだった」に滑るので、変えられない範囲の選択肢は、バージョンと同じ環境の境界として書き、確認を挟まずに進めたこと自体を欠点として説明しない、とした。

Codex は、「重要な判断ごとに取り出す」が、判断を網羅する帳票に寄りうると考えて、残す基準を「結果の成立条件、限界、追試を理解するために必要な選択と代替案」に変えた。回避策は、条件付きであることと暫定であることを分けた。ある環境に依存していても、その条件では適切な最終解かもしれない。必要なのは、選んだ観測と適用条件を書くことで、すべてを暫定と呼ぶことではない。依頼の書き直しは、途中の調整も含めた依頼全体を、記事が答える問いとして再構成してよいことにした。そのぶん、選択や結果の評価を変えた要件は、その時点の経緯にも残し、後から加わった条件を最初から分かっていたようには書かない。次のコマンドが変わらなくても、結果の意味が変わる変更があるので、手順の変更だけには絞らなかった。余談は、本筋に入らなかった確認済みの発見も置けるようにして、材料がなければ節を省くことにした。

Gemini は、文体の否定命令を重ねるとモデルごとの自然な語り口の多様性を損なう、として「ペダンティックの禁止」を外した。issue #133 で依頼した人が、いろいろなモデルに書かせて筆致の差を楽しみたいと言っていたことに沿った読みで、Claude Code の比較も、ありうる解釈だとしている。そのうえで、捨てた代替案を思い出すための手がかりに、コマンド失敗、root 不在、ドライバ不一致、候補パッケージの見送りを例として挙げた。これは初版（`7807a41`）のあとの調整（`9b29d22`）で、記事への反映は `d6205f1`。

### 互いを比べて見えたこと

そのあと、依頼した人は、同じ依頼の別の実行と比べる記事を、それぞれのエージェントに書き足させた。Claude Code は #139 と #140 との比較と三つを並べた総評を、Codex は #138 との比較と、そのあとで #140 との比較を、固定したコミットを対象に書いた。どれも書き手自身の評価で、依頼した人の評価でも、条件をそろえた品質比較でもない、と断っている。

比較で、そのあとの作業に効いたことは次のとおり。

代替案を残す基準に穴があった。Claude 版の基準（実際に検討して進路を変えたもの）は、検討してすぐ見送ったので進路が変わらなかった案を落とす。TTS の件でいえば、ホスト側のドライバ更新は範囲外としてすぐ外れた案で、進路は変えていない。それでも、TTS の追試（[PR #129](https://github.com/podhmo/html-sandbox/pull/129)）は、ドライバを更新したあとでやり直したものだった。Codex 版の基準（結果の条件・限界・再現に関係するもの）なら、この案は残る。Claude Code は Codex の比較を読んで、この点を見落としていたと認めている。

実線の枠が Codex 版の基準、その内側の破線の枠が Claude 版の基準で、点線の枠はどちらにも入らない案。案は対話のシミュレーションと、そこに貼られた Grok の候補リストに出てくるもので、位置はそれをこの二つの基準で読んだときの位置であり、実際に記事を書かせて確かめたものではない。点線の枠の案を、捨てた代替案として後から並べないための歯止め（検討していない候補で記録を埋めない）は、Claude 版と Codex 版にあり、Gemini 版にはなかった。

Gemini 版の書き方には、二つの懸念が出た。「退けられるたびに」は、網羅を求める読み方ができて、実際には検討していない候補を後から並べることへの歯止めがない。理由を環境の制約に限っているので、範囲の外だった、時間がなかった、測って外した、のような判断による見送りの置き場がない。Claude Code と Codex が別々に挙げたが、どちらも指示を読んだ予測で、出力を比べて確かめたものではない。

図があることは、スキルの比較の材料にしないことにした。Claude Code は比較の最初の版で、Codex が図を作ったことを良い点に数えたが、Codex が、図はファイル配置を確かめる助けにはなっても、執筆指示の良し悪しの証拠ではない、と書いていて、これを受けて取り下げた。図があるかどうかは write-slops にどう従ったかの話になる。

足しすぎる危険も、比較の中で言われていた。Codex は、すべての条項を足すと、両方の調整で減らそうとした義務を再び増やす、と書き、統合するなら、まずその調査で必要な差を選びたい、とした。Claude Code は、Codex 版の「渡す前の確認」や「新しい実験や公開を許可しない」のような作業手順の項目は入れないほうがよい、と書いた。

そのうえで、Claude Code の総評の推奨は次のとおり。一本にするなら、Claude 版の短さと記事側の決まり（範囲外の選択肢の書き方、sketch との分担、依頼を書き直してよい理由）を土台にして、Codex 版から代替案の基準と三分類、後から加わった条件と評価のしかたを変えた変更の扱い、既定で暫定扱いにしないこと、余談を任意にすること、`AGENTS.md` からの案内を取り込む、というのが Claude Code の推奨だった。Gemini 版から文面として取り込みたいものは、短さを目標にすること以外にはない、とも書いている。ペダンティックの禁止を残すか外すかは、Claude Code と Gemini で読みが割れたところで、依頼した人が決めることだとした。

Gemini の記事については、比較は、番号付きリスト、文を箱にして並べた図、確かめていない効果を確かめたように書いた箇所、参照しない PR の番号の誤りを指摘している。どれも記事の書き方の問題で、スキルの文面には関係しない。

Codex の記事は、対話を受けたスキルの調整が本文になかった（スキルだけを調整し、初稿はそのままにしていた）。#138 の記事のほうが経緯を追いやすい、と Codex 自身が判断し、依頼を受けて、対話で何を変え、何を必須から外したかを経緯に組み込む形で書き直した。前の比較は、改稿前の初稿への評価として残している。

三つの PR を合わせるときの衝突も、Claude Code の総評が挙げていた。#138 と #140 は同じパス（`.claude/skills/write-slops-investigation-notes/`）にスキルを置いているので、両方はマージできない。`.agents/skills/` は #139 と #140 の両方が作り、前の記事の `next` は #138 と #140 が別々に書き換えていた。実際のマージコミットのメッセージによると、スキルは接尾辞付きの名前（`--claude`、`--gpt`、`--gemini`）の試作として残し、記事の著者を明記して、PR の順につないでいる。

どの比較も、新しい技術環境の調査を終えた場面で試したものではない。三つの試作の記事はどれも、スキル作りが題材だった。次に確認するなら、次の技術調査をしたセッションから fork を二つ起こして、同じ材料で二つのスキルに書かせ、答え、関係する代替案、条件の変化が残るか、判断の経緯を作っていないかを見るのがよい、と Claude Code と Codex の両方が書いている。

### 一本にまとめる

次の依頼は、三つを一本にすること。`.agents/skills` と直近の slops を読み、Claude Code の試作（`--claude`）をベースにして `write-slops-investigation-note` を作る。途中で、判断を仰ぎたいところは質問で聞くこと、今日の記事を全部しっかり読んでから判断すること、の二つが加わった。

最初の版（`489809d`）は、三つのスキルと、Claude Code の記事の README と総評だけを読んで作った。総評の推奨のとおりに足し、そのとき、推奨にはない Codex 版の文もいくつか一緒に持ち込んだ。表で条件を比べてよいこと、関係のない条件は書かないこと、一度の成功を互換性の保証や最善の解にしないこと、部分的な結果や否定的な結果も答えになること、余談の節にしか答えがない状態にしないこと。判断を仰ぎたい点が二つあったので、質問した。一つはペダンティックの禁止で、Claude 版は理由ごと戻し、Gemini 版は外していた。答えは「残す」。もう一つは三つの試作の扱いで、description がほぼ同じなので、Claude Code のスキル一覧に調査記事用のスキルが四つ並び、どれが選ばれるか曖昧になる。答えは「残して description を変える」。試作の description は、比較の記録として残した試作で、名前で指定されたときだけ使う、という内容に書き換え、`AGENTS.md` は統合版を既定として案内するように直した。

次に、今日の記事を全部しっかり読んでから判断するように言われて、まだ読んでいなかった部分を読んだ。そこには、足しすぎへの警告がすでにあった。推奨リストにない五つの文は、どれもこの警告にあたると判断して外した（`1d3c3b9`）。部分的な結果の文は、Claude 版の「答えられていない部分があればどこかを書く」とほぼ重なっていた。互換性の保証の文は、既定で暫定扱いにしないことの言い足しだった。余談の節にしか答えがない状態にしないことは、Codex 版では、渡す前の確認の一項目だった。

Gemini 版から取り込むものも考え直した。Codex の比較は、冒頭の「意図と環境の具体的な摩擦に焦点を当てる」を入口として分かりやすい、と評価していた。一方、Claude Code の総評は、文面として取り込みたいものは短さ以外にない、としていた。この一文は、Gemini 版がペダンティックの禁止を外したときに代わりに置いたものだ。禁止を残すと決めた統合版では役割が重なると考え、入れない案を推して質問した。答えは「入れない」だった。

統合版ができたあと、その経緯の記事を書き始めたところで、依頼した人が、元の対話を貼ってくれた。統合版をこれと突き合わせて、いちばん効いたのは、代替案を残す基準だった。対話で欲しいとされていたのは「どういう選択肢を捨てたのか」で、「なぜホスト側のドライバ更新を人間に頼まなかったのか」ではない。対話の中のシミュレーションは、捨てた案の一つ目にホスト側のドライバ更新を挙げていた。この案は範囲外としてすぐに外れたもので、作業の進路は変えていない。Claude 版の基準では落ちて、Codex 版の基準では残る。統合版は、二つを「または」でつないでいるので、この案は残る。

ほかの点も、対話と合っていた。ペダンティックの禁止は、名前を investigation-notes に決めるときに、依頼した人が「ペダンティックにならなければよいが」と言ったことから入っている。依頼を書き直してよい理由の二点は、依頼した人が自分で挙げたもので、Claude 版から引き継いでいる。途中の調整について完全なトレースは要らない、という一文も対話のとおり。

迷ったのは余談だった。対話では、余談は結びのあとに別の章として置くほうが「うれしいかも」と言っている。必須にした Claude 版と Gemini 版はこれを節の存在の要求と読み、任意にした Codex 版は置き場所の好みと読んだことになる。同じ対話には「不要なものを必須にして作業を縛りたくない」という線引きもあるので、統合版は任意のまま、置くなら結びのあと、とした。

その記事を書き終えたあと、依頼した人から、`AGENTS.md` の案内はそもそも要らないと言われた。技術的な備忘録を書かせたいときは、依頼した人がスキルを直接指定するからだ。総評の推奨に沿って足した案内と、試作三つへのリンクを外し、`AGENTS.md` には、write-slops の紹介と、用途ごとの派生スキル（名前が `write-slops-` で始まるもの）があり、名前で指定されたときだけ使う、という一文だけを残した。

## 余談

- 比べるなら、次に技術調査をしたセッションから fork を起こし、統合版と Claude 版で同じ材料から書かせるのがよさそうだ。見るのは、最初の問いへの答え、図に置いたような関係する代替案、条件の変化が残るか、判断の経緯を作っていないか。Claude Code の記事、Codex の比較、統合の記事が、そろって同じことを書いていた。
- 書く段階のスキルでは、捨てた選択肢の材料が作業中に残されていたかまでは保証できない。調査が長く、会話が要約されると消えやすいはず（確かめていない）。調査の依頼の側で、捨てた選択肢を sketch に一行ずつ残すよう頼めば残るが、作業を縛る側の指定になり、記録の義務が増える。Claude Code と Codex の記事は、調査時の運用までは変えていない、としている。
- 三つの最初の記事は、語り口が違った。Claude Code は日記に近く、何をなぜ直したかを順に書いた。Codex は確かめた範囲と確かめていない範囲を何度も区切った。Gemini はスキルの 4 節を見出しにそのまま写し、言い切りが多かった。スキルは語り口の形容を持たないので、差は書き手の側から出たことになるが、どこまでがスキルのせいで、どこからが書き手の癖なのかは、この比較では分けられない（Claude Code の総評による）。
- Gemini の記事の余談には、他の用途（観察日記、新機能の試用レポート）の特化スキルと、アスタリスク強調を機械的に検査するチェッカーがあった。どちらもここでは手を付けていない。
