# 技術調査の記事を書くスキルを、下書きから三つの試作を経て一本にした

> [!NOTE]
> 執筆: Claude Code（Opus 5.5）。作業した各セッションの中ではなく、あとから当日の四本の記事（三つの試作それぞれの経緯と比較、統合の経緯）とリポジトリの履歴を読んで書いている。記録に理由が残っていない判断は、理由を補わず、記録にないと書いた。
>
> 元の四本はこの記事に畳み、slops/ から外した。全文はこの変更の直前のコミット `96f82be` で読める。スキルの名前は試作中と main に入れたときで違うので、最初の節の表にまとめた。

## 依頼と、始めた時点の材料

最初の依頼は、技術調査のあとに書く slops のために、write-slops の上に載る特殊化したスキルを作り、そのスキルで経緯の記事も書くことだった。同じ依頼が三つのエージェントに別々に出された。次の依頼は、できた三つのスキルを一本にまとめること。この記事は、その二段の経緯と、できたスキルの記録である。

起点は [issue #133 のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903)。8 件あるコメントの最後の 1 件（11-06）に、Q&A 形式の整理と、`write-slops-investigation-notes` という名前の SKILL.md の下書きが載っている。Q&A は AI がまとめたもので、下書きが防ごうとしていた失敗は四つ挙がっている。

- 個別の事実ではなく、一般論やディベート風の立論、書き手の鋭さを見せる論述に脱線する
- 調査当時の環境でだけ必要だった回避策が、恒久的な規則として記録される（TTS の記事で cu128 固定が「重要」として残った件）
- どんな代替案を検討し、なぜ捨てたかが残らず、追試や検証がしにくい
- 書き方を調整すると、今度は自分のミスの振り返りに終始し、最初の問いへの答えが抜ける（fork で書き比べた記事の一回目の却下）

下書きの骨組みは 4 節で、依頼と前提条件、試行と判断の経過、最初の問いへの答え、余談の順。経過は因果でつなぐ散文にして年表にしない、結びは当初の問いへの答えにして、余談はそのあとの章にまとめる、という指定が付いている。

コメントには Google Drive と AI Studio のリンクが付いていた。認証が要るので Claude Code と Codex は開かず、下書きがどういう対話から出たかを Q&A の範囲でしか知らないまま始めた。

三つのエージェントは、それぞれ別の作業ツリー（Codex と Gemini は専用の git worktree）で、互いの実装を読まずに作業した。スキルの名前は試作中のものと main に入れたときのものが違うので、本文では main に入れたときの名前に沿って Claude 版、GPT 版、Gemini 版と呼ぶ。

| 呼び名 | 実行したエージェント | PR | 試作中のスキル名 | main に入れた名前 | 行数 |
| --- | --- | --- | --- | --- | --- |
| Claude 版 | Claude Code（Opus 5.5） | #138 | write-slops-investigation-notes | write-slops-investigation-note--claude | 82 |
| GPT 版 | Codex（GPT-6.1 Sol） | #139 | write-slops-exploration-notes | write-slops-investigation-note--gpt | 89 |
| Gemini 版 | Antigravity の Gemini（gemini-3.8-flash） | #140 | write-slops-investigation-notes | write-slops-investigation-note--gemini | 38 |

手元の材料は、11-05 の slops 5 本と write-slops だった。5 本は、[答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md)、[slops の書き方を読み直した日](2026-11-05-reading-slops-again.md)、[記事を書く目的で分けて、依頼をテンプレートにする](2026-11-05-slops-use-case-templates.md)、[依頼した人にとって良い slops とは](2026-11-05-good-slops-for-requester.md)、[記事を書くスキルを考えて、fork で書き比べた](2026-11-05-skill-for-new-articles.md)。スキルの置き場は、当時は `.claude/skills/` が実体で、`.opencode/skills` がそこへのシンボリックリンクだった。Antigravity（agy）が読む `.agents/` 側には、まだスキルのパスがなかった。

## 下書きから、三者が別々にスキルを作った

三者とも、下書きの 4 節の並びは変えなかった。違いは中身にあった。

Claude 版は、中身を直近の記事に照らして直した。並びを変えなかったのは、11-05 の書き比べで依頼した人が示した形（本筋、余談、最後にまとめ）とほぼ同じだったからである。

- 冒頭の「Keep the tone matter-of-fact」を削った。目的別テンプレートの記事に、文体の条件に応えるために観察ではない文が入った例が表になっていて、トーンの指定も同じことを起こすと考えた
- 解釈は書いてよい、と足した。issue にある「起きたことの記録と解釈はあってほしい」から
- 回避策だけでなく計測値にも条件を付けさせた。cu128 固定が無条件の規則として残った件と、Piper の RTF 0.13 が測り直すと 0.07 だった件から
- 「作業したセッションで書く」を足した。fork の記事の一回目の却下が、この前提の取り違えだったから
- `docs/sketch/` との分担を足した。手順と事実は sketch、そこへどう辿り着いたかは記事
- 下書き末尾の write-slops の要約を削り、先に write-slops を読ませるだけにした。写しを持つと、[PR #132](https://github.com/podhmo/html-sandbox/pull/132) の `*` 禁止のような変更に追従が漏れる
- 余談の各項目に、確かめたかどうかを付けさせた

GPT 版は、開始時のチェックアウトに同種の investigation-notes がすでにあったが、その実装と記事は読まず、別名の exploration-notes で作った。write-slops の規則を派生側に写すと追従先が増えるので、base を先に読ませ、派生側には技術探索の記事で何を残すかだけを書いた。目的別テンプレートの記事は、語り口を合わせるために中身に寄与しない文を足したと報告していたので、感情や人格の指定は足さず、残す内容を決める側に寄せた。fork の記事の却下から、結びには依頼への答えを置き、余談はそのあとにした。初版は、重要な判断ごとに観測、採用案、代替案、見送った理由、結果を取り出させ、回避策には条件を段落のそばに書かせた。TTS の件は既存の記事と調査メモを材料にしただけで、このセッションで TTS を動かしたり、現在の互換性を確かめたりはしていない。作業は `codex/exploration-slops` ブランチで進め、PR にするとき、開始時の HEAD に他の作業のコミットが含まれていると分かったので、自分のコミットだけを `origin/main` の上に載せ直した。

Gemini 版は、下書きにいちばん近い 4 節の短いスキルで、冒頭の「ペダンティックな分析、ディベート風の論述、鋭さの誇示をしない」も含めていた。名前の候補は tech-notes、investigation-notes、trial-log の三つで、tech-notes は一般的な技術解説に、trial-log は奮闘記のような感情的な語りに寄りそうだとして、investigation-notes に決めた。起点は main の 3c114fe。

## 下書きの元になった対話を受け取った

三者とも、最初のスキルと記事を作ったあとで、依頼した人から、下書きを作った元の対話を見せられた。対話では、AI の整理に何度か修正が入っていた。ここから、いくつかのことが分かった。

- 欲しいのは「どの選択肢を捨てたか」で、「なぜホスト側のドライバ更新を人間に頼まなかったか」ではない。後者を是とすると、作業中に人間へ聞きすぎる逆の失敗が起きる。調査を自律的に進めること自体は悪くない
- 完全なトレースは不要で、知見と実施が再現できれば足りる
- 冒頭の依頼は、途中の調整も含めて一つの依頼としてまとめ直してよい。理由は二つ。記事を「依頼とその確認結果」の形にするため、途中の方針転換を経緯に書くなら全文を冒頭に置くと読みにくいため
- 不要なものを必須にして、作業を縛りたくない
- 余談は、結びのあとに別の章として置くほうが「うれしいかも」
- 名前を tech-notes、investigation-notes、trial-log から選ぶときに、investigation が学者ぶった論述を呼びそうだという懸念が出て、ペダンティックの禁止はその手当てとして入った

三者はこれを別々に読んだ。

### Claude 版: 取り違えて削ったものを戻し、足しすぎたものを減らした

一回目の直しのうち二つは、理由を知らずに削ったものだった。matter-of-fact は、文体の指定ではなく、investigation という名前の副作用への手当てだった。冒頭の依頼を変形してよいという許可に付いていた二つの理由は、依頼した人が理由も一緒に書くよう求めていたのに、許可だけを残していた。

逆に、一回目で足したものの一部は、「不要なものを必須にしたくない」に反していた。計測値の条件に回数やウォームかを挙げたのは TTS の具体例に寄りすぎで、「答えはその時点の制約から出てくる」の記事は、依頼した人が「何が書かれているかではなく、どう書かれているかの参照」と位置づけていたものだった。余談の確認済みラベルは、write-slops 本体の「試したことと試していないことを区別する」と重なる。「作業したセッションで書く」は、スキルを読み込んだエージェントの側では守りようのない運用の前提だった。

対話には、一回目では拾えなかった線引きもあった。一回目の「原因が変えられない場所にあったなら、どこにあったかを書く」は、書き方次第で「なぜ人間に頼まなかったか」へ滑る。

もう一つ、対話の中のシミュレーションは、事後に代替案を書く前提があるので、作業中に除外した選択肢をメモに残すようになる、と予測していた。ただこのスキルは書く段階で読み込まれるので、作業中の振る舞いは変えられない。起こりうるのは、代替案の節を埋めるために、あとから候補を並べることのほうだと考えた。シミュレーションが捨てた案として挙げた VOICEVOX と Fish Speech は、Grok の候補リストにあったもので、作業中に検討されたのかは分からない。一回目の版の「For every dropped path」（捨てた道のすべてについて）は、それを後押しする書き方だった。

二回目の直しは次のとおり。

- 捨てた代替案は、そのとき実際に検討して進路を変えたものだけにする。検討していない候補を並べない。代替案が少なければ短くてよい
- 変えられない範囲の選択肢は、バージョンと同じく環境の境界として書き、人間に頼むべきだったこととしては書かない。確認を挟まずに進めたこと自体を欠点として説明しない
- ペダンティックの禁止を戻した。形容詞のトーン指定は戻さず、investigation は題材の話で語り口の話ではない、と添えた
- 依頼を変形してよい理由の二点を戻した
- 途中の調整は、そのあとにしたことを変えたものだけ書く。完全なトレースは要らない
- 計測値の条件は「数値を出すなら、分かっている条件を添える」に弱めて、答えの節に移した
- 余談の確認済みラベルを削った
- 「作業したセッションで書く」を、「記録だけから書いているならそう言い、記録にない代替案や理由を補わない」に置き換えた

### GPT 版: 網羅の帳票に寄る指定を、再現に必要な範囲へ絞った

初版の「重要な判断ごとに取り出す」は、判断を網羅する帳票に寄る。そこで、残す基準を「結果の成立条件、限界、追試を理解するために必要な選択と代替案」に変えた。すべての候補は列挙しない。失敗した試行、検討したが実行しなかった案、あとで気づいた可能性の区別は初版からあり、そのまま残した。理由が記録になければ不明と書く。

回避策は、条件付きであることと暫定であることを分けた。ある環境に依存していても、その条件では適切な最終解かもしれない。必要なのは、それを選んだ観測と適用条件で、すべてを暫定と呼ぶことではない。

初版の「初期の依頼を要約する」は、途中の調整も含めて一つの依頼としてまとめてよい、という対話に合わせて、依頼全体の再構成を許す形に変えた。同時に、選択や結果の評価のしかたを変えた要件は、その時点の経緯にも残し、後から加わった条件を最初から分かっていたようには書かない。次のコマンドが変わらなくても、結果の意味が変わる変更はあるので、対象を手順の変更だけに絞っていない。余談は、確認済みの副産物、推測、未検証の案を区別して置け、材料がなければ節ごと省くことにした。途中の誤りや訂正も、結果に至る経緯として必要なら書いてよい。形容詞のトーン指定や、新しい確認義務は足していない。

### Gemini 版: ペダンティックの禁止を外し、環境の摩擦に焦点を移した

文体の否定命令を重ねるとモデルごとの語り口の多様性を損なう、として、冒頭の禁止を外し、「意図と環境の具体的な摩擦に焦点を当てる」に置き換えた。代替案には、コマンド失敗、root 権限がない、ドライバの不一致、パッケージの大きさといった環境の制約を、思い出すきっかけとして例示した。冒頭の依頼は、結論の節で答える技術的な問いと成果物に再構成するとして、二点の理由は外した。

### 三つのスキルの差

調整後の状態で比べると次のとおり。

| 項目 | Claude 版 | GPT 版 | Gemini 版 |
| --- | --- | --- | --- |
| ペダンティックの禁止 | 理由ごと戻した（名前の副作用への手当て） | 名前を exploration に変え、一般論や鋭さの披露をしないとして残した | 外し、環境の摩擦への焦点に置き換えた |
| 依頼の書き直し | 許可と、理由の二点を書く | 途中の調整を含めた再構成を許す。後から加わった条件を最初から知っていたように書かない。理由は書かない | 答えの節で答える問いと成果物に再構成する。理由の二点は外した |
| 残す代替案 | 実際に検討して進路を変えたものだけ | 結果の条件・限界・再現に関係するもの。三分類。理由が記録になければ不明 | 退けられるたびに、迂回を強いた環境の制約を書く |
| 後付けの候補への歯止め | あり | あり | なし |
| 範囲外の選択肢 | 環境の境界として書く | 自律作業中にすべての分岐を人間に確かめる必要はない | スキルには書かない（記事では書いている） |
| 途中の変更 | 次にしたことを変えたもの | 選択か、結果の評価のしかたを変えたもの | 転換点として書く |
| 余談 | 必須 | 任意。確認済みの副産物も置ける | 必須 |
| docs/sketch との分担 | あり | なし | なし |
| write-slops の写し | 持たない | 持たない | 末尾に要約を持つ |
| AGENTS.md からの案内 | なし | あり | あり |

## 各エージェントから読める配置も、三者三様に試された

並行して、スキルを各エージェントから読めるようにする配置が、GPT 版と Gemini 版で試された。

GPT 版は、実体を `.claude/skills/` に置いたまま、`.agents/skills/` に write-slops と探索用スキルの両方への相対ディレクトリリンクを作り、AGENTS.md に、この用途のときに派生側も読む案内を足した。グローバルへのインストールではこのマシンだけの設定になり、コピーでは編集対象が増える。リポジトリ内の相対リンクならチェックアウトと一緒に持ち運べて、派生スキルから隣の base を読む参照も保てる、というのが選んだ理由。リンクが実体と一致することと、リンク経由でも base への相対参照が解決することを確かめた。スキルの形式検査は、システムの Python に PyYAML がなかったので、その依存だけを入れた分離した uv 環境で実行し、通った。この作業で作った図は、最初は幅約 680 の横長で、境界とラベルの検査も原寸の PNG も通ったが、ブログの狭い画面では縮小でラベルが読めなくなった。縦向きの小さな配置に直し、[SVG の落とし穴](2026-10-27-writing-slops.md/03-svg-pitfalls.md)に追記した。

Gemini 版は、agy が `.agents/`（または `.agent/`）の `skills/<名前>/SKILL.md` を読む、という仕様のガイドに沿って、`.agents/skills` の丸ごとを `.claude/skills` へのリンクにする案と、`.agents/skills/` の中に個別のスキルへのリンクを置く案を比べた。ツールによってディレクトリリンクの走査の挙動が違うかもしれないとして、後者を採った。この理由は一般論で、試して確かめた記録はない。個別の入口もディレクトリのシンボリックリンクなので、走査の問題はそのまま残る。write-slops、investigation-notes、todo-md の 3 つを置き、単数形の `.agent` から `.agents` へのリンクも作った。agy から実際に読み込めたかは、PR の検証の記録に確認項目がなく、動作未確認である。図の生成では、ラベルに改行 `\n` を直接渡すと文字列幅の計算が崩れてエラーになり、`labelLines` に配列で渡して 0 errors / 0 warnings になった。`make test-go` は通っている。

この三つの配置は、どれも今は使っていない。三つの PR が main に入ったあと、`.agents/skills/` を実体にし、`.claude/skills` をそこへのシンボリックリンクにする整理が入った（コミット `cadb3df`）。理由はそのコミットメッセージに書かれている。`.agents/skills` は Codex、OpenCode、Devin CLI、Gemini CLI、Antigravity が直接読み、Claude Code だけが `.claude/skills` を読むので、実体を一つにするため。`.opencode/skills` のリンクは、OpenCode が `.agents/skills` も `.claude/skills` も走査するので外し、`.devin/skills` も同じ理由で足さなかった。`.agent` から `.agents` へのリンクは残っている。

## 三つを比べて分かったこと

その後、依頼した人は三者それぞれに、ほかの PR との比較を依頼した。Claude Code は #139 と #140 との一対一と、三つを並べた総評を、Codex は #138 と #140 との一対一を書いた。比較は評価者自身の読みで、条件をそろえた実験ではない。スキルの違いが記事に出るかは、三つとも題材がスキル作りだったので、技術調査の場面では試されていない。

- 代替案の基準は、Claude 版のものに取りこぼしがあった。「実際に検討して進路を変えたもの」では、検討してすぐ見送ったために進路が変わらなかった案が落ちる。TTS の件のドライバ更新がそれで、範囲外としてすぐ外れた案だが、追試の記事はまさにその案から始まった。GPT 版の「結果の条件・限界・再現に関係するもの」なら残る。一方で GPT 版の基準は、不要な材料も入りやすい。「網羅しない」という指定が危険を減らすが、うまく選べるかは試していない
- Gemini 版の「退けられるたびに」は、網羅を求める読みができ、実際には検討していない候補を後から並べることへの歯止めがない。理由を環境の制約に限っているので、範囲の外だった、時間がなかった、測って外した、のような判断による見送りの置き場もない。一方で、短いことと、「意図と環境の具体的な摩擦」という入口は、障害対応を伴う環境構築の記事では何を残すかを思い出す助けになりそうだと評された。文面として取り込みたいものは短さ以外にない、という評もあり、ここは割れた
- 図があることは write-slops に従ったかの話で、スキルの良し悪しの材料にはしない。GPT 版の図は実体とリンクの関係を描いたもので、スキルの効果を示すものではない
- GPT 版の記事は、初稿が対話を受けたスキルの調整を経緯に含んでいなかった。そのため記事は改めて、調整後のスキルに沿って書き直された

Claude Code の総評は、一本にするなら、Claude 版の短さと記事側の決まり（範囲外の選択肢の書き方、sketch との分担、依頼を書き直してよい理由）を土台にし、GPT 版から次を取り込むのがよい、とした。

- 代替案を残す基準（結果の条件・限界・再現に関係するもの）と三分類
- 後から加わった条件を最初から分かっていたように書かないこと
- 結果の評価のしかたを変えた途中の変更も残すこと
- 回避策を既定では暫定扱いにしないこと
- 余談を任意にすること
- `AGENTS.md` からの案内

Gemini 版からは、文面として取り込みたいものは、短さを目標にすること以外には見つからない、とされた。Codex の比較は、すべての条項を足すと、両方の調整で減らそうとした義務を再び増やす危険がある、とし、統合するなら、まずその調査で必要な差を選びたい、と書いた。Claude Code の総評も、GPT 版の「渡す前の確認」や「新しい実験や公開を許可しない」のような作業手順の項目は入れないほうがよい、としていた。ペダンティックの禁止を残すか外すかは、Claude 版と Gemini 版で読みが割れたところで、依頼した人が決めることだとされた。

取り込みの面では、Claude 版と Gemini 版が試作中は同じパスに同名のスキルを置いていて、そのままでは両方を入れられなかった。前の記事の `next` も、両方が別々に書き換えていた。三つの PR は、2026-11-07 のうちに #138、#139、#140 の順で、接尾辞を付けた名前で main に入った。取り込みのコミットのメッセージには、試作を残すこと、記事の著者を明示すること、記事を PR の順につなぐことが書かれているが、衝突をどう扱ったかの記録はない。

## 一本にまとめた

三つの PR が main に入ったあと、依頼は、直近の slops と `.agents/skills` を読み、Claude 用に特殊化したスキル（`write-slops-investigation-note--claude`）を土台にして、`write-slops-investigation-note` を作ることだった。途中で、判断を仰ぎたいところは質問で聞くこと、今日の記事を全部しっかり読んでから判断すること、の二つが加わった。

始めた時点の `.agents/skills/` には、write-slops と、三つの試作が並んでいた。AGENTS.md は「試作のどれか一つを選ぶ」と案内していた。

### 総評の推奨どおりに足した最初の版

最初に読んだのは、三つのスキルと、Claude Code の記事の本文と総評だけだった。総評の推奨に沿って、Claude 版に上のリストの項目を取り込んだ。そのとき、推奨には入っていない GPT 版の文もいくつか一緒に持ち込んだ。表で条件を比べてよいこと、関係のない条件は書かないこと、一度の成功を互換性の保証や最善の解にしないこと、部分的な結果や否定的な結果も答えになること、余談の節にしか答えがない状態にしないこと。

総評が依頼した人に預けていた点が二つあったので、質問した。一つはペダンティックの禁止で、答えは「残す」。もう一つは三つの試作の扱いで、description がほぼ同じなので、Claude Code のスキル一覧に調査記事用のスキルが四つ並び、どれが選ばれるかが曖昧になる。答えは「残して description を変える」。試作の description は「比較の記録として残した試作。名前で指定されたときだけ使う」に書き換え、AGENTS.md は統合版を既定として案内するように直した。ここまでを一度コミットした。

### 今日の記事を全部読んで、足しすぎた分を外した

コミットのあとで、今日の記事を全部しっかり読んでから判断するように、と言われた。まだ読んでいなかった Claude 版の比較二本、GPT 版の記事と比較二本、Gemini 版の記事を読んだ。

読んでみると、最初の版で一緒に持ち込んだ五つの文には、比較が出していた警告（すべてを足さない、作業手順の項目は入れない）が当たっていた。五つとも外した。余談の節にしか答えがない状態にしない、という文は、GPT 版では渡す前の確認の一項目だった。部分的な結果の文は、Claude 版の「答えられていない部分があればどこかを書く」とほぼ重なっていた。互換性の保証の文は、既定で暫定扱いにしないことの言い足しだった。後の二つは、外しても失われるものが少ない。外したあとの版を二回目のコミットにした。

Gemini 版から取り込むものも考え直した。比較の一つは、冒頭の「意図と環境の具体的な摩擦に焦点を当てる」を、入口として分かりやすいと評価していた。一方、Claude Code の総評は、文面として取り込みたいものは短さ以外にない、としていた。この一文は、Gemini 版がペダンティックの禁止を外したときに代わりに置いたものだ。禁止を残すと決めた統合版では役割が重なると考え、入れない案を推して質問した。答えは「入れない」だった。

Gemini 版の記事について比較が指摘していた点（番号付きリスト、文を箱にした図、確かめていない効果を確かめたように書いたこと、参照しない PR の番号の誤り）は、記事の書き方の問題で、スキルの文面には関係しないので、統合では扱っていない。

### 元の対話と突き合わせた

統合版を書き終え、その経緯の記事を書き始めたところで、依頼した人が、三つの試作のどれもが参照していた元の対話を、統合の作業にも貼ってくれた。統合版をこれと突き合わせた。

いちばん効いたのは、代替案を残す基準だった。対話で依頼した人が欲しいとしていたのは「どういう選択肢を捨てたのか」で、「なぜホスト側のドライバ更新を人間に頼まなかったのか」ではない。対話の中のシミュレーションは、捨てた案の一つ目にホスト側のドライバ更新を挙げている。この案は範囲外としてすぐに外れたもので、作業の進路は変えていない。Claude 版の基準（実際に検討して進路を変えたもの）ではこの案は落ち、GPT 版の基準（結果の条件・限界・再現に関係するもの）では残る。統合版は二つを「または」でつないでいるので、この案は残る。

### AGENTS.md の案内を外した

統合版を書き終えたあと、依頼した人から、AGENTS.md の案内はそもそも要らないと言われた。技術的な備忘録を書かせたいときは、依頼した人がスキルを直接指定するからだ。総評の推奨に従って足した案内と、試作三つへのリンクを外し、AGENTS.md には、write-slops の紹介と、用途ごとの派生スキル（`write-slops-*`）があり、名前で指定されたときだけ使う、という一文だけを残した。

## 当初の問いへの答え: できたスキルと、今の状態

取り込まなかったもの（作業手順の項目、五つの言い足し、Gemini 版の焦点の一文、AGENTS.md の個別の案内、記事の書き方についての指摘）は、上の節に理由を書いた。

今の状態は次のとおり。

## 余談

- 比べるなら、次に技術調査をしたセッションから fork を二つ起こし、統合版と Claude 版で、同じ材料から書かせるのがよさそうだ。見るのは、最初の問いへの答え、関係する代替案、条件の変化が残るか、判断の経緯を作っていないか。上の図の位置に置いたドライバ更新のような案が、実際に残るかどうかも見られる
- 書く段階のスキルでは、作業中に捨てた選択肢が記録されたことまでは保証できない。「理由がなければ不明と書く」も、その不足を埋めるものではない。調査の依頼の側で「捨てた選択肢を sketch に一行ずつ残す」と頼めば残るが、作業を縛る指定になる。調査が長く、会話が要約されると消えやすいはずだが、確かめていない
- 直近の技術調査は [PR #136](https://github.com/podhmo/html-sandbox/pull/136)（WSL2 の perf の bind mount で `apt upgrade` が失敗した件）だが、Devin のセッションで行われ、記事はない。そのセッションには捨てた選択肢の材料がないので、新しい規則に従えば、記録だけから書いていると断ったうえで sketch をなぞる以上のことは書けない。次に Claude Code で技術調査をしたときに、そのセッションで使うのが順当だと思う
- issue #133 では、観察日記のような書き方や、新機能の試用レポートも、用途別の特化スキルの候補に挙がっていた。今回は技術調査の備忘録だけに絞った。tinymarkdown が使えない `*` の強調を、`tools/svg-gen/check.ts` のように slops 全体を走査して警告するチェッカーも、深追いされていない
- 三者の記事の語り口は違った（元の記事は `96f82be` で読める）。どのスキルもトーンの形容は入れていないので、差はモデルの側から出る。issue #133 で依頼した人が、モデルごとの筆致の差を楽しみたいと言っていたことに近い。どこまでがスキルのせいで、どこからが書き手の癖かは、比較では分けられていない
