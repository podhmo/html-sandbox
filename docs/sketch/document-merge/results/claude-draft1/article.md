## 試行と判断の経緯

### 下書きが前提にしていた問題

write-slops は記法、SVG、ファイル構成といった形式を細かく決めているが、本文で何をどう語るかは、エージェントと個別の依頼文に任されていた。11-05 の記事群と issue #133 が指摘していた問題を、Gemini の記事は次の四つにまとめている。

- 一般論やディベートへの脱線。具体的な事実や境界条件の代わりに、抽象的な主張や書き手の視点の鋭さの披露が前に出る。
- 回避策の無条件な規則化。その場の環境制約（特定のドライバ版や権限境界）を乗り切るための回避策が、以後も必須の規則として残る。
- 判断の過程の不可視化。自律的に問題を回避して進めたとき、どの代替案を検討してなぜ外したかが残らない。
- 自己反省への偏り。振り返りを求めると手順の悔やみに終始して、当初の目的への答えが抜ける。

下書きの骨組みは、依頼と前提条件、試行と判断の経過、最初の問いへの答え、余談の 4 節だった。11-05 の[書き比べの記事](2026-11-05-skill-for-new-articles.md)で依頼した人が示した形（本筋、余談、最後にまとめ）とほぼ同じで、三つの試作はどれもこの並びを変えていない。

### 一回目: 三つの試作

三つは、対話を渡される前の材料で別々に始めた。

#### Claude 版: 直近の記事に照らして下書きを直した

4 節の並びは変えず、中身を、直近の記事に理由を求めて直した。

- 冒頭の「Keep the tone matter-of-fact」を削った。記事を書く目的で分けた記事に、文体の条件に応えるために観察ではない文が入っていたことが表になっていて、トーンの指定は同じことを起こすと考えた。
- その調査についての解釈は書いてよい、と足した。issue の「起きたことの記録と解釈はあってほしい」から。
- 回避策に加えて計測値にも条件を付けさせた。答えはその時点の制約から出てくる、の記事で、cu128 固定が「重要」という無条件の規則として残った件と、Piper の RTF 0.13 が測り直すと 0.07 だった件から。
- 「作業したセッションで書く」を冒頭に足した。fork で書き比べた記事の一回目の却下が、この前提の取り違えだったから。
- `docs/sketch/` との分担（手順は sketch、どう辿り着いたかは記事）を足した。issue の「sketch は情報収集、それを適用した結果の出来事を綴るのが日記の一部」から。
- 下書き末尾の write-slops の要約を削り、先に write-slops を読ませるだけにした。写しを持つと、PR #132 の `*` 禁止のような変更に追従が漏れる。
- 余談の各項目に、確かめたかどうかを付けさせた。

この版を PR #138 にした。

#### GPT 版: コメントから別名で作った

Codex の開始時のチェックアウトには、同種の investigation-notes というスキルがすでにあった。Codex はその実装と付随する記事を読まず、別名の `write-slops-exploration-notes` を `codex/exploration-slops` ブランチに作った。PR を作る段階で、開始時の HEAD に他の作業のコミットが含まれていると分かったため、自分のコミットだけを `origin/main` の上に載せ直して [PR #139](https://github.com/podhmo/html-sandbox/pull/139) にした。チェックアウトにそのスキルがあった経緯は、依頼した人によれば、Codex 側から main が見えていた、ということだった。Claude は、自分が一度 main に直接コミットしてから PR のブランチへ移した間のことだろうと推測しているが、確かめてはいない。

スキルの設計では、write-slops にある問い・観測・未検証の案・決定の区別、測定値や約束を創作しないこと、記法・図・バンドル・表示確認の指定を、派生側に写さなかった。写すと追従する場所が増えるので、先に write-slops を読ませ、派生側には技術探索の記事で何を残すかだけを書いた。骨格は、依頼と前提、試行と判断の経緯、依頼への答え、最後に余談の順。語り口の調整のために中身に寄与しない文を足した、という[目的別テンプレートの記事](2026-11-05-slops-use-case-templates.md)の報告を受けて、感情や人格の指定は足さず、残す内容を決める方に寄せた。[forkで書き比べた記事](2026-11-05-skill-for-new-articles.md)には、二つの試作記事が自己の間違いを振り返って終わり、求められた答えが抜けたことと、筋を一本に絞る指定で有用な余談まで落ちたことが書かれていた。そこで結びには依頼への答えを置き、余談はそのあとに残すことにした。時系列をコマンド一覧にせず、観測から選択と結果へつながる散文にする方針は、指定コメントから引き継いだ。

初版は、重要な判断ごとに観測、採用案、代替案、見送った理由、結果を取り出させ、回避策の条件をその段落のそばに書かせた。材料は[TTSの記事](2026-11-05-answers-under-constraints.md)、[issue #128](https://github.com/podhmo/html-sandbox/issues/128)、[調査メモ](../docs/sketch/ja/tts-wsl2.md)で、環境表に条件があっても手順だけ抜き出すと無条件の規則として伝わる、という問題だった。ただし Codex はこのセッションで TTS を動かしておらず、現在の互換性も確かめていない。

Codex から同じ実体を読むために、スキルの実体は `.claude/skills/` に置いたまま、`.agents/skills/` に write-slops と派生スキルへの相対ディレクトリシンボリックリンクを作った。グローバルへのインストールではこのマシンだけの設定になり、コピーでは編集対象が増える。リポジトリ内の相対リンクならチェックアウトと一緒に持ち運べ、派生スキルから隣の write-slops を読む参照も保てる。`AGENTS.md` には、この用途のときに派生側も読む案内を足した。

この配置を、実体とリンクの図にした。最初の図は幅約 680 の横長で、SVG の検査も原寸の PNG の確認も通ったが、ブログの狭い画面では記事幅への縮小でラベルが読みにくくなった。そこで縦向きの矢印を使う小さな配置に変え、正式名は本文に残した。この件は[SVG の落とし穴](2026-10-27-writing-slops.md/03-svg-pitfalls.md)にも追記した。

記事の初稿は英語で書いた。本文を日本語にする依頼があとから来たので、翻訳で対応した。

#### Gemini 版: 4 節を規則にし、agy 向けのリンクを置いた

Gemini は、write-slops の形式の規則はそのまま継承し、技術調査ノートに特化した構成の規則を足すことにした。名前は、tech-notes では一般的な技術解説に傾き、trial-log では奮闘記のような感情的なスタンスが文体に乗るおそれがある、という Gemini 自身の理由で `write-slops-investigation-notes` とした。

構成は 4 節を義務付けた。前提と制約では、依頼を技術的な問いと検証条件に再構成して初期条件（環境、権限、版）を整理し、依頼プロンプトは逐語引用せず要約する。試行と判断の経緯では、タイムスタンプや手順の箇条書き（作業ログ、年表）を禁じ、前後の因果関係を結ぶ散文で書く。除外した代替案と環境制約を明記し、途中の要件変更も転換点として組み込む。当初の問いへの結論では、最初の依頼に対する結果、実測値、後片付けで完結させ、反省や後悔は含めない。余談では、本筋から外れた未着手の案や将来の方向を、結びのあとの独立した章に集める。

agy は `.agents/`（または `.agent/`）の下の `skills/<名前>/SKILL.md` をワークスペース固有のスキルとして検出する（agy-customizations の仕様ガイドによる）。リポジトリには Claude 用の `.claude/skills` と、そこへのリンクである `.opencode/skills` があった。そこで、`.agents/skills` 自体を `.claude/skills` へのリンクにする案と、`.agents/skills/` を作って個別のスキルへのリンクを置く案を比べ、後者を採った。理由は、ディレクトリのシンボリックリンクの走査がツールによって異なる場合があるので堅牢性を重視した、というもので、何かを動かして確かめた記録はない。write-slops、write-slops-investigation-notes、todo-md の三つへのリンクを置き、単数形の `.agent` を見る環境のために `.agent` から `.agents` へのリンクも作った。

図は、4 節と、除外する書き方（一般論の主張、作業ログ・年表、自己反省・後悔）を箱で並べたものを tools/svg-gen で作った。最初の試行では、ラベル文字列に改行コード `\n` を直接渡したため文字列幅の計算が崩れてエラーになった。`labelLines` の配列（`["1行目", "2行目"]`）に直すと、check.ts が 0 errors / 0 warnings で通った。最後に `make test-go` を実行して、サイトのルーティング、Markdown のパース、テストが通ることを確認した。

### 下書きの元になった対話を受け取った

三つのエージェントは、それぞれの途中で、下書きの元になった対話を依頼した人から受け取った。Claude は PR のあとに全文を貼られて「自分ならどう調整するか」を尋ねられ、Codex はスキルと初稿を作ったあとに渡された。Gemini の記事は、初期ドラフトのあとに対話の文脈を再検討する転換点があったと書いているが、いつどう受け取ったかは書いていない。

対話には、下書きだけでは分からなかった線引きがあった。

- 欲しいのは「なぜホスト側のドライバ更新を人間に頼まなかったか」という反省ではなく、「どの選択肢を捨てたか」。前者を是とすると、人間に聞きすぎる逆の失敗が起きる。調査を自律的に進めること自体は悪くなく、そのあとで見返せる記事にする。
- 完全なトレースは要らず、知見や実施を再現できればよい。不要なものを必須にして作業を縛りたくない。
- 記事の冒頭では、途中の調整も含めて依頼全体を一つの依頼としてまとめてよい。理由は二つあり、記事を「依頼とその確認結果」の形にするため、途中の方針転換を経緯に書くなら全文を冒頭に置くと読みにくいため。依頼した人は理由も一緒に書くよう求めていた。
- 名前の候補は `tech-notes`、`investigation-notes`、`trial-log` から選ばれた。investigation という語が学者ぶった論述を呼びそうだと、依頼した人は「ペダンティックにならなければよいが」と話している。ペダンティックな分析や鋭さの誇示の禁止は、その名前の副作用への手当てとして入っていた。
- 対話の中のシミュレーションは、事後に代替案を書く前提があれば、作業中に除外した選択肢をメモに残すようになる、と予測していた。

#### Claude 版: 理由を知らずに削ったものを戻し、足しすぎたものを減らした

読んで分かったのは、一回目の直しのうち二つが、理由を知らずに削ったものだったことだ。一つは matter-of-fact で、文体の指定ではなく名前の副作用への手当てだった。もう一つは、依頼を変形してよいという許可に付いていた二つの理由で、一回目の版は許可だけを残していた。

逆に、一回目で足したいくつかは「不要なものを必須にして縛りたくない」に反していた。計測値の条件として回数やウォームかを挙げたのは TTS の具体例に寄りすぎで、答えはその時点の制約から出てくる、の記事は、依頼した人が「何が書かれているかではなく、どう書かれているかの参照」と位置づけていた。余談に確認済みかを付けさせるのは、write-slops 本体の「試したことと試していないことを区別する」と重なる。「作業したセッションで書く」は、スキルを読み込んだエージェントの側では守りようのない運用の前提だった。一回目の版の「原因が変えられない場所にあったなら、どこにあったかを書く」も、書き方次第で「人間に頼むべきだった」へ滑る。

シミュレーションの予測にも注意が要った。このスキルは書く段階で読み込まれるので、作業中の振る舞いは変えられない。起こりうるのは、代替案の節を埋めるために、あとから候補を並べることのほうだった。たとえばシミュレーションが捨てた案として挙げた VOICEVOX や Fish Speech は Grok の候補リストにあったもので、作業中に検討されたのかは分からない。一回目の版の「For every dropped path」は、それを後押しする書き方だった。

これを受けた二回目の直しは次のとおり。

- 捨てた代替案は、そのとき実際に検討して進路を変えたものだけを書く。検討していない候補を並べて網羅的に見せない。代替案が少なければこの部分は短くてよい。
- 変えられない範囲の選択肢は、バージョンと同じく環境の境界として書き、人間に頼むべきだったこととしては書かない。確認を挟まずに進めたこと自体を欠点として説明しない。
- ペダンティックな分析や鋭さを見せることの禁止を戻した。形容詞としてのトーンの指定は戻さず、investigation は題材の話で語り口の話ではない、と一言添えた。
- 依頼を変形してよい理由の二点を戻した。
- 途中の調整は、そのあとにしたことを変えたものだけ書く。完全なトレースは要らず、知見と手順を再現できれば足りる。
- 計測値の条件は「数値を出すなら、分かっている条件を添える」に弱めて、結論の節に移した。
- 余談の確認済みラベルは削った。
- 「作業したセッションで書く」は、「記録だけから書いているならそう言い、記録にない代替案や理由を補わない」という条件付きの指示に置き換えた。

この版のスキルは Claude 版として `.claude/skills/` に置かれ、`.opencode/skills` 経由で OpenCode からも見え、write-slops に合わせて `agents/openai.yaml` も付いた。description は、write-slops-threads のように「名前を指定されたときだけ」にはせず、技術調査（環境構築、実現性の確認、追試、デバッグ）の記事では write-slops の代わりに使う、とした。

#### GPT 版: 必須にする範囲を絞り、依頼と余談の扱いを直した

Codex は、初版の「重要な判断ごとに取り出す」が、判断を網羅する帳票へ寄る可能性があると考えた。残す基準を「結果の成立条件、限界、追試を理解するために必要な選択と代替案」へ変え、すべての候補を列挙することは求めないことにした。失敗した試行、検討したが実行しなかった案、あとで気づいた可能性の区別は残した。理由が記録になければ不明と書く。欠けた判断を後付けで埋めないための指定である。

回避策では、条件付きであることと暫定解であることを分けた。環境に依存していても、その条件では適切な最終解かもしれない。必要なのは選んだ観測と適用条件であり、すべてを暫定解と呼ぶことではない。条件を添える指示は保ち、環境依存の選択を一律に暫定とは扱わない、と明記した。

依頼の扱いでは、初版の「初期の依頼を要約する」を、依頼全体を問いとして再構成してよい、に変えた。同時に、選択や結果の評価を変えた要件は、その時点の経緯にも残す。後から加わった条件を、最初から分かっていたようには書かない。次のコマンドが変わらなくても結果の評価方法が変わることがあるので、対象は手順の変更だけに絞っていない。

余談は、初版では未検証と明記させ試す条件を付けるよう求めていたが、本筋に入らなかった確認済みの発見も余談になりうる。調整後は、確認済みの副産物、推測、未検証案を区別して置け、材料がなければ節を省くことにした。途中の誤りや訂正も、結果へ至る経緯として必要なら書いてよい。結びを自己評価で置き換えないことは、その経緯まで消すことではない。

この調整で、4 部の順序と因果でつなぐ散文は維持し、網羅的な判断記録、初期プロンプトへの限定、未検証案だけの余談を必須とする形は外した。文体を揃える形容詞や、新たな確認義務は足していない。

#### Gemini 版: ペダンティックの禁止を外し、環境との摩擦に焦点を移した

Gemini の最初の指示文には、ペダンティックな分析やディベート風の立論、知的な鋭さのアピールを禁止する否定命令があった。Gemini は、文体の否定命令を重ねるとエージェントの自由度を縛り、モデルごとの自然な語り口の多様性（依頼した人が期待するセレンディピティ）を損なうおそれがある、と考えた。そこで、焦点を「文体の禁止」から「意図と環境の具体的な摩擦の記述」へ移した。

- 文体の否定を抑え、実際に実行し観測した事実と選択の連鎖に集中させる。
- 「捨てた代替案」を思い出すための具体的な手掛かりとして、コマンド失敗、root 権限の不在、ドライバの不一致、候補パッケージのスキップといった環境要因を例示する。
- 冒頭の依頼の再構成について、単に短くするだけでなく、結論の節で直接答えられる技術的な問いと成果物の条件を明確にする。

依頼を変形してよい二つの理由は、この調整で外れた。Gemini の記事は、この改訂でスキルが「記録テンプレートとして機能するようになった」と書いているが、改訂の前後で出力を比べたわけではない。

#### ペダンティックの禁止は三者三様に扱われた

同じ対話から、この禁止の扱いは三通りに分かれた。

- Claude は、investigation という名前が学者ぶった語り口を呼ぶという対話中の懸念への手当てと読み、理由ごと戻した。
- Codex は名前を exploration にし（開始時のチェックアウトにあった investigation-notes と別にするため、と記事は説明している）、一般論や書き手の鋭さの披露をしない、という指定は残した。Claude の比較は、結果として名前の副作用を避けているとも読める、と述べている。
- Gemini は、文体の否定命令がモデルごとの語り口を損なうとして外した。issue の「自由に書けという表現自体が命令として機能する」や、対話の「3 はセレンディピティ的に得られるべき」を読めばありうる解釈だが、対話の中でこの禁止は、名前が学者ぶった語り口を呼びそうだという依頼した人自身の懸念から入っていた。

Claude の比較は、同じ材料から逆の結論になったところで、どちらが意図に近いかは依頼した人にしか決められないとし、自分は名前の副作用への手当てと読んだと書いている。

三つの PR ができたあとで、依頼した人が各エージェントに比較を依頼した。比べた版は次のとおり。

- Claude の比較: #138（`5c08749`）を、#139（`2ce2651`。スキルは `a2208c7` 以降変わっていない）と、#140（`d6205f1`）とそれぞれ 1 対 1 で比べ、三つを並べた総評も書いた。#140 は 3 コミットで、初版 `7807a41`、対話を受けたスキルの調整 `9b29d22`、それを記事に反映した `d6205f1` の順になっている。

Claude の比較の最初の版には、二つの誤りがあった。一つは「下書きの元の対話を見たのはこちらだけ」としたことで、実際には依頼した人は三者に見せていて、#139 の `a2208c7` が対話を受けた調整にあたる。対話に由来する差を「材料の差」として片づけていたのは、この前提の誤りによる。もう一つは、Codex の記事にある「開始時に investigation-notes のスキルがすでにあった」を、Claude 側の作業ツリーの事情と推測したことで、依頼した人に、Codex 側から main が見えていたのだと指摘された。Claude の比較は、両方が対話を見たという前提で書き直された。

#### 比較で見つかった点

Claude 版と GPT 版は、write-slops の規則を写さず先に読ませること、タイムスタンプの一覧にせず因果でつなぐこと、確認を挟まずに進めたこと自体を欠点として扱わないこと、実際には検討していない代替案で記事を埋めないことで共通していた（Codex の比較）。代替案の三分類と「理由が記録になければ不明と書く」は、GPT 版では対話の前の初版（`dda0d00`）にすでにあり、Claude 版は対話を読んだあとで同じところに辿り着いた（Claude の比較）。「不要なものを必須にして縛りたくない」にも、三つとも応えようとしていた。Claude は自分が足した細目を削り、Codex は余談を任意にし、Gemini はもともと短い。

代替案を残す基準が、いちばん差の出たところだった。Claude 版の「実際に検討して進路を変えたもの」は、検討してすぐ見送ったために進路が変わらなかった案を落とす。TTS の件で言えば、ホスト側のドライバ更新は範囲外としてすぐ外れた案で、進路を変えていないが、追試の記事はまさにその案から始まった。GPT 版の「結果の条件・限界・再現に関係するもの」なら、この案を残せる。Claude は、Codex の比較を読むまでこの弱さを見落としていた。一方、Codex の比較は、「進路を変えたもの」のほうが記述を簡潔に保ちやすく、GPT 版の基準は読み手に不要な材料まで入りやすい、という得失も書いている。網羅的に並べない指定がその危険を減らすはずだが、うまく選べると示したわけではない。

Claude の比較では、Gemini 版の代替案の書き方が最も危うい。「退けられるたびに」は網羅を求める書き方で、実際には検討していない候補を後から並べることへの歯止めがない（Claude 版の一回目の版と同じ穴）。理由を環境の制約に限っているので、範囲の外だった、時間がなかった、測って外した、といった判断による見送りの置き場もない。Codex の比較も同じ方向で、環境構築の障害対応なら、環境要因の例は何を残すかを思い出す助けになりそうだが、採用しなかった理由が「その範囲は依頼されていない」「比較に時間がかかる」だった場合を拾いにくくなる可能性がある、と書いている（出力を比べて確かめたものではない）。Gemini 版の短さには実用上の利点がある、とも書いている。逆に GPT 版は読む指示が多く、実際に検討した案が少ない短い作業では、細かな区別が本文の重さにつながる可能性がある、と同じ比較は見ている。

依頼を書き直してよい理由を Gemini 版が外した点について、Claude の比較は、依頼した人が理由も一緒に書くよう求めていたことを踏まえつつ、「冒頭を、最後の答えがそのまま解決する形にする」という言い方は、依頼と答えを対応させるという一つ目の理由の中身を規則として取り込んでいるとも読める、としている。

Gemini 版は、write-slops の要約を末尾に写している。今は write-slops と食い違っていないが、write-slops が変わると古くなる。Claude と GPT は写しを避けた。Claude 版が持たず Gemini 版が持つものは、`AGENTS.md` からの案内と他のエージェント向けのリンク。Gemini 版が持たず Claude 版が持つものは、範囲外の選択肢を「人間に頼むべきだった」と書かない規則、記録だけから書くならそう言うこと、sketch との分担。

図については、Claude の比較の最初の版は、GPT 版が図を作ったことを良い点に数えた。Codex は、自分の図はファイル配置を確かめる助けにはなるが、執筆指示の良し悪しの証拠ではないので順位付けに使わない、と書いていて、Claude もそのとおりだと認めた。図があることは write-slops に従ったかどうかの話で、スキルの比較の材料ではない。Claude が図を試さず、試さなかった理由も書かなかったことは、write-slops への従い方の問題として別に残る。

利用環境への組み込みは、役割が違う別々のものだった。Claude 版の `agents/openai.yaml` は UI 向けのメタデータ、GPT 版と Gemini 版の `.agents/skills/` のリンクは発見用、`AGENTS.md` の案内は読み分けの指示で、一つがあることを他の確認済みという意味には扱えない。Codex は、自分のリンクの参照先と内容の一致は確かめたが、#138 のスキルを Codex や OpenCode で実行してはいない。Gemini の記事は agy から正しく読み込めると結論しているが、記事と PR 本文の検証欄には svg-gen の lint と Go のテストがあるだけで、agy の実際のスキル発見結果は示されていない。ここは動作未確認として扱うほかない。Codex の比較は、Gemini 版のリンクの対象（todo-md を含む）が、このタスクに必要な範囲より広いとも見ている。

Gemini の記事は、リンク構成を、ディレクトリ全体へのリンクにせず個別リンクにした理由として、ディレクトリのシンボリックリンクの走査差を挙げている。しかし Codex の比較が指摘するとおり、個別の入口もディレクトリのシンボリックリンクなので、その説明だけでは実行環境での堅牢性までは確かめられない。

#### 記事についての指摘

比較は、三つの記事の読み方にも及んだ。次はそれぞれの比較者の読みで、スキルを動かした結果の統制された比較ではない。

- Claude の記事は、一回目と二回目の調整を転換点にして時系列で書いていて、なぜスキルがその形になったかを追いやすい。一方、作業の中で実際に試して退けたものの記録は少ない。判断の大半が、記事や対話を読むことだったからでもある。
- GPT の記事の初稿には、リンク、PyYAML がなかったことと分離した検証環境、狭い画面で読めなかった図の修正といった、実装と検証の具体的な記録があった。一方、TTS の背景の再説明と書き方の規則の意図に使う分量が多く、対話を受けた調整が本筋に含まれていなかった。この版については、Codex 自身が、初稿が調整後スキルの試用だったことにはならない、と書いている。
- Gemini の記事で良いのは、リンク構成の二案を比べた段落と、svg-gen のラベルの失敗と直し方の段落で、捨てた代替案とその理由、失敗とその直し方という、このスキルが求める記録の形が素直に出ている。Claude の比較は、この実際の試行を具体的に書くやり方は取り込みたい、としている。気になった点は四つ。前半が issue のコメントの Q&A を言い直したもので、「真に必要としているのは」「こそが」のような言い切りが続き、試行や判断の記録ではないこと。「この改訂により、スキルは…記録テンプレートとして機能するようになった」「agy 環境から…正しく読み込み可能になった」と、確かめていない効果を確かめたように書いていること。前提の節に、参照しない PR として #128 と #129 が挙がっていること（#128 は TTS の追試の issue、#129 はマージ済みの TTS の PR で、並行していたのは #138 と #139 のはずだが、依頼文が実際に何と書いていたかは記録にない）。write-slops は番号付きリストに頼らないよう書いているのに、記事が 2 箇所で `1.` から `4.` のリストを使い、図も 4 節の名前を箱に入れて並べた、write-slops が避ける「文を箱にして並べた図」に近いこと。

語り口の差は、依頼した人が issue #133 で楽しみたいと言っていたものに近い形で出た、と Claude の総評は書く。Claude は日記に近く、何をなぜ直したかを順に書いた。Codex は確かめた範囲と確かめていない範囲を何度も区切り（Claude の総評は、やや過剰とも見ている）、PR の説明に近い慎重さになった。Gemini はスキルの 4 節を見出しにそのまま写し、言い切りが多い。どこまでがスキルのせいで、どこからが書き手の癖なのかは、この比較では分けられない。Codex の比較も、GPT 版の初稿にも TTS の再説明が多かったので、この差をモデルの固定的な筆致と読むことはできない、と書いている。

三つの記事とも、題材はスキル作りで、環境構築や追試のあとに書くという本来の用途では試されていない。

#### 統合するなら

比較の結論は、書き手によって強調点が違った。

- Claude の総評は、Claude 版の短さと記事側の決まり（範囲外の選択肢の書き方、sketch との分担、依頼を書き直してよい理由）を土台にして、GPT 版から、代替案の基準（結果の条件・限界・再現に関係するもの）と三分類、後から加わった条件の扱い、評価のしかたを変えた変更、既定で暫定扱いにしないこと、余談を任意にすること、`AGENTS.md` からの案内を取り込むのがよいとした。GPT 版の「渡す前の確認」や「新しい実験や公開を許可しない」のような作業手順の項目は、入れないほうがよい。Gemini 版から文面として取り込みたいものは、短さを目標にすること以外には見つからなかった。ペダンティックの禁止を残すか外すかは、Claude と Gemini で読みが割れたので、依頼した人が決めることだとした。
- Codex の比較は、すべての条項を足すと、両方の調整で減らそうとした義務がまた増える、と警告した。短い調査で sketch と記事の重複を減らしたいなら Claude 版の分担と冒頭・経緯をまとめる許可が、依頼が途中で変わって手順より結果の評価基準が動いた調査なら GPT 版の変更条件の扱いが明示的で、二つを統合するならまずその調査で必要な差を選びたい、とした。Gemini 版へ補うなら、理由不明を創作しない指示と、環境以外の範囲やコストによる見送りも残す基準の二点で、長い手順書にする必要はない。GPT 版には、必要な区別を保ったまま説明を短くできるかを見る余地がある。
- Claude の総評は、どれを残すにしても、記事はそれぞれの PR の記録として残し、スキルは一本にしてから fork での比較に進むのがよい、とも書いていた。
- どのスキルが良い記事を生むかは、これらの比較では分からない。次に確認するなら、次の技術調査のセッションから fork を 2 つ起こして、同じ材料で両方のスキルに書かせ、最初の問いへの答え、関係する代替案、条件の変化が残るか、判断の経緯を作っていないかを見る、という点で二つの比較は一致している。

### 統合版を作った

#### 総評の推奨どおりに足した最初の版

統合版の作業は、三つのスキルと、Claude の README と総評（`03-overall.md`）だけを読んだ状態で始まった。総評の推奨に沿って、Claude 版を土台に、GPT 版から次のものを取り込んだ。

- 代替案を残す基準（結果の条件・限界・再現に関係するもの）と、失敗した試行・検討したが実行しなかった案・あとで気づいた可能性の三分類
- 後から加わった条件を最初から分かっていたように書かないこと
- 結果の評価のしかたを変えた途中の変更も残すこと
- 回避策を既定では暫定扱いにしないこと
- 余談を任意にすること
- `AGENTS.md` からの案内

このとき、推奨には入っていない GPT 版の文も五つ、一緒に持ち込んでいた。表で条件を比べてよいこと、関係のない条件は書かないこと、一度の成功を互換性の保証や最善の解にしないこと、部分的な結果や否定的な結果も答えになること、余談の節にしか答えがない状態にしないこと。

総評が依頼した人に預けていた点が二つあったので、質問した。ペダンティックの禁止については、残す、という答え。三つの試作の扱いは、description がほぼ同じなので、Claude Code のスキル一覧に調査記事用のスキルが四つ並び、どれが選ばれるかが曖昧になる、という問題があった。答えは「残して description を変える」で、試作の description を「比較の記録として残した試作。名前で指定されたときだけ使う」に書き換え、`AGENTS.md` は統合版を既定として案内するように直した。ここまでを `489809d` でコミットした。

#### 今日の記事を全部読んで、足しすぎた分を外した

コミットのあとで、今日の記事を全部しっかり読んでから判断するように、と言われた。まだ読んでいなかった Claude の 01・02、Codex の README と 01・02、Gemini の記事を読むと、最初の版で一緒に持ち込んだ五つの文には、記事が先に釘を刺していた。Codex の 01 は、すべての条項を足すと両方の調整で減らそうとした義務を再び増やす危険がある、と書き、Claude の 01 は、GPT 版の「渡す前の確認」のような作業手順の項目は入れないほうがよい、と書いていた。余談の節にしか答えがない状態にしない、という文は、GPT 版では渡す前の確認の一項目だった。

総評の推奨リストに入っていなかった五つの文は、どれもこの警告にあたると判断して外し、`1d3c3b9` でコミットした。部分的な結果の文は、Claude 版の「答えられていない部分があればどこかを書く」とほぼ重なっていた。互換性の保証の文は、既定で暫定扱いにしないことの言い足しだった。どちらも、外しても失われるものは少ない。
