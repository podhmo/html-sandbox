# Document Merge

## このSkillが解く問題

「文書Xと文書Yをマージして」と頼まれたとき、素朴な処理は2つに崩れる。

- **連結（concat）**：Xの後ろにYを置く。章の順序が「出典順」になり、Yの第2章がXの第3章で導入された概念を前提にしていても、読者はそれをまだ知らない。重複する章もそのまま残る。
- **要約**：両方を縮める。情報が落ちる。マージは圧縮ではない。

マージとは、**XとYに含まれる内容を（重複を除いて）すべて保存したまま、章の並びが「前提 → 展開」の一本の流れとして成立するように文書を再構成すること**である。章を並べる基準は出典ではなく依存関係。

そのため本文を直接いじらず、一度「章ごとの骨子」に下ろし、骨子の上で構成を統合してから本文に戻す。

## 粒度の原則：章を単位にし、必要な所だけ降りる

考える単位は**章**（文書が大きければ章、小さければ節）。一文ずつに分解すると、文書全体の構造が見えなくなり、作業量も文書の長さに比例して膨らむ。章は書き手がすでに「一まとまりの話」として切った単位なので、それをそのまま使う。

ただし、章どうしが部分的に重なる・食い違う箇所だけは、その章の中に**一段だけ降りて**節や段落の単位で比べる。全体を細かく刻むのではなく、問題のある場所だけ解像度を上げる。

見出しのない文書や、見出しが内容と合っていない文書は、話題の切れ目で暗黙の章に分けてから始める。

## 全体の流れ

1. 各文書を章ごとの骨子（章カード）に展開する
2. 各文書の章の依存の流れを把握する
3. XとYの章を対応づける
4. 前提層を統合する（ここがマージの本体）
5. 統合された目次を組み立てる
6. 章ごとに本文を書く
7. 検証する

文書が3つ以上なら、全部を一度に章カードにしてから同じ手順で処理する（2つずつ畳み込むと、最初のペアの都合で構成が固まってしまうため）。

---

## 1. 章カードに展開する

各章について、次の項目を持つカードを作る。

- **ID**：`X1`, `X2`, … / `Y1`, `Y2`, …（節まで降りたときは `X3.2` のように）
- **見出し**：原文の見出し
- **要旨**：この章が言っていることを一〜二文で
- **要点**：章の中身を構成する主な項目を数個。詳細は原文にあるので、ここでは「何が書いてあるか」がわかれば十分
- **前提とするもの**：この章を読むのに、先に読者が知っている・受け入れている必要があるもの（概念、用語の定義、決定事項、背景事情）
- **確立するもの**：この章を読み終えた読者が新たに得るもので、後の章が使うもの

「前提とするもの」と「確立するもの」が、章と章をつなぐ接点になる。章Bの「前提とするもの」が章Aの「確立するもの」に含まれていれば、AはBより前に来る必要がある。

**文書全体の暗黙の前提も書き出す。** どの章にも書かれていないが文書全体が当然としているもの（対象読者、スコープ、時点・バージョン、立場、用語の意味）は `X0` というカードにまとめる。マージで衝突するのはたいていここである。

## 2. 章の依存の流れを把握する

文書ごとに、「前提とするもの」と「確立するもの」を結んで、章の依存関係を一行ずつ書き出す（例：`X2（要件）→ X3（アーキテクチャ）：X3はX2の要件一覧を前提にする`）。

これで各文書の**構成の背骨**が見える。原文の章順がこの依存と一致しているとは限らない。マージ後の構成はどちらの背骨にも従わず、統合後の背骨に従う。

## 3. 章を対応づける

XとYの章を突き合わせ、各ペアを以下に分類する。

| 関係 | 意味 | 扱い |
|---|---|---|
| 同一 | 同じ話題を同じ範囲で扱う | 1章にする。内容は両方の和集合 |
| 部分重複 | 話題は重なるが範囲や詳しさが違う | 節の単位まで降りて、重なる節と片方にしかない節を分ける |
| 包含 | 一方の章が他方の章の一部を詳しく書いている | 一般側を章、詳細側をその中の節にする |
| 補完 | 片方にしかない章 | 残す。どこに置くかは依存関係で決める |
| 前提ずれ | 同じ話題だが、依存している前提が違う | 前提を統合してから判断する（ステップ4） |
| 矛盾 | 両立しない内容がある | 解消方針を決める（ステップ4） |

見出しが違っても中身が同じ章、見出しが同じでも中身が違う章があるので、見出しではなく要旨と要点で比べる。

用語の揺れ（同じ概念に別の言葉、同じ言葉で別の概念）はここで拾い、統一表記を決める。用語の不一致は見かけの重複や見かけの矛盾を生む。

## 4. 前提層を統合する

マージの本体。X0・Y0（文書全体の前提）と、各章の「前提とするもの」を集めて、統合後の文書の土台を作り直す。

**4-1. 文書全体の前提を揃える。** X0とY0を比べる。

- 一致していれば、そのまま統合文書の前提になる。
- **一方が他方を含む**（例：Xは「サービス全体」、Yは「その認証部分」）なら、広い方を文書のスコープにし、狭い方はその中の一部として位置づける。
- **独立**しているなら、統合文書のスコープは両方を覆うものにする。冒頭（序章・概要）で両者の関係を説明する必要がある。
- **矛盾**するなら（対象読者が違う、前提とする版が違う、など）、次のどれかを選ぶ：
  - 場合分けにする：「〜の場合は…」。両方が別の状況で正しいとき
  - 一方を採る：明らかに一方が古い・誤り・範囲外のとき。採らなかった側とその理由を報告に残す
  - ユーザーに尋ねる：どちらを採るかが方針・立場・事実確認に関わり、文書から決められないとき

**4-2. 章の前提が満たされるか確かめる。** 各章の「前提とするもの」について、統合後の構成でそれを「確立する」章が前にあるかを見る。ない場合：

- どこか後ろの章が確立しているなら、並び順で解決する（ステップ5）
- どこにも確立されていないなら（元の文書では暗黙だった、あるいは相手側の文書にしかなかった）、**橋渡し**を作る

**4-3. 橋渡しを作る。** 橋渡しは、章の冒頭に置く導入段落、章と章の間の短い節、または序章の一部として入れる。役割は、すでにある内容どうしの関係（なぜこの話がここに来るか、前の章のどれを受けているか、どの場合の話か）を読者に示すこと。

橋渡しは**新しい事実を持ち込まない**。必要に見える内容がX・Yのどちらにもないなら、作らずにユーザーに指摘する。

`B1`, `B2`… のIDを付け、どこに置き、何と何をつないでいるかを記録する。

## 5. 統合された目次を組み立てる

統合文書の目次を作る。各章について次を書く。

- 新しい章番号と見出し
- **出典**：どの元章・元節から構成するか（例：`第3章 認証 ← X3.1, Y2, Y3.2 ＋ B2`）
- 前提とするもの / 確立するもの

並び順は依存関係に従う（どの章も、その前提を確立する章より後）。依存関係で順序が決まらない章どうしは、読み手にとって自然な順（概要→詳細、背景→決定→実施、全体→部分、時系列）で並べる。

見出しも新しい構成に合わせて付け直す。元の見出しをそのまま並べない。

この目次がマージの設計図になる。本文を書く前に、文書が長い場合や判断が多い場合は、目次と出典をユーザーに見せて確認を取ってよい。

## 6. 章ごとに本文を書く

目次の上から一章ずつ書く。各章で：

- 出典の元章・元節の本文を読み、その内容をすべて含む本文を書き直す。**要約しない。** 元の具体例・数値・手順・図表の参照・留保はそのまま持ってくる
- 同一・部分重複の箇所は一つの記述にまとめる。言い方が違うだけなら、より正確・具体的な方を採り、もう一方にしかない細部を加える
- 章の冒頭で、その章が前の章のどれを受けているかが読者にわかるようにする（必要なら橋渡しをここに置く）
- 文体・トーン・人称・表記は一つに揃える。指定がなければ、主となる側（分量が多い方、またはユーザーが「ベース」と言った方）に合わせる
- 用語はステップ3で決めた統一表記を使う
- 出典の痕跡（「別の資料では」「Y版によれば」）は残さない。最初から一人が書いた一つの文書として読めるようにする
- 章をまたぐ参照（「第3章で述べたように」）は新しい章番号で付け直す

文書が長いときは、一章書くごとに次の章に進む。全体を一度に書こうとすると後半の章が要約に崩れやすい。

## 7. 検証する

文書を出す前に、次を確認する。

- **網羅**：X・Yのすべての章（降りた所はすべての節）が、統合文書のどこかに入っているか。ステップ5の出典欄から逆引きして、使われていない元章・元節がないかを見る。落ちたものがあれば、それは要約になっている
- **分量の目安**：統合文書が、重複を除いた元文書の合計より大きく短くなっていないか。大きく短いなら要約に崩れている箇所がある
- **前提順序**：頭から読んで、どの章も、その前提を確立する章より後に出てくるか
- **橋渡しの健全性**：橋渡しが新しい事実を持ち込んでいないか
- **矛盾の処理**：ステップ3・4で見つけた矛盾がすべて、場合分け・採択・質問のどれかで処理されているか
- **相互参照**：章番号・節番号・図表番号の参照が新しい構成で正しいか

## 出力

ユーザーへの出力は次の構成にする。

1. **統合文書**（主成果物）。形式は、ユーザーの指定、なければ元の文書の形式に合わせる
2. **マージ報告**（短く）：
   - 統合文書のスコープと前提（数行）
   - **章の対応表**：新しい章ごとに、どの元章・元節から作ったか
   - 主な重複と、どちらの記述を採ったか
   - 追加した橋渡しとその理由
   - 矛盾とその処理（採らなかった側を含む）
   - ユーザーに判断を求める点（あれば）

章の対応表は、ユーザーが「元のあの話はどこへ行ったか」を確かめるための索引になるので、短い文書でも付ける。

矛盾の中にユーザーにしか決められないものがあるときは、勝手に決めずに尋ねる。ただし、決まっている部分まで止める必要はない。仮の扱い（例：両論併記）で全体を書き、その箇所を明示して確認を求めてもよい。

## 例

**X：「新会員サービス 基本設計書」**
1. 背景 2. 要件 3. システム構成 4. 運用

**Y：「認証基盤 刷新提案」**
1. 現行の課題 2. 認証方式（SSO） 3. API仕様 4. 移行計画

**ステップ1：章カード（抜粋）**

```
X0 [文書全体の前提] 対象は新会員サービス全体。読者は開発チーム。
                    認証は「ID・パスワード方式」を暗黙に前提（X3内の記述から）
X2 要件
   前提とするもの：X1の背景（会員数の増加）
   確立するもの：機能要件・非機能要件の一覧
X3 システム構成
   前提とするもの：X2の要件
   確立するもの：コンポーネント構成（認証部を含む）

Y0 [文書全体の前提] 対象は認証基盤のみ。読者は開発チームと情シス
Y2 認証方式（SSO）
   前提とするもの：Y1の現行課題
   確立するもの：SSO方式の採用、IdPの選定
Y3 API仕様
   前提とするもの：Y2のSSO方式
   確立するもの：認証APIのエンドポイント一覧
```

**ステップ3：対応**
- X1（背景）とY1（現行の課題）：部分重複。節に降りると、X1.2「会員管理の手作業」とY1.1「パスワード再発行の問い合わせ増」は同じ問題の別の面
- X3（システム構成）とY2・Y3：包含。Y2・Y3はX3の認証部の詳細
- X3の認証部（ID・パスワード）とY2（SSO）：**矛盾**
- X4（運用）とY4（移行計画）：補完

**ステップ4：前提層**
- スコープ：X0（サービス全体）がY0（認証基盤）を含むので、統合文書はXのスコープ。読者はXとYの和（開発チーム＋情シス）
- 認証方式の矛盾：Yの方が新しい提案で、X3の認証部はYの導入前の記述と判断 → SSOを採用。ただしこれは方針の判断なので、報告で確認を求める
- 橋渡し B1：システム構成の章で、全体構成を示した後、「認証部は以下の方式で構成する」とYの内容につなぐ導入段落

**ステップ5：統合目次**

```
1 背景と課題           ← X1, Y1（X1.2とY1.1を統合）
2 要件                 ← X2（認証要件にY1由来の項目を追加）
3 システム構成         ← X3（認証部の記述をSSOに更新）＋ B1
  3.1 全体構成         ← X3
  3.2 認証方式         ← Y2
  3.3 認証API          ← Y3
4 移行計画             ← Y4
5 運用                 ← X4
```

YのAPI仕様（Y3）はSSO方式（Y2）を前提とし、SSO方式は全体構成（X3）の中に位置づけて初めて意味を持つので、3.1→3.2→3.3の順になる。移行計画は構成が決まってからの話であり、運用は移行後の話なので、4→5の順になる。

連結なら、Xの第3章で「ID・パスワード方式」と書いた後に、Yの第2章で「SSOを採用」と出てきて、読者はどちらが正しいかわからない。要約なら、API仕様のエンドポイント一覧や移行の手順が落ちる。マージでは、認証の詳細が全体構成の中の節として入り、方式の食い違いは解消されて、移行計画も運用の前の正しい位置に来る。
