# 技術調査のあとに書く記事のスキルを、issue の下書きから作った

## 依頼と、始めた時点の材料

依頼は二つだった。[issue #133 のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903)を踏まえて、技術的な探索のあとに slops を書くための、write-slops を土台にした特殊化スキルを作ること。そのあと、直近の記事や issue を参照しながら、作ったスキルで経緯を含めた記事を書くこと。この記事が後者にあたる。

始めた時点で手元にあったのは次のもの。

- issue #133 のコメント 8 件。最後の 1 件（11-06）が今回の起点で、Q&A 形式の整理と、`write-slops-investigation-notes` という名前の SKILL.md の下書きがそのまま載っている。
- 11-05 の slops 5 本。[答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md)、[slops の書き方を読み直した日](2026-11-05-reading-slops-again.md)、[記事を書く目的で分けて、依頼をテンプレートにする](2026-11-05-slops-use-case-templates.md)、[依頼した人にとって良い slops とは](2026-11-05-good-slops-for-requester.md)、[記事を書くスキルを考えて、fork で書き比べた](2026-11-05-skill-for-new-articles.md)。
- 既存の [write-slops](../.claude/skills/write-slops/SKILL.md)。

コメントには Google Drive と AI Studio のリンクが 6 つ付いていて、Q&A はそこでの対話を圧縮したものに見える。リンク先は認証が要るので開いていない。下書きがどういう対話から出てきたかは、コメントに書かれた Q&A の範囲でしか分からない。

## 下書きを読んで、何を変えるか決めた

下書きの骨組みは、依頼と前提条件、試行と判断の経過、最初の問いへの答え、余談、の 4 節だった。この並びは変えていない。11-05 の書き比べで出た「求めていた形」（本筋、余談、最後にまとめ）とほぼ同じ形で、そちらの結論とも食い違わなかったからだ。変えたのは中身の細部で、どれも直近の記事のどこかに理由がある。

### 文体の指示を削った

下書きは冒頭で「Keep the tone matter-of-fact」と書き、知的な鋭さの誇示を禁じていた。後半はそのまま残し、トーンを指定する形容は落とした。[記事を書く目的で分けて…](2026-11-05-slops-use-case-templates.md)で、issue のコメントから読み取った文体の条件に応えるために、観察ではない文が入っていたことが表になっている。「淡々と」と書けば淡々と聞こえる文を足しに行く、という同じことが起きると考えた。代わりに、何を書かないか（主張を立てない、コーディングエージェント一般の性質に広げない、書き手を採点しない）だけを書いた。

一方で issue には「起きたことの記録と解釈はあってほしい」「淡々と記録するだけではつまらない」ともある。そこで、その調査についての解釈（そのときエラーが何を意味すると思ったか、なぜ一方の道が安く見えたか）は歓迎する、と一文足した。広げるのは禁止、その場の解釈は可、という線にしている。

### 回避策と計測値に条件を付けさせる

下書きにも「回避策は環境の制約に結び付いた条件付きの選択として書く」とあった。これを具体例付きにし、計測値にも同じことを求める項目を足した。元になったのは [答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md) の表で、前回の TTS 検証では cu128 への固定が「重要」という無条件の規則として残り、Piper の RTF 0.13 は同じ venv で測り直すと 0.07 だった。原因がホスト側のドライバにあったことも、記録の中に材料はあったのに規則からは参照されていなかった。それで「原因がエージェントの変えられない場所にあったなら、どこにあったかを書く」も入れた。

この記事の側から見ると、この項目は 11-05 の記事の「性質」の節とは逆向きになっている。あの記事は 1 件の追試から、変更できる範囲の中で解を選ぶというエージェントの性質を立てた。issue #133 の「論ずる文体が鼻についてきた」はそこへの反応だった。スキルでは性質を論じる代わりに、その都度の記録に条件を残させる側に寄せた。

### 作業したセッションで書く、を足した

下書きにはなかった。[fork で書き比べた記事](2026-11-05-skill-for-new-articles.md)の一回目の却下は、「作業が終わったあとに記録だけを読んで書いたから…」という前提の取り違えだった。実際には記事は作業したセッションで書かれていて、依頼した人の運用もそうなっている。捨てた選択肢とその理由はコミットにも docs にもほとんど残らないので、このスキルにとっては前提そのものになる。そう考えて冒頭に置いた。

### docs/sketch との分担を書いた

技術調査は、このリポジトリでは `docs/sketch/` に手順と事実のまとめが残ることが多い（TTS なら `docs/sketch/ja/tts-wsl2.md`、[PR #136](https://github.com/podhmo/html-sandbox/pull/136) なら `docs/sketch/ja/wsl2-perf-bind-mount.md`）。記事がそれを写し直すと、二箇所に同じ手順が置かれて片方が古くなる。issue のコメントにも「sketch は何かを実現するための情報収集で、それを適用した結果の出来事を綴るのが日記の一部」とある。それで、手順と事実は sketch、どうやってそこに辿り着いたかは記事、と分けて、記事からはリンクする形にした。

### write-slops の写しを持たない

下書きの最後には「Base rules from write-slops」として、tinymarkdown、svg-gen、バンドルの決まりが短く写してあった。これは削り、冒頭で write-slops を先に読むように書くだけにした。写しを持つと、write-slops 側が変わったとき（たとえば 11-05 に `*` の強調を禁じた [PR #132](https://github.com/podhmo/html-sandbox/pull/132)）に追従が漏れる。[write-slops-threads](2026-11-05-skill-for-new-articles.md#01-write-slops-threadsmd) も同じやり方で、そちらの比較でも「違いを一箇所にしておく」が理由だった。

### 余談の節は残し、各項目に確かめたかどうかを付ける

write-slops-threads の書き比べでは、「筋を一本選び、ほかは名前だけ挙げる」という規則のせいで、求められていた余談（fork の提案）まで落ちた。下書きの第 4 節はちょうどその逆で、本筋から外したものを結びのあとに集める。ここはそのまま採った。足したのは、余談の各項目に確かめたかどうかを書かせることだけで、write-slops の「試したことと試していないことを区別する」をこの節にも効かせるためだ。

### 最後を反省で締めない、は強めた

下書きにもあった項目だが、書き比べた 2 本がどちらも「自分がどこで間違えたか」で締めていたので、書き方を足した。結果を変えた間違いは、起きた場所（第 2 節）に書く。こうすると間違いは消えずに残り、結びは最初の問いへの答えになる。issue のコメントの Q2 にある「人間に聞くべきだったという反省ではなく、捨てた代替案とその理由」もここに対応する。

### 使う場面の書き方

description は、write-slops-threads のように「名前を指定されたときだけ使う」にはしなかった。あちらは比較用の実験で、こちらは技術調査の記事を書くときに普段から使ってほしいものだからだ。技術調査（環境構築、実現性の確認、追試、デバッグ）の記事を書くときは write-slops の代わりにこれを使う、と書いた。機能紹介や「書き方そのもの」の記事は、引き続き write-slops だけで書く想定になる。

名前は下書きの `write-slops-investigation-notes` のまま。Q4 に、`tech-notes` だと解説記事に、`trial-log` だと奮闘記に寄る、という検討が書かれていて、それ以上の材料がなかった。

## できたもの

スキルは [.claude/skills/write-slops-investigation-notes/SKILL.md](../.claude/skills/write-slops-investigation-notes/SKILL.md) に置いた。`.opencode/skills` は `.claude/skills` へのシンボリックリンクなので、OpenCode からも同じものが見える。write-slops に合わせて `agents/openai.yaml` も付けた。

下書きとの対応をまとめると次のとおり。

| 項目 | 下書き | 置いたスキル | 理由の出どころ |
| --- | --- | --- | --- |
| 4 節の並び | あり | そのまま | #135 で求められていた形と一致 |
| トーンの指定 | matter-of-fact | 削除。書かないことだけ書く | use-case-templates の表 |
| その調査についての解釈 | なし | 可と明記 | #133 のコメント |
| 回避策の条件 | あり | 具体例付き、原因の場所も書く | answers-under-constraints |
| 計測値の条件 | なし | 回数・環境・ウォームかを書く | 同上（Piper 0.13 / 0.07） |
| 作業したセッションで書く | なし | 冒頭に追加 | #135 の一回目の却下 |
| docs/sketch との分担 | なし | 手順は sketch、経緯は記事 | #133 のコメント、#136 |
| write-slops の写し | あり | 削除、先に読ませる | write-slops-threads と同じ理由 |
| 余談の節 | あり | 各項目に確認済みかを付ける | #135 で余談が落ちた件 |

この記事はそのスキルの順に書いた。ただ、題材がスキル作りなので、第 2 節の「捨てた道と制約」は、権限やバージョンではなく、直近の記事に書かれた失敗が制約の代わりになっている。技術調査の記事で使えるかは、まだ確かめていない。

## 余談

- 本来の題材で書いていない。直近の技術調査は [PR #136](https://github.com/podhmo/html-sandbox/pull/136)（WSL2 の perf の bind mount で `apt upgrade` が失敗した件）だが、これは Devin のセッションで行われ、記事は書かれていない。このセッションには捨てた選択肢の材料がないので、このスキルで書いても sketch の言い換えにしかならないはず。次に Claude Code で技術調査をしたときに試すのが順当だと思う。未確認。
- write-slops との書き比べもしていない。[fork で書き比べた記事](2026-11-05-skill-for-new-articles.md)と同じく、調査したセッションから fork を 2 つ起こせば、違いをスキルだけにできる。その手順はこのスキルには書いていない（必要になったら write-slops-threads のブランチにあるものを参照する）。
- Drive と AI Studio のリンク先は読んでいない。下書きに至る対話の中に、ここで落とした項目（トーンの指定など）を入れた理由があったかもしれない。
- issue #133 の「色々なモデルに記事を書かせて筆致の差を楽しみたい」とは、トーンの指定を削ったことが合っている気がする。スキルが文体を決めなければ、差はモデル側から出る。これも試してはいない。
