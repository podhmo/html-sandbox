## スキルの比較

#140 のスキルは、issue のコメントに載っていた下書きにいちばん近い。4 節の並び、年表やコミットログにしないこと、因果の散文、代替案と理由、回避策を条件付きで書くこと、途中の転換を経緯に入れること、反省で締めないこと、余談を結びのあとに置くこと。どれも下書きのままか、短く言い換えたものだ。短く読みやすい点は、依頼した人の「不要なものを必須にして縛りたくない」に合っている。

対話を受けた調整（`9b29d22`）では、二つのことをしている。

一つは、冒頭の「ペダンティックな分析、ディベート風の論述、鋭さの誇示をしない」を削り、「意図と環境の具体的な摩擦に焦点を当てる」に置き換えたこと。記事には、文体の否定命令を重ねるとモデルごとの語り口の多様性（セレンディピティ）を損なうから、と理由が書かれている。issue の「自由に書けという表現自体が命令として機能する」や、対話の「3 はセレンディピティ的に得られるべき」を読めばありうる解釈だが、対話の中でこの禁止は、investigation という名前が学者ぶった語り口を呼びそうだ、という懸念から依頼した人が入れたものだった。こちらは同じ対話から、この禁止を理由ごと戻している。同じ材料から逆の結論になったところで、どちらが意図に近いかは依頼した人にしか決められないが、こちらは「名前の副作用への手当て」と読んだ。

もう一つは、依頼の書き直しについて、下書きにあった二つの理由（依頼と確認結果の形にするため、途中の転換と重複させないため）を外し、「第 3 節で答えるべき技術的な問いと成果物に再構成する」とまとめたこと。依頼した人は理由を一緒に書くよう求めていた。一方で「冒頭を、最後の答えがそのまま解決する形にする」という言い方は、依頼と答えを対応させるという一つ目の理由の中身を、規則として取り込んでいるとも読める。

代替案の書き方は、#140 のほうが危うい。「候補が退けられるたびに、迂回を強いた具体的な環境の制約を記録する」とあり、例はコマンドの失敗、root がない、ドライバの不一致、パッケージの大きさ。二つ気になる。まず「たびに」は網羅を求める書き方で、実際には検討していない候補を後から並べることへの歯止めがない（こちらの一回目の版と同じ穴）。次に、理由を環境の制約に限っている。範囲の外だった、時間がなかった、測って外した、のような判断による見送りの置き場がない。

こちらにあって #140 にないものは、範囲外の選択肢を「人間に頼むべきだった」として書かないこと（#140 は記事には書いているがスキルにはない）、記録だけから書くならそう言うこと、`docs/sketch/` との分担。#140 にあってこちらにないものは、`AGENTS.md` からの案内と、他のエージェント向けのリンク。

write-slops の要約を末尾に写していることは、こちらと Codex が避けたことで、#140 は残した。今のところ内容は write-slops と食い違っていないが、write-slops 側が変わると古くなる。

## 記事の比較

#140 の記事は 4 節の見出しに番号を振り、スキルの構造をそのまま記事の形にしている。読みやすく、どこに何があるかは分かりやすい。

良いところは、第 2 節の後半にある実際の試行だ。`.agents/skills` を丸ごと `.claude/skills` へのリンクにする案と、スキルごとにリンクを置く案を比べて後者を選んだこと、svg-gen にラベルを `\n` 入りの文字列で渡して幅の計算が崩れ、`labelLines` の配列に直したこと。前者は捨てた代替案とその理由、後者は失敗とその直し方で、このスキルが求めている記録の形がいちばん素直に出ているのは三つの記事の中でこの段落だと思う。ただ、ディレクトリリンクを退けた理由（ツールによって走査の挙動が異なる場合がある）は一般論で、何かを試して確かめた形跡はない。

気になったところは四つある。

- 第 2 節の前半は、issue のコメントの Q&A（四つの課題、依頼した人が必要としている情報、名前の選び方）を言い直したもので、試行や判断の記録ではない。「真に必要としているのは」「こそが」「まさに」のような言い回しが続き、issue #133 が最初に挙げていた論じる調子に近い。ペダンティックの禁止を外した版で書かれたことと関係があるかもしれないが、確かめようはない。
- 効果をまだ確かめていないことを、確かめたように書いている。「この改訂により、スキルは…記録テンプレートとして機能するようになった」「agy 環境から基本スキルと特化スキルの双方が正しく読み込み可能になった」。PR のテスト計画にあるのは svg-gen の lint と `make test-go` で、agy での読み込みは確認項目にない。
- 前提の節に「他のエージェントが作業中の PR（具体的には PR #128、PR #129）は参照しない」とある。#128 は TTS の追試の issue、#129 はマージ済みの TTS の PR で、並行して作業していたのは #138 と #139 のはず。
- write-slops は番号付きリストに頼らないよう書いているが、記事は 2 箇所で `1.` 〜 `4.` のリストを使っている。図も 4 節の名前と除外するものを箱に入れて並べたもので、write-slops が避けるよう書いている「文を箱にして並べた図」にあたる。

こちらの記事は、一回目と二回目の調整を転換点にして時系列で書いていて、なぜスキルがその形になったかは追いやすい。一方で、Gemini の記事のリンク構成の段落のような、作業の中で実際に試して退けたものの記録は少ない。こちらの作業が、ほとんど記事を読んで判断することだったからでもある。図はない。

## 総評（#138 と #140）

#140 のスキルは下書きに忠実で短い。その代わり、下書きにあった穴（代替案を網羅させる書き方、後付けの候補への歯止めがないこと、理由を環境の制約に限ること）もそのまま残っている。対話を受けた調整は、こちらと逆の方向（ペダンティックの禁止を外す）に進んだ。

記事は構造が分かりやすく、リンク構成と図の失敗の段落は、このスキルの使い方の良い見本になっている。ただ前半は issue の要約で、効果の言い過ぎと PR 番号の誤りがある。

#140 から取り込みたいのは、`AGENTS.md` からの案内と、記事の中で実際の試行（リンク構成、図の失敗）を具体的に書いたやり方。スキルの文面として取り込みたいものは、短さ以外には見当たらなかった。
