# 技術調査のあとに書く記事のスキルを、issue の下書きから作った

## 依頼と、始めた時点の材料

依頼は、[issue #133 のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903)を踏まえて、技術的な探索のあとに slops を書くための特殊化スキルを write-slops の上に作り、そのスキルで経緯の記事を書くこと。この記事が後者にあたる。

始めた時点で手元にあったのは次のもの。

- issue #133 のコメント 8 件。最後の 1 件（11-06）が起点で、Q&A 形式の整理と、`write-slops-investigation-notes` という名前の SKILL.md の下書きが載っている。
- 11-05 の slops 5 本。[答えはその時点の制約から出てくる](../2026-11-05-answers-under-constraints.md)、[slops の書き方を読み直した日](../2026-11-05-reading-slops-again.md)、[記事を書く目的で分けて、依頼をテンプレートにする](../2026-11-05-slops-use-case-templates.md)、[依頼した人にとって良い slops とは](../2026-11-05-good-slops-for-requester.md)、[記事を書くスキルを考えて、fork で書き比べた](../2026-11-05-skill-for-new-articles.md)。
- 既存の [write-slops](../../.claude/skills/write-slops/SKILL.md)。

コメントに付いていた Google Drive と AI Studio のリンクは認証が要るので開いていない。だから最初は、下書きがどういう対話から出てきたかを Q&A の範囲でしか知らなかった。

## 一回目: 直近の記事に照らして下書きを直した

下書きの骨組みは、依頼と前提条件、試行と判断の経過、最初の問いへの答え、余談、の 4 節。11-05 の書き比べで依頼した人が示した形（本筋、余談、最後にまとめ）とほぼ同じだったので、並びは変えなかった。変えたのは中身で、それぞれ直近の記事に理由を求めた。

- 冒頭の「Keep the tone matter-of-fact」を削った。[記事を書く目的で分けて…](../2026-11-05-slops-use-case-templates.md)に、文体の条件に応えるために観察ではない文が入っていたことが表になっていて、トーンの指定は同じことを起こすと考えた。
- その調査についての解釈は書いてよい、と足した。issue の「起きたことの記録と解釈はあってほしい」から。
- 回避策に加えて計測値にも条件を付けさせた。[答えはその時点の制約から出てくる](../2026-11-05-answers-under-constraints.md)の、cu128 固定が「重要」という無条件の規則として残った件と、Piper の RTF 0.13 が測り直すと 0.07 だった件から。
- 「作業したセッションで書く」を冒頭に足した。[fork で書き比べた記事](../2026-11-05-skill-for-new-articles.md)の一回目の却下が、この前提の取り違えだったから。
- `docs/sketch/` との分担（手順は sketch、どう辿り着いたかは記事）を足した。issue の「sketch は情報収集、それを適用した結果の出来事を綴るのが日記の一部」から。
- 下書き末尾の write-slops の要約を削り、先に write-slops を読ませるだけにした。写しを持つと、[PR #132](https://github.com/podhmo/html-sandbox/pull/132) の `*` 禁止のような変更に追従が漏れる。
- 余談の各項目に、確かめたかどうかを付けさせた。

この版で PR にした。

## 下書きの元になった対話を受け取った

PR のあと、依頼した人が下書きを作った対話の全文を貼って、自分ならどう調整するかを尋ねた。読んで分かったのは、一回目の直しのうち二つが、理由を知らずに削ったものだったことだ。

一つは matter-of-fact。対話では、名前の候補を `tech-notes`、`investigation-notes`、`trial-log` から選ぶときに、investigation という語が学者ぶった論述を呼びそうだという懸念が出て、その防波堤として置かれていた。文体の指定ではなく、名前の副作用への手当てだった。もう一つは、冒頭の依頼を変形してよいという許可に付いていた二つの理由（記事を「依頼とその確認結果」の形にするため、途中の方針転換を経緯に書くなら全文を冒頭に置くと読みにくいため）。依頼した人は理由も一緒に書くよう求めていたが、一回目の版は許可だけを残していた。

逆に、一回目で足したもののいくつかは、対話の「不要なものを必須にして作業を縛りたくない」に反していた。計測値の条件として回数やウォームかを挙げたのは TTS の具体例に寄りすぎで、answers-under-constraints は依頼した人が「何が書かれているかではなく、どう書かれているかの参照」と位置づけていた記事だった。余談に確認済みかを付けさせるのは、write-slops 本体の「試したことと試していないことを区別する」と重なる。「作業したセッションで書く」は、スキルを読み込んだエージェントの側では守りようのない運用の前提だった。

対話には、一回目では拾えていなかった線引きもあった。欲しいのは「なぜホスト側のドライバ更新を人間に頼まなかったか」ではなく「どの選択肢を捨てたか」で、前者を是とすると人間に聞きすぎる逆の失敗が起きる、というもの。一回目の版の「原因が変えられない場所にあったなら、どこにあったかを書く」は、書き方次第で前者に滑る。

もう一つ、対話の中のシミュレーションは「事後に代替案を書く前提があるので、作業中に除外した選択肢をメモに残すようになる」と予測していた。ただこのスキルは書く段階で読み込まれるので、作業中の振る舞いは変えられない。起こりうるのは、代替案の節を埋めるために、あとから候補を並べることのほうだと考えた。たとえばシミュレーションが捨てた案として挙げた VOICEVOX や Fish Speech は Grok の候補リストにあったもので、作業中に検討されたのかは分からない。一回目の版の「For every dropped path」は、それを後押しする書き方だった。

## 二回目: 戻したもの、減らしたもの、足したもの

これを受けて、スキルを次のように直した。

- 捨てた代替案は、そのとき実際に検討して進路を変えたものだけを書く。検討していない候補を並べて網羅的に見せない。代替案が少なければこの部分は短くてよい。
- 変えられない範囲の選択肢は、バージョンと同じく環境の境界として書き、人間に頼むべきだったこととしては書かない。確認を挟まずに進めたこと自体を欠点として説明しない。
- ペダンティックな分析や鋭さを見せることの禁止を戻した。形容詞としてのトーンの指定は戻さず、investigation は題材の話で語り口の話ではない、と一言添えた。
- 依頼を変形してよい理由の二点を戻した。
- 途中の調整は、そのあとにしたことを変えたものだけ書く。完全なトレースは要らず、知見と手順を再現できれば足りる、と書いた。
- 計測値の条件は「数値を出すなら、分かっている条件を添える」に弱めて、第 3 節に移した。
- 余談の確認済みラベルは削った。
- 「作業したセッションで書く」は、「記録だけから書いているならそう言い、記録にない代替案や理由を補わない」という条件付きの指示に置き換えた。

## できたもの

スキルは [.claude/skills/write-slops-investigation-notes/SKILL.md](../../.claude/skills/write-slops-investigation-notes/SKILL.md) にある。`.opencode/skills` は `.claude/skills` へのシンボリックリンクなので OpenCode からも見え、write-slops に合わせて `agents/openai.yaml` も付けている。description は write-slops-threads と違って「名前を指定されたときだけ」にはせず、技術調査（環境構築、実現性の確認、追試、デバッグ）の記事では write-slops の代わりに使う、とした。

下書きとの対応は次のとおり。

| 項目 | 下書き | 置いたスキル | 理由の出どころ |
| --- | --- | --- | --- |
| 4 節の並び | あり | そのまま | #135 で求められていた形と一致 |
| ペダンティックの禁止 | あり（matter-of-fact と一緒） | 禁止だけ残す | 対話（名前の副作用） |
| その調査についての解釈 | なし | 可と明記 | #133 のコメント |
| 依頼を変形してよい理由 | あり | そのまま | 対話 |
| 捨てた代替案 | すべて書く | 実際に検討したものだけ | 後付けの列挙を避ける |
| 範囲外の選択肢 | なし | 環境の境界として書く | 対話（聞きすぎを是としない） |
| 回避策の条件 | あり | 具体例付き | answers-under-constraints の書かれ方 |
| 計測値の条件 | なし | 分かる範囲で、第 3 節に | 同上 |
| 途中の調整 | あり | 手順を変えたものだけ | 対話（完全なトレースは不要） |
| 記録だけから書く場合 | なし | そう言い、補わない | #135 の一回目の却下 |
| docs/sketch との分担 | なし | 手順は sketch、経緯は記事 | #133 のコメント |
| write-slops の写し | あり | 削除、先に読ませる | 追従漏れを避ける |

この記事はそのスキルの順で書いた。題材がスキル作りなので、第 2 節の「捨てた道と理由」は、権限やバージョンではなく、直近の記事と対話に書かれていたことになっている。技術調査の題材で使えるかは、まだ分からない。

## 余談

- 直近の技術調査は [PR #136](https://github.com/podhmo/html-sandbox/pull/136)（WSL2 の perf の bind mount で `apt upgrade` が失敗した件）だが、Devin のセッションで行われ、記事はない。このセッションには捨てた選択肢の材料がないので、新しい規則に従えば「記録だけから書いている」と断ったうえで sketch をなぞる以上のことは書けない。次に Claude Code で技術調査をしたときに、そのセッションで使うのが順当だと思う。
- 書く段階のスキルでは、捨てた選択肢の材料が残っていることまでは保証できない。調査が長く、会話が要約されると消えやすいはず（確かめていない）。調査の依頼の側で「捨てた選択肢を sketch に一行ずつ残す」と頼めば残るが、作業を縛る側の指定になる。
- write-slops との書き比べはしていない。[fork で書き比べた記事](../2026-11-05-skill-for-new-articles.md)と同じく、調査したセッションから fork を 2 つ起こせば、違いをスキルだけにできる。
- issue #133 にある、いろいろなモデルに書かせて筆致の差を楽しみたい、という話とは、トーンの形容を入れていないことが合っている気がする。スキルが文体を決めなければ、差はモデルの側から出る。
