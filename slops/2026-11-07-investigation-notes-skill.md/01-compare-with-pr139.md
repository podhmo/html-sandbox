# Claude Code から: PR #139 との比較と総評

この節は、README のスキルと記事を書いた Claude Code が、あとから依頼されて書き足したもの。同じ依頼（issue #133 のコメントを踏まえて write-slops の特殊化スキルを作り、それで記事を書く）を Codex が別に実行した [PR #139](https://github.com/podhmo/html-sandbox/pull/139) を読み、こちらの [PR #138](https://github.com/podhmo/html-sandbox/pull/138) と並べた。読んだのは PR #139 のブランチ `codex/exploration-slops` の 2 コミット（dda0d00、a2208c7）で、スキル、記事、`AGENTS.md`、`03-svg-pitfalls.md` への追記、図の生成スクリプト。Codex 側を動かしたり書き直させたりはしていない。

前提に一つ差がある。こちらは途中で、下書きの元になった対話の全文を見せてもらい、それを受けて二回目の調整をした。Codex 側の記事は、Drive と AI Studio のリンクは開かず、コメントの文面とリポジトリの記録だけで書いたと述べている。なので、対話に由来する項目の差は書き手の差ではなく、材料の差として読む必要がある。

## スキルの比較

### 共通しているところ

骨組みはほぼ同じだった。write-slops を先に読ませて写しを持たないこと、依頼を書き直してよいこと、出来事の順を骨にして因果の散文で書き、年表やコミットログにしないこと、最初の依頼への答えで締めて反省で代えないこと、余談は答えのあとに置くこと、回避策をその条件と並べて書くこと、エージェント一般の話や書き手の鋭さの披露にしないこと。どれも下書きにあった項目なので、ここが揃うのは当然とも言える。

もう一つ、こちらが対話を読んで二回目にようやく入れた「候補を並べて網羅的に見せない」「記録にない理由を作らない」を、Codex は対話なしで最初から書いていた。こちらの一回目は「For every dropped path」で、ちょうどその逆だった。

### PR #139 のほうが良いところ

- 代替案を三つに分けている。試して失敗したもの、検討したが実行しなかったもの、あとから気づいた可能性。こちらは「実際に検討したものだけ」と書いて、あとから気づいたものの置き場を余談に任せた。三分類のほうが捨てずに区別できるし、Codex の記事自身もこの区別で TTS の件を説明できていた。
- 回避策について「その道を見直してよい条件の変化」まで書かせている。TTS の件ならドライバの更新がそれにあたり、追試の記事（answers-under-constraints）が後から見つけたことを、最初の記録の時点で書かせる指示になっている。
- 「環境に依存する選択を、既定で暫定扱いにしない」「最初に動いた解を最良と見なさない」。こちらの「条件付きで書く」は、逆にすべてを仮のものとして書かせる方向に振れうる。
- まとめた依頼の中で「後から加わった条件を、最初から分かっていたように書かない」。依頼を書き直してよいと許すなら必要になる歯止めで、こちらにはない。
- `AGENTS.md` から案内している。こちらは description だけで、AGENTS.md は今も write-slops だけを指しているので、Codex など他のエージェントがこのスキルに辿り着く経路が弱い。
- write-slops の「図を積極的に試す」「新しい失敗は 03-svg-pitfalls.md に記録する」に従っている。こちらは図を作らず、作らなかった理由も書いていない。

### PR #138 のほうが良いところ

- 短く、必須の項目が少ない。依頼した人は対話の中で「不要なものを必須にして作業を縛りたくない」と言っていた。#139 は、書く前に材料を取り戻す手順、渡す前の確認、「新しい実験や外部への公開を許可するものではない」といった但し書きまで入っていて、指示としては丁寧だが、そのぶん従う項目が多い。
- 範囲外の選択肢を「人間に頼むべきだった」として書かない、を記事の書き方として決めている。#139 にも近い文はあるが、「自律作業中にすべての分岐を人間に確かめる必要はない」という作業中の話として書かれていて、記事の中でどう書くかまでは決めていない。
- `docs/sketch/` との分担（手順と事実は sketch、どう辿り着いたかは記事）がある。このリポジトリの技術調査はたいてい sketch を残すので、記事が sketch の写しになるのを防ぐ項目は効くと思う。
- ペダンティックの禁止の理由（investigation という名前が呼ぶ語り口）を書いている。これは対話を見たから書けたことで、Codex は名前自体を変えている。

## 記事の比較

Codex の記事は英語で、主語は一人称、出来事を「〜したので〜にした」とつなぐ形は守られている。ただ後半（What this attempt produced）は、validator が PyYAML の不足で止まった件、`GOCACHE` を指定した `make test-go`、ブラウザでの確認、何を確かめていないか、と PR の説明に近い。「This establishes … It does not establish …」のような限定がくり返されて、慎重ではあるが、issue #133 の言う「記録と解釈」の解釈のほうは薄い。表で TTS の記録とスキルの項目を対応させた節は、題材がスキル作りでも技術調査の例を一つ通して見せていて、こちらの記事にはない良さだった。

こちらの記事は日本語の日記に近い調子で、一回目と二回目の直しが転換点として残っている。読み手には、なぜその項目がそうなったかが追いやすいと思う。一方で、TTS の具体例は対応表の一行に縮み、スキルを実際の調査に当てるとどう書けるかは見せていない。図もない。

両方とも、題材が技術調査ではなくスキル作りなので、本来の使い道で試していないことを認めている。

## 総評

スキルの中身では、代替案と条件の扱いは #139 のほうが細かく、見落としが少ない。依頼した人の意図への合わせ方では、対話を見た #138 のほうが近い。ただしこれは材料の差によるところが大きい。リポジトリへの組み込み（AGENTS.md、図と落とし穴の記録）は #139 のほうが丁寧だった。

一本にまとめるなら、#138 の短さと記事の書き方の項目（範囲外の選択肢の扱い、sketch との分担、依頼を書き直してよい理由）を土台にして、#139 から次の四つを取り込むのがよいと思う。代替案の三分類、見直してよい条件の変化、既定で暫定扱いにしないこと、後から加わった条件を最初からのように書かないこと。それに `AGENTS.md` からの案内。名前はどちらでもよいが、対話で選ばれたのは investigation-notes だった。

どちらのスキルが良い記事を生むかは、この比較では分からない。2 本の記事は題材も言語も違い、スキル以外の差が大きすぎる。比べるなら、次の技術調査のセッションから fork を 2 つ起こして、同じ材料で両方のスキルに書かせるのが筋だと思う。
