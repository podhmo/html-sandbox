## 前の記事までで分かっていた要求

出発点は [issue #133](https://github.com/podhmo/html-sandbox/issues/133) で、[答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md)の論じる文体が鼻につく、という指摘だった。依頼した人が挙げた好みは次のとおり。

- 視点の鋭さをアピールしない。テーマを決めてディベートのように主張しない。
- 個人の日記のようなスタイル（くだけた物言いではない）。起きたことの記録と解釈はあってほしい。
- 実施したことを淡々と並べるだけではつまらない。
- いろいろなモデルに書かせて筆致の差を楽しみたい。「自由に書け」のような指示が命令として働くのは避けたい。

11-05 に続けて書かれた slops のうち、[記事を書くスキルを考えて、fork で書き比べた](2026-11-05-skill-for-new-articles.md)が、問題をもう一段はっきりさせていた。機能紹介の頃は diff をなぞれば話の筋になったが、実験や追試のように語る対象が複雑になると、何を語るかを書き手が選ばなければならず、選べないときに性質の一覧や論じる形で埋めていた。そこから出た良い記事の形は、本筋（頼まれたこと、したこと、起きたこと）があり、却下や外れた推測は本筋の中に起きた順に置き、外れたことは余談として短く残し、最後に最初の問いへの答えをまとめる、というもの。自分の間違いの振り返りで締めない。スキルの違いを比べるなら、作業したセッションから fork したサブエージェントに書かせる、という方法もここで出ている。

ただ、これは用途を問わない一般解として書かれていた。11-06 のコメントで、依頼した人は一つの体裁として「技術的な備忘録」を用途に置いてみる、と提案した。用途を絞れば、何を語るかの選び方を具体的に書ける。コメントには、技術調査の記事で起きていた課題四つと、`write-slops-investigation-notes` という名前の SKILL.md の下書きが載っていた。

- 個別の事実ではなく、エージェントの一般的な性質のような主張に脱線する。
- その環境でだけ必要だった回避策が、恒久的な規則として残る。
- 自律的に動く状態にしたとき、どの代替案をなぜ捨てたかが残らず、追試しにくい。
- 書き方を直そうとすると、今度は自分のミスの振り返りに終始し、調査の答えが抜ける。

依頼した人が必要としているのは「人間に聞くべきだった」という反省ではなく、どういう選択肢をどういう制約で捨てたか。作業は自律的に進めてよく、あとで読む記事でそれが見えればよい。

## 特殊解としてのスキルに必要だった要素

三つの試作は、下書きと、そのあとに渡された下書きの元の対話を受けて作られた。三者の記事と比較を通して見ると、技術調査の記事のスキルに要る要素は次のものだった。

### 記事の骨組み

- 依頼と前提、試行と判断の経過、最初の問いへの答え、余談、の順。11-05 の良い記事の形を、技術調査に当てはめたもの。
- 経過は年表やコマンドの一覧ではなく、「X で失敗したので Y を試した」とつながる散文。
- 結びは最初の問いへの答え。数値を出すなら分かっている条件を添える。答えられていない部分があればそれを書く。反省で締めない。

### 残すもの

- 捨てた代替案と、その具体的な理由（権限、バージョン、範囲、計測）。
- 回避策は、それが必要になった条件と一緒に書く（「ドライバ 573.22 が既定のビルドを受け付けなかったので cu128 に固定した」）。無条件の規則にしない。
- 途中で依頼が変わり、それでその後の作業や結果の判断が変わったなら、その時点で書く。

### 書かないもの

- 検討していない候補を後から並べて、記録を網羅的に見せること。書く段階で読まれるスキルが「代替案を書け」と言うと、作業中に検討していない候補で節を埋めることが起こりうる。
- 範囲外の選択肢を「人間に頼むべきだった」こととして書くこと。それはバージョンと同じ環境の境界として書く。確認を挟まずに進めたこと自体を欠点として説明しない。
- ペダンティックな分析や鋭さを見せること。名前に investigation を選ぶときに、学者ぶった語り口を呼ぶのではという懸念が依頼した人から出ていて、その手当て。
- 文体の形容（下書きにあった matter-of-fact など）。文体を指定すると、それに応えるための文が入る。モデルごとの筆致の差を残したいという #133 の希望にも合う。

### 周辺との関係

- 依頼文は逐語で引かず、書き直してよい。記事を「依頼とその確認結果」の形にするためと、途中の転換を経緯に書くなら冒頭に全文を置くと重なるため。
- 再現手順が `docs/sketch/` にあるなら、手順は sketch、そこへ辿り着いた経緯は記事。
- 記法、図、ファイル配置は base の write-slops に任せ、写しを持たない。写すと base の変更（`*` 強調の禁止など）に追従が漏れる。

## 三つの試作の比較

三つとも、下書きの 4 節の並び、因果の散文、反省で締めないこと、回避策を条件付きで書くことは守っていた。差が出たのは、元の対話を受けた調整で何を読み取ったかだった。

| 要素 | `--claude`（82 行） | `--gpt`（89 行） | `--gemini`（38 行） |
| --- | --- | --- | --- |
| 残す代替案 | 実際に検討して進路を変えたもの | 結果の条件・限界・再現に関係するもの。失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分ける | 退けられるたびに、環境の制約を書く |
| 後付けの候補への歯止め | あり | あり（理由が記録になければ不明と書く） | なし |
| 途中の変更 | 次の手順を変えたもの | 手順か、結果の評価を変えたもの。後から加わった条件を最初からあったように書かない | 転換点として書く |
| 回避策 | 条件付き | 条件付き。既定で暫定扱いにしない | 条件付き |
| ペダンティックの禁止 | 理由ごと残す | 一般論や鋭さの披露をしない、として残す | 外し、「意図と環境の摩擦に焦点を当てる」に置き換え |
| 依頼を書き直してよい理由 | 二つとも書く | 書かない | 外し、答えと対応させる形にまとめる |
| 余談 | 必須 | 任意 | 必須 |
| docs/sketch との分担 | あり | なし | なし |

比べて分かったことは三つ。

一つは、代替案を残す基準は `--gpt` がよいこと。TTS の追試の件で、ホスト側のドライバ更新は範囲外としてすぐに外れ、作業の進路は変えていない。それでも追試の記事はまさにその案から始まっていた。「進路を変えたもの」ではこの案が落ち、「条件・限界・再現に関係するもの」なら残る。

二つめは、`--gemini` の「退けられるたびに」が網羅を求める読み方をされうること。理由を環境の制約に限っているので、範囲外、時間、計測による見送りの置き場もない。短さは、依頼した人の「不要なものを必須にして作業を縛りたくない」に合っていた。

三つめは、条項を全部足すと、三者がそれぞれの調整で減らそうとした義務がまた増えること。Codex の比較がこれを指摘し、Claude Code の比較も、`--gpt` にある「渡す前の確認」のような作業手順の項目は入れないほうがよい、と書いていた。

ペダンティックの禁止は、同じ対話から逆の結論が出た。`--claude` は名前の副作用への手当てと読んで残し、`--gemini` は文体の否定命令がモデルごとの語り口の差を損なうとして外した。どちらを取るかは依頼した人が決めることとして残された。

## 一本にまとめたときの狙い

まとめたスキルは [.agents/skills/write-slops-investigation-note/SKILL.md](../.agents/skills/write-slops-investigation-note/SKILL.md)。狙いは、`--claude` の短さと記事の側の決まり（範囲外の選択肢の書き方、sketch との分担、依頼を書き直してよい理由）を土台にして、`--gpt` からは代替案の扱いと途中の変更の扱いだけを取り込み、義務は増やさないことだった。

| 項目 | `--claude` | まとめたスキル | 出どころ |
| --- | --- | --- | --- |
| 残す代替案 | 進路を変えたもの | それに加えて、結果の条件・限界・再現を説明するもの | `--gpt`、元の対話 |
| 代替案の区別 | なし | 失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分ける | `--gpt` |
| 記録にない理由 | 補わない | 補わず、不明と書く | `--gpt` |
| 回避策 | 条件付き | 条件付きで、既定では暫定扱いにしない | `--gpt` |
| 途中の変更 | 次にしたことを変えたもの | 結果の判断を変えたものも。後から加わった条件を最初からあったように書かない | `--gpt` |
| 余談 | 必須 | 任意。置くなら答えのあと | `--gpt`、元の対話 |
| ペダンティックの禁止 | あり | あり | 依頼した人の判断 |

取り込まなかったものと、その理由。

- `--gpt` の作業手順や確認の項目（表で条件を比べてよい、関係のない条件は書かない、一度の成功を互換性の保証にしない、部分的な結果も答えになる、余談にしか答えがない状態にしない）。一度は入れたが、上の「義務がまた増える」に当たるので外した。部分的な結果の文は `--claude` の「答えられていない部分があれば書く」とほぼ重なっていた。
- `--gemini` の「意図と環境の摩擦に焦点を当てる」。入口として分かりやすいという評価もあったが、ペダンティックの禁止を外した代わりに置かれた文で、禁止を残すなら役割が重なる。依頼した人に確認して、入れないことになった。
- `AGENTS.md` からの案内。技術的な備忘録を書かせたいときは依頼した人がスキルを名前で指定するので、自動で選ばせる案内は要らない。`AGENTS.md` には、用途ごとの派生スキル（`write-slops-*`）があり名前で指定されたときだけ使う、という一文だけを置いた。

余談は、元の対話で「結びのあとに別の章として置くほうがうれしいかも」と言われていた。必須にした `--claude` と `--gemini` はこれを節の要求と読み、任意にした `--gpt` は置き場所の好みと読んだことになる。「不要なものを必須にしない」に合わせて任意にした。

試作三つは `write-slops-investigation-note--claude`、`--gpt`、`--gemini` として本文を当時のまま残し、description を「比較の記録として残した試作。名前で指定されたときだけ使う」に変えた。スキル一覧に同じ用途のものが四つ並んでも、既定で選ばれるのはまとめたスキルになる。実体は `.agents/skills/` に置き、`.claude/skills` はそこへのシンボリックリンクにしている。

まとめたスキルが、実際の技術調査のあとで `--claude` より必要な代替案を残せるかは、まだ試していない。三つの試作も、題材はどれもスキル作りだった。

## 余談: 元の記事にあったこと

- Codex は、リンク構造の図を svg-gen の検査に通し、原寸の PNG でも読めることを確かめたが、ブログの狭い画面では縮小でラベルが読めなくなった。縦向きの小さな配置に直し、[SVG の落とし穴](2026-10-27-writing-slops.md/03-svg-pitfalls.md)に記録している。座標の検査を通ることは、縮小後に読めることを保証しない。
- Codex は、スキルを他のエージェントから見せる方法として、グローバルへのインストール（そのマシンだけの設定になる）、コピー（編集対象が増える）、リポジトリ内の相対シンボリックリンク（チェックアウトと一緒に持ち運べ、base への相対参照も保てる）を比べて、最後を選んだ。この形はのちに、実体を `.agents/skills/` に置いて `.claude/skills` をリンクにする構成（`cadb3df`）になった。
- Gemini は、`.agents/skills` 自体を `.claude/skills` へのリンクにする案と、スキルごとにリンクを置く案を比べて後者を選び、単数形の `.agent` へのリンクも足した。svg-gen にラベルを `\n` 入りの文字列で渡すと幅の計算が崩れ、`labelLines` の配列で渡すと通った。
- Codex のスキル検査は、システムの Python に PyYAML がなかったので、その依存だけを入れた uv の環境で走らせている。
- Codex は、回避策について「条件付き」と「暫定」を分けた。ある環境に依存していても、その条件では最終解でありうる。必要なのは選んだ観測と適用条件で、すべてを暫定解と呼ぶことではない。
- Claude Code は、書く段階で読まれるスキルでは、作業中に代替案が記録されたことまでは保証できない、と書いていた。調査の依頼の側で「捨てた選択肢を sketch に一行ずつ残す」と頼めば残るが、作業を縛る側の指定になる。
- 三つの記事は、#133 で依頼した人が楽しみたいと言っていた筆致の差がはっきり出た。Claude Code は何をなぜ直したかを順に書く日記に近く、Codex は確かめた範囲と確かめていない範囲を何度も区切る PR の説明に近く、Gemini はスキルの 4 節を番号付きの見出しにそのまま写し、「真に必要としているのは」「こそが」のような言い切りが多かった。Gemini の記事には、write-slops が避けるよう書いている番号付きリストと、文を箱にして並べた図もあった。
- 同じ下書きから Devin が作ったスキルの [PR #137](https://github.com/podhmo/html-sandbox/pull/137) が開いたまま残っている。トーンの指定を外し、write-slops の写しを持たず、sketch へのリンクを足した点は、`--claude` の最初の版と近い。
- 比べるなら、11-05 の記事と三つの記事がそろって書いていたとおり、次に技術調査をしたセッションから fork を起こし、まとめたスキルと `--claude` で同じ材料から書かせるのがよさそうだ。図に置いたドライバ更新のような案が残るかどうかを見ることになる。
