## きっかけ: 論じる文体と、技術的な備忘録という用途

[issue #133](https://github.com/podhmo/html-sandbox/issues/133) は、[答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md)を読んで、論じる文体が鼻についてきた、というところから始まっている。slops はどれも write-slops で書いているので、その指定がこういう表現を生んでいる可能性もある。依頼した人が挙げた好みは、視点の鋭さをアピールしない、テーマを決めてディベートのように何かを主張しない、個人の日記のような（くだけた物言いではない）スタイル、起きたことの記録と解釈はあってほしい、実施したことを淡々と並べるだけではつまらない、というものだった。いろいろなモデルに書かせて筆致の差を楽しみたいので、「自由に書け」という指示が命令として働くのも避けたい、とも書いている。

同じ 11-05 には、この問題を扱った slops が続けて書かれている。[記事を書く目的で分けて、依頼をテンプレートにする](2026-11-05-slops-use-case-templates.md)、[依頼した人にとって良い slops とは](2026-11-05-good-slops-for-requester.md)、[記事を書くスキルを考えて、fork で書き比べた](2026-11-05-skill-for-new-articles.md) などで、あとの三者はどれもこれらを材料として読んでいる。

11-06 のコメントで、依頼した人は一つの体裁として「技術的な備忘録」を用途に置いてみる、と提案した。コメントには、別の場で AI と対話して整理した Q&A と、`write-slops-investigation-notes` という名前の SKILL.md の下書きが載っている。Q&A が挙げていた課題は四つ。

- エージェントが視点の鋭さを見せようとして、個別の事実ではなく一般論や立論に脱線する。
- その環境でだけ必要だった回避策が、恒久的な規則として残る。
- 自律的に動く状態にしたとき、どの代替案をなぜ捨てたかが残らず、追試しにくい。
- 書き方を直そうとすると、今度は自分のミスの振り返りに終始し、調査の答えが抜ける。

依頼した人が必要としているのは「人間に聞くべきだった」という反省ではなく、どういう選択肢をどういう制約で捨てたか。下書きはそれを、依頼と前提、試行と判断の経過（年表ではなく因果の散文）、最初の問いへの答え、余談、の 4 節にしていた。名前は、`tech-notes` は解説記事に、`trial-log` は奮闘記に傾くとして `investigation-notes` を選び、ペダンティックにならないよう歯止めを置いている。

## 依頼と、始めた時点の条件

依頼は、この 11-06 のコメントを踏まえて、技術的な調査（環境構築、実現性の確認、追試、デバッグ）のあとに slops を書くための特殊化スキルを write-slops の上に作り、そのスキルで作成の経緯を記事にすること。同じ依頼を三つのエージェントに別々に出し、それぞれの成果を比べたあと、一本のスキルにまとめた。この記事が答えるのは、そのスキルがどういう形になり、各部分がどこから来たか。

始めた時点の条件は三者で共通していた。

- 下書きの元になった対話は Google Drive と AI Studio にあり、認証が要るので、どのエージェントも最初は開けていない。対話はあとで依頼した人が貼った。
- 各エージェントは専用の worktree で作業し、別のエージェントの PR は参照しない。比べたのは、あとで比較を頼まれてから。
- 材料は、issue のコメント、11-05 の slops、base の write-slops。

## 下書きから、三者がそれぞれ作った最初の版

三者とも 4 節の並びは変えず、年表にしない因果の散文、回避策を条件付きで書くこと、反省で締めないことは下書きから引き継いだ。違いが出たのは、下書きのどこを削り、どこに何を足したかだった。

Claude Code は、下書き冒頭の「Keep the tone matter-of-fact」を削った。[目的別テンプレートの記事](2026-11-05-slops-use-case-templates.md)で、文体の条件に応えるために観察ではない文が入っていたことが報告されていて、トーンの指定は同じことを起こすと考えたため。下書き末尾の write-slops の要約も、[PR #132](https://github.com/podhmo/html-sandbox/pull/132) の `*` 禁止のような変更に追従が漏れるとして削った。足したのは、手順は `docs/sketch/`、経緯は記事という分担、計測値に条件を添えること、作業したセッションで書くという前提、余談に確認済みかを付けること。

Codex は、名前を `write-slops-exploration-notes` に変えた。開始時のチェックアウトに investigation-notes というスキルがすでに見えていたためで、これは Claude Code が一度 main に直接コミットしてから PR のブランチへ移した間のものだった（あとで依頼した人が確認している）。write-slops の写しを持たない点は Claude Code と同じ。他のエージェントから使えるように `.agents/skills/` に base と派生への相対シンボリックリンクを置き、`AGENTS.md` に案内を足した。グローバルへのインストールはそのマシンだけの設定になり、コピーは編集対象が増えるので、リポジトリ内の相対リンクを選んでいる。スキルの形式検査は、システムの Python に PyYAML がなかったので、その依存だけを入れた uv 環境で通した。リンクの構造図は、検査を通り原寸の PNG でも読めたが、ブログの狭い画面では縮小でラベルが読めなくなり、縦向きの小さな配置に直した。この件は [SVG の落とし穴](2026-10-27-writing-slops.md/03-svg-pitfalls.md)に記録されている。

Gemini は、下書きにいちばん近い 38 行のスキルを作り、名前もパスも下書きのままにした。agy がスキルを `.agents/skills/` から探すので、`.agents/skills` 自体を `.claude/skills` へのリンクにする案と、スキルごとにリンクを置く案を比べ、ツールによってディレクトリリンクの走査が異なるかもしれないとして後者にした（試して確かめた記録はない）。単数形の `.agent` へのリンクも足している。図を svg-gen で作るときに、ラベルに `\n` 入りの文字列を渡して幅の計算が崩れ、`labelLines` の配列に直した。

## 元の対話を受けて、三者がそれぞれ調整した

最初の版のあと、依頼した人が下書きを作った対話の全文を三者に渡した。三者とも対話を受けてスキルを直したが、読み取ったものは揃わなかった。

対話で依頼した人が求めていたのは、記事を読むと「どういう選択肢を捨てたのか」が分かることで、「なぜホスト側のドライバ更新を人間に頼まなかったのか」ではない。後者を是とすると人間に聞きすぎる逆の失敗が起きる。調査を自律的に進めること自体は悪くなく、完全なトレースも要らず、知見と手順を再現できればよい。もう一つ、「不要なものを必須にして作業を縛りたくない」という線引きがあった。

Claude Code は、一回目で削ったものの二つが理由を知らずに削ったものだったと分かった。matter-of-fact は、名前に investigation を選ぶときに学者ぶった論述を呼ぶのではという依頼した人の懸念への手当てだった。そこで、ペダンティックな分析や鋭さを見せることの禁止を、investigation は題材の話で語り口の話ではない、という理由と一緒に戻した。依頼を書き直してよい理由の二点（記事を依頼とその確認結果の形にするため、途中の転換を経緯に書くなら全文を冒頭に置くと読みにくいため）も戻した。逆に、一回目で足した計測値の細目、余談の確認済みラベル、作業したセッションで書くという前提は、必須にしすぎとして外したり弱めたりした。最後のものは「記録だけから書くならそう言い、記録にない理由を補わない」に置き換えた。代替案は「実際に検討して進路を変えたもの」に絞った。スキルは書く段階で読み込まれるので、起こりうるのは作業中のメモが増えることではなく、代替案の節を埋めるために後から候補を並べることだと考えたため。

Codex は、代替案を残す基準を「結果の成立条件・限界・再現を理解するのに必要なもの」にし、失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分けさせた。理由が記録になければ不明と書く。依頼は途中の調整も含めて冒頭で書き直してよいが、後から加わった条件を最初から分かっていたようには書かない。途中の変更は、次の手順を変えたものだけでなく結果の評価のしかたを変えたものも残す。回避策は条件付きで書くが、既定で暫定扱いにはしない。余談は任意にした。記事はこの時点では対話前の初稿のままで、あとで依頼されて書き直している。

Gemini は、ペダンティックの禁止を外した。文体の否定命令を重ねるとモデルごとの語り口の多様性を損なう、という理由で、代わりに「意図と環境の具体的な摩擦に焦点を当てる」を冒頭に置いた。捨てた代替案を思い出す手がかりとして、コマンドの失敗、root がない、ドライバの不一致、パッケージの大きさを例に挙げた。依頼を書き直してよい理由の二点は外し、第 3 節で答えるべき問いと成果物に再構成する、とまとめた。

調整後の三つは次のように並ぶ。行数は調整後。

| | Claude Code（82 行） | Codex（89 行） | Gemini（38 行） |
| --- | --- | --- | --- |
| ペダンティックの禁止 | 理由ごと戻した | 一般論や鋭さの披露をしない、として残す | 外した |
| 依頼を書き直してよい理由 | 二つとも書く | 書かず、後から加わった条件の扱いを足す | 外し、答えと対応させる形にまとめる |
| 残す代替案 | 実際に検討して進路を変えたもの | 結果の条件・限界・再現に関係するもの。三分類 | 退けられるたびに、環境の制約を書く |

| 途中の変更 | 次の手順を変えたもの | 手順か、結果の評価を変えたもの | 転換点として書く |

## 互いの成果を比べた

そのあと依頼した人は、Claude Code に #139 と #140 との比較と総評を、Codex に #138 と #140 との一対一の比較を頼んだ。Gemini が書いた比較は記録にない。比較はどれも書いたエージェント自身の評価で、条件をそろえた品質比較ではないと各記事が断っている。

Claude Code の最初の比較には誤った前提が二つあった。対話を見たのは自分だけだと思っていたことと、Codex に investigation-notes が見えていた理由を自分の作業ツリーの事情と推測していたこと。依頼した人の指摘で、両方とも対話を見ていた前提に書き直している。

比較から出た判断のうち、のちの統合に効いたものは次のとおり。

- 代替案の基準は Codex 版がよい。Codex の比較が指摘し、Claude Code も認めた。TTS の件のドライバ更新は、範囲外としてすぐに外れて進路は変えていないが、追試の記事はまさにその案から始まった。Claude 版の基準では落ち、Codex 版の基準では残る。
- Gemini 版の「たびに」は網羅を求める読み方ができ、後から候補を並べることへの歯止めがない。理由を環境の制約に限っているので、範囲外や時間、計測による見送りの置き場もない。両方の比較が同じ点を挙げた。
- 図があることはスキルの良し悪しの証拠ではない。Codex が自分の図について書き、Claude Code が自分の最初の比較を訂正した。
- Gemini の記事については、番号付きリストと文を箱にして並べた図（どちらも write-slops が避けるよう書いている）、agy での読み込みを確かめていないのに確かめたように書いたこと、参照しない PR を #128・#129 と書いた（並行していたのは #138・#139）ことが指摘された。これは記事の書き方の問題で、スキルの文面の話ではない。
- 条項を全部足すと、両方の調整で減らそうとした義務がまた増える（Codex）。GPT 版の「渡す前の確認」のような作業手順の項目は入れないほうがよい（Claude Code）。

#138 と #140 は同じパスにスキルを置いていたので、そのままでは両方マージできなかった。三つは `write-slops-investigation-note--claude`、`--gpt`、`--gemini` に改名してそれぞれマージされ（`3b86665`、`e27ae4d`、`7f71377`）、そのあとスキルの実体を `.agents/skills/` に移し、`.claude/skills` をそこへのシンボリックリンクにした（`cadb3df`）。

## 三つを一本にした

統合の依頼は、直近の slops と `.agents/skills` を読み、`--claude` をベースにして `write-slops-investigation-note` を作ること。途中で、判断を仰ぎたいところは質問で聞くこと、今日の記事を全部読んでから判断すること、の二つが加わった。

最初の版は、Claude Code の総評（`03-overall.md`）の推奨に沿って作った。Claude 版を土台に、GPT 版から代替案の基準と三分類、後から加わった条件の扱い、評価のしかたを変えた変更、既定で暫定扱いにしないこと、余談を任意にすること、`AGENTS.md` からの案内を取り込む。このとき、推奨に入っていない GPT 版の文も五つ一緒に持ち込んでいた（表で条件を比べてよい、関係のない条件は書かない、一度の成功を互換性の保証にしない、部分的・否定的な結果も答えになる、余談にしか答えがない状態にしない）。

総評が依頼した人に預けていた二点は質問した。ペダンティックの禁止は「残す」。試作三つは「残して description を変える」で、description が同じだとスキル一覧に調査記事用が四つ並んでどれが選ばれるか曖昧になるため、試作のほうを「比較の記録として残した試作。名前で指定されたときだけ使う」にした。ここでいったんコミットした。

コミットのあとで、今日の記事を全部読むよう言われ、比較の 01・02 と Codex、Gemini の記事を読んだ。上に挙げた「条項を全部足すと義務が増える」「作業手順の項目は入れない」という二つの指摘に、持ち込んだ五つの文がそのままあたっていたので外した。部分的な結果の文は Claude 版の「答えられていない部分があればどこかを書く」とほぼ重なり、互換性の文は暫定扱いにしないことの言い足しだったので、外して失うものは少ないと判断した。Gemini 版の「意図と環境の摩擦」の一文は、Codex の比較は入口として分かりやすいと評価していたが、ペダンティックの禁止を外した代わりに置かれたもので、禁止を残す統合版では役割が重なる。入れない案を推して質問し、答えは「入れない」だった。

統合版で記事を書き始めたところで、依頼した人が元の対話をもう一度貼り、統合版と突き合わせた。いちばん効いたのは代替案の基準で、統合版は二つの基準を「または」でつないでいるので、ドライバ更新の案は残る。

余談の扱いは迷った。対話では、余談は結びのあとに別の章として置くほうが「うれしいかも」と言っている。必須にした Claude 版と Gemini 版はこれを節の存在の要求と読み、任意にした GPT 版は置き場所の好みと読んだことになる。同じ対話の「不要なものを必須にして縛りたくない」に合わせて、統合版は任意のまま、置くなら結びのあと、とした。

記事を書き終えたあと、依頼した人から `AGENTS.md` の案内はそもそも要らないと言われた。技術的な備忘録を書かせたいときは、依頼した人がスキルを直接指定するから。総評の推奨で足した案内と試作へのリンクを外し、`AGENTS.md` には、用途ごとの派生スキル（`write-slops-*`）があり名前で指定されたときだけ使う、という一文だけを残した。途中のコミットは一つにまとめて `96f82be` として main に入っている。

その後、依頼した人は、三つのエージェントが書いた記事は本来なら候補として PR のコミットの中にだけ残るものだったと判断し、経緯ごとこの記事にまとめることにした。三本を削除するコミットを [PR #143](https://github.com/podhmo/html-sandbox/pull/143) に置き、差分で本文を読めるようにして、この記事はそこへリンクしている。三本を指していたリンクは、前の記事の `next` をこの記事に、SVG の落とし穴の記録からのリンクを `96f82be` の固定パスに付け替えた。三本でしか使っていなかった svg-gen の生成元（`fig-exploration-skill-links.ts`、`fig-investigation-notes-flow.ts`）も消した。まとめるにあたって、この記事は統合の記録ではなくスキルを作った記事として扱うことにし、題名とファイル名（もとは `2026-11-07-merge-investigation-note-skill.md`）を変えて、issue #133 のきっかけから書き直した。

## できたもの

スキルは [.agents/skills/write-slops-investigation-note/SKILL.md](../.agents/skills/write-slops-investigation-note/SKILL.md) にあり、`.claude/skills` は `.agents/skills` へのシンボリックリンクなので Claude Code からも同じものが見える。試作三つは `--claude`、`--gpt`、`--gemini` として本文を当時のまま残し、description だけを「名前で指定されたときだけ使う」に変えた。Claude 版からの差分は次のとおり。

| 項目 | Claude 版 | 統合版 | 出どころ |
| --- | --- | --- | --- |
| 残す代替案 | 実際に検討して進路を変えたもの | それに加えて、結果の条件・限界・再現を説明するもの | GPT 版、元の対話 |
| 代替案の区別 | なし | 失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分ける | GPT 版 |
| 記録にない理由 | 補わない | 補わず、不明と書く | GPT 版 |
| 回避策 | 条件付きで書く | 条件付きで書き、既定では暫定扱いにしない | GPT 版 |
| 途中の変更 | 次にしたことを変えたもの | 結果の判断のしかたを変えたものも。後から加わった条件を最初からあったように書かない | GPT 版 |
| 余談 | 必須 | 任意 | GPT 版、元の対話 |
| ペダンティックの禁止 | あり | あり | 依頼した人の判断 |
| 案内 | description だけ | `AGENTS.md` は派生スキルがあることだけ書き、使うのは名前で指定されたとき | 依頼した人の判断 |

Gemini 版から文面として入ったものはない。

この記事は統合版の節の順で書いた。題材はスキル作りなので、捨てた道の理由は権限やバージョンではなく、記事の指摘と依頼した人の答えになっている。技術調査の題材で、統合版が Claude 版より必要な代替案をよく残すかは、まだ確かめていない。
