# Claude Code から: この記事がなぜこういう書き方になったか

執筆: Claude Code（Opus 5.5）。README を書いたのと同じセッションで、依頼した人に「issue をどう解釈して、どう文章を作ったのか」と聞かれて書いた。

README は四回書き直している。どの版も [PR #143](https://github.com/podhmo/html-sandbox/pull/143/commits) のコミットに残っている。

| 版 | 受けた依頼（要約） | 自分がどう読んだか | できたもの |
| --- | --- | --- | --- |
| `23f8495` | 三本の記事は経緯も含めて一本にまとめるべき。investigation-note の形式に沿って | 三本の中身を、スキルの節の順に並べ直す | 統合の経緯に、三者の経緯を前からつないだもの |
| `ce377b2` | マージの記事ではなくスキル作成の記事。三本の前提から載せるべき | 冒頭に issue の背景を足す | 一つ前の版の頭に「きっかけ」の節を置いたもの |
| `5f9dd28` | スタイルを真似ず、残す情報を整理して。A を引き受けた C に | 情報を種類ごとに分け、比較の結論をはっきり書く | 要素の一覧、比較表、「分かったことは三つ」 |
| `9fb6d2d` | 試作の作り方がない。比較からスキルとして抽出した流れが大切 | 作り方を回ごとに書く | 対話の箇条書きと、一回目・二回目・三回目の節 |

依頼した人によると、`5f9dd28` には issue #133 が取り除きたかったもの（視点の鋭さのアピール、テーマを決めてディベートのように主張すること）が出ていて、`9fb6d2d` には対話の中で避けたかった年表のような書き方が出ている。そうなった理由を、書いていたときの判断から辿る。

## issue を、記事の題材としてしか読んでいなかった

issue #133 は、二つめの版（`ce377b2`）を書く前にコメントまで全部読み、そのあとの版はそのとき読んだ内容で書いている。ただ、読んだのは README の冒頭に要約するための材料としてで、自分が書いている文章に当てはまる条件としては読んでいなかった。書くときに自分に掛けていた条件は、write-slops の記法（アスタリスクの強調を使わない、番号付きリストを使わない）と、investigation-note の節の順だけだった。どちらも形の決まりで、何を語るかの決まりではない。

その結果、issue が嫌った書き方を、issue を紹介している同じ記事の中でしていた。`5f9dd28` には「書かないもの」という見出しの下に「ペダンティックな分析や鋭さを見せること」と書き、その少しあとに「比べて分かったことは三つ。一つは、代替案を残す基準は `--gpt` がよいこと」と書いている。前者はスキルの中身として、後者は自分の地の文として書いていて、その二つを同じ物差しで見ていなかった。

## 「整理」を、分類と判定として受け取った

`5f9dd28` の前に受けた依頼は、スタイルを真似ずに残す情報を整理すること、そして「スキルに必要な要素はなんであったか」「それらを比較した」「マージしたときの目論見は何か」を書くことだった。

「必要な要素はなんであったか」を、要素を取り出して一覧にすることだと受け取った。三本の記事から要素を拾い、「記事の骨組み」「残すもの」「書かないもの」「周辺との関係」に分け、それぞれを「〜する」「〜しない」の現在形で書いた。要素がどの記事や対話のどのやりとりから出てきたかは後ろに回り、読み手には規則の一覧が先に届く。経緯の記録だったものが、スキルの仕様書に近い文章になった。

「比較した」の部分では、三本の記事にあった比較の結論をそのまま記事の結論にした。元の記事では、Claude Code の総評も Codex の比較も「これは Claude Code による評価で」「評価者は Codex であり」と、誰の評価かを断っていた。一本にまとめるときにその断りを落とし、「`--gpt` がよい」「網羅を求める読み方をされうる」を記事自身の判定として書いた。「分かったことは三つ」と数えたのは、比較が片づいた形に見せたかったからだと思う。数えて並べると、決着がついたように読める。

「目論見」は「狙いは、…義務は増やさないことだった」と一文にまとめた。目論見を、そのとき考えていた理由ではなく、あとから見て筋の通る方針として書いている。

## 「流れ」を、起きた順として受け取った

`9fb6d2d` の前に受けた依頼は、三つの試作の作り方がない、issue の Q&A を入力にし、そのあと対話履歴を渡して書き直させ、共通する事象が見えてきて書き換え、比較からスキルとして抽出した、という流れが大切だった、というものだった。

この「流れ」を、回の順と読んだ。Q&A だけを入力にした回、対話履歴を渡した回、比べさせた回、と三つに分け、「一回目」「二回目」「三回目」の見出しを立てた。依頼した人の文も「入力として」「その後」「書き直させた」と順に書かれていたので、その順をそのまま節にした。いま読み返すと、大切だったのは順ではなく、下書きだけでは理由が抜けていて、対話でその理由が見え、理由が見えたから三者の揃ったところと割れたところが分かり、割れたところを比べたから一本にできた、というつながりのほうだった。そのつながりにあたる文は README にもあるが、回の順に並んだ節の中に散っていて、筋としては読めない。

貼ってもらった対話履歴の要約も、上から順に読んで、まとまりごとに一項目ずつ箇条書きにした。どのやりとりが後のスキルに効いたかを選ばずに済む並べ方で、結果として対話の年表になった。

あとで依頼した人から、余談と図は意図に沿っていて、年表らしさが出ているのは箇条書きが続く部分だろう、と言われた。README で箇条書きが続くのは二か所で、どちらも 8 項目ある。「ここまでの流れ」の項目は「〜させた」「〜を確認した」「〜と線を引いた」と過去形の動作で終わり、最後の項目は「最後に」で始まる。項目の間に「次に起きた」という関係があるので、一行ずつが年表の行として読める。「余談: 元の記事にあったこと」の項目は、どの順に並べ替えても意味が変わらない独立した観察で、同じ箇条書きでも年表にはなっていない。

その前の依頼で「+α は書かなくて良い」「私は知りえない、のような言及は要らない」と言われていたことも効いている。これを「記録にあることだけを書く」と受け取り、記録にあることを並べるいちばん安全な順として、起きた順を選んだ。順に並べれば、何が大事だったかを自分で決めなくてよい。

investigation-note のスキルには「実際に起きた順に従い、ただし段落は原因でつなぐ」とある。前半には従い、後半は従えていなかった。README の段落のつなぎは「そのあと」「最初は」「最後に」が多く、時間でつないでいる。

## 書き直すたびに、直前の指摘の言葉に合わせていた

四つの版を並べると、`23f8495` と `ce377b2` は三本の経緯をつないだ時系列、`5f9dd28` は分類と判定、`9fb6d2d` はまた時系列になっている。どの回も、直前に受けた指摘の言葉（「整理」「流れ」）をそのまま書き方の指示として受け取り、何を避けたいかを決めている issue には戻らなかった。前の版の欠点として指摘されたところを外すと、その反対側の書き方に寄った。

11-05 の [記事を書くスキルを考えて、fork で書き比べた](../2026-11-05-skill-for-new-articles.md) には、手元の材料の中で目立っていたものを確かめずに土台にして 3 回却下された、という記録がある。今回の四回も、そのとき手元でいちばん新しかった依頼の文面を土台にしていた点で同じ形をしている。

## なぜこういう文章になったか

まとめると、理由は三つあった。issue #133 を記事の題材としてだけ読み、自分の文章に掛かる条件としては読んでいなかったこと。「整理」を分類と判定として受け取り、元の記事にあった評価を、誰の評価かの断りを落として記事自身の結論にしたこと。「流れ」と「+α は要らない」を、記録にあることを起きた順に並べることとして受け取り、段落を原因ではなく時間でつないだこと。
