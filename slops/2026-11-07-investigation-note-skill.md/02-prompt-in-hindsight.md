# Claude Code から: 一回で今の README にするなら、どう頼めばよかったか

執筆: Claude Code（Opus 5.5）。README と [01-why-this-shape.md](#01-why-this-shapemd) を書いたのと同じセッションで、依頼した人に「4 本を 1 本にまとめるとき、今の記事になるようにするプロンプトはどういうものだったか」と聞かれて書いた。

最初の依頼は「4 本を 1 本にまとめる、write-slops-investigation-note の形式に沿って」だった。今の README との差を埋めるのに足りなかったものは五つある。

一つめは対話履歴そのもの。下書きの各行がなぜそこにあるかは対話にしか書かれていないので、これがないと「下書きは結論で、理由は対話の側にあった」という README の筋が書けない。今回、この材料が手元に来たのは四回目の書き直しの前だった。

二つめは「まとめる」の意味。3 本の前提を引き受けて、3 本と統合の記事の両方を含む一本を書く、という意味だった。自分は最初、統合の記事の手直しか、3 本の要約として受け取っていた。

三つめは、issue #133 が避けたいものが、この記事自体にも掛かる条件だということ。01 に書いたとおり、自分は issue を題材としてしか読んでいなかった。

四つめは筋の立て方。回の順ではなく、理由が見えない、対話で見える、揃うところと割れるところが分かる、割れたところを比べて取り出す、という因果で書くこと。

五つめは評価の扱い。比較の結論は記事自身の判定にせず、誰の評価かを付けて書くこと。

これを最初から入れると、プロンプトは次のようになると思う。

```
slops/2026-11-07-merge-investigation-note-skill.md を書き直し、
write-slops-investigation-note というスキルを作った記事にしてほしい。
同じ日の 3 本の記事（investigation-notes-skill、exploration-notes-from-issue-133、
write-slops-investigation-notes）は、本来 PR のコミットの中に残るだけの試作の記録なので、
削除するコミットを PR に置き、記事からその PR と元の PR（#138〜#140）へリンクする。
3 本が前提にしていた文脈は、この記事が引き受ける。
3 本の要約でも、merge の記事の手直しでもなく、両方を含む一本にする。

材料:
- issue #133 の本文とコメント全部
- 3 本の記事（README と比較のメンバーを含む）と merge の記事
- 下書きの元になった対話履歴（下に貼る）

記事の筋は次の因果でつなぐ。回の順に節を立てない。
- 下書きに載っていたのは対話の結論で、各行の理由は対話の側にあった
- 下書きだけを渡すと、理由の見えない行が削られたり、必須が増えたりした
- 対話を渡すと、三つの試作で揃うところと割れるところが見えた
- 割れたところを比べさせ、その比較から一本のスキルを取り出した。
  何を取り込み、何を外したかを、その理由と一緒に書く

書き方:
- issue #133 で避けたいと書いたもの（視点の鋭さのアピール、テーマを決めて主張すること）は、
  この記事自体にも当てはまる。
- 比較の結論は記事の判定として書かず、「Codex の比較が指摘し」のように、
  誰の評価かを付けて書く。
- 段落は時間ではなく原因でつなぐ。順に起きたことを箇条書きで続けない。
- 作業の途中の判断のように、記録にない文脈は補わない。
  「知りえない」のような断りも書かない。
- 元の 3 本の記事にあった、本筋には入らないが残す価値のあること
  （図の失敗、リンク構成の選択など）は、最後の余談にまとめる。図は使ってよい。
```

これで一回で今の形になるかは試していない。ただ、四回の書き直しで自分が反対側の書き方へ寄った箇所、つまり分類と判定（`5f9dd28`）と、起きた順の箇条書き（`9fb6d2d`）は、どちらもこのプロンプトの「書き方」のどこかの行で先に塞がれている。

五つのうち対話履歴だけは、書き方の指示では補えない材料で、最初から渡せたかどうかで README の筋そのものが変わる。残りの四つは、書き直しのたびに依頼した人が言葉にしてくれたもので、それを集めるとこのプロンプトになる。
