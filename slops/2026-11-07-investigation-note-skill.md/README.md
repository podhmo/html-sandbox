## 下書きに載っていたのは結論で、理由は対話の側にあった

[issue #133](https://github.com/podhmo/html-sandbox/issues/133) で問題になっていたのは、slops が論じる文体になっていることだった。視点の鋭さを見せたり、テーマを決めて何かを主張したりせず、起きたことの記録と解釈がほしい。11-05 の [記事を書くスキルを考えて、fork で書き比べた](../2026-11-05-skill-for-new-articles.md) は、その原因を、語る対象が複雑になって何を語るかを選べなくなったことに見ていた。

この見立ては用途を問わない話だったので、依頼した人は用途を一つに絞ってみることにして、別の AI と「自分が欲しい技術的な備忘録とは何か」を詰めた。題材にしたのは、WSL2 と 8GB の GPU で音声読み上げを動かし、結果を docs/sketch に残すよう頼んだ TTS の件だった。その作業では、ドライバが古いというエラーに対してホスト側のドライバ更新は変えられない範囲として外され、torch を cu128 に固定して動かし、その回避策が「重要」という無条件の規則として記録されていた。

対話で依頼した人が求めたのは、結果と一緒に返ってくる作業の内側の選択だった。それも「なぜホスト側のドライバ更新を人間に頼まなかったか」ではなく、「どういう選択肢を捨てたか」。前者を良しとすると、作業中に人間に聞きすぎる逆の失敗が起きる。改善したいのは記事の良し悪しではなく記事を頼むプロンプトやスキルのほうで、不足しているものは必須にしたいが、不要なものを必須にして作業を縛りたくはない。時系列で書かせたいが、強調すると年表になるので、因果でつなぐ散文にする。余談は結びのあとに別の章として置くほうがうれしい。名前は、`tech-notes` は知識の解説に、`trial-log` は挑戦というスタンスに傾くので `investigation-notes` にして、ペダンティックにならなければよい、と言っている。依頼が途中で調整されることについては、冒頭の依頼は記事を書きやすい形に変形してよく、完全なトレースは要らず、知見と実施を再現できればよい、とした。

この対話を Q&A にまとめたものと SKILL.md の下書きが、[issue #133 のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903)に置かれた。下書きには 4 節の並び（依頼と前提、試行と判断の経過、最初の問いへの答え、余談）、年表にしないこと、捨てた代替案と理由、反省で締めないことが入っている。一方で、たとえば「Keep the tone matter-of-fact. Do not perform pedantic analysis」という行がなぜそこにあるのか、つまり名前に investigation を選んだときの懸念への手当てだということは、下書きからは読めない。下書きは対話の結論で、各行の理由は対話の側に残っていた。

## 下書きだけで作ると、理由の見えない行が削られた

Claude Code、Codex、Gemini（Antigravity）に、issue のコメントだけを渡して、同じ依頼を別々に出した。write-slops の上に技術調査の記事用のスキルを作り、そのスキルで作成の経緯を記事にする。互いの PR は見ない。

三者とも 4 節の並びは変えなかったが、理由の見えない行の扱いが分かれた。Claude Code は、matter-of-fact の行を、文体の指定はそれに応えるための文を呼ぶという 11-05 の記事の観察を根拠に、ペダンティックの禁止ごと削った。下書き末尾の write-slops の要約も、base の変更に追従が漏れるとして削り、代わりに sketch との分担や計測値の条件を足した。Codex は名前を `write-slops-exploration-notes` に変え、重要な判断ごとに観測、採用案、代替案、見送った理由、結果を取り出させる形にした。代替案を「失敗した試行」「検討したが実行しなかった案」「あとで気づいた可能性」に分け、理由が記録になければ不明と書くことは、この時点で入っている。Gemini は下書きをほぼそのまま、名前もパスも変えずにスキルにした。

Claude Code が削った行と、Codex の「判断ごとに取り出す」は、どちらも対話を知っていれば別の扱いになったはずのものだった。前者は対話の中の懸念への手当てで、後者は「不要なものを必須にしない」に引っかかる。

## 対話を渡すと、揃うところと割れるところが見えた

依頼した人は三者に対話履歴を渡し、スキルを書き直させた。下書きの行がどのやりとりから出てきたかが分かると、11-05 の記事群に共通していた事象（回避策が無条件の規則になる、計測値が条件なしで残る、捨てた選択肢が残らない、書き方を直すと反省文になる）と、それに依頼した人が引いた線（何を捨てたか、不要なものを必須にしない、完全なトレースは要らない）が読めるようになる。三者の書き直しは、どれもこの線に向かって何かを減らすか、言い直すものだった。

Claude Code は、理由が分かったのでペダンティックの禁止を戻した。文体の形容は外したまま、investigation は題材の話で語り口の話ではない、と理由を添えている。依頼を変形してよい理由の二点（依頼とその確認結果の形にするため、途中の転換を経緯に書くなら全文を冒頭に置くと読みにくいため）も戻し、自分で足した計測値の細目や余談の確認済みラベルは必須にしすぎとして外した。捨てた代替案は「実際に検討して進路を変えたもの」に絞った。書く段階で読まれるスキルが代替案を求めると、作業中に検討していない候補で節を埋めることが起きうると考えたからで、範囲外の選択肢は「人間に頼むべきだった」ではなく環境の境界として書く、とした。Codex は「判断ごとに取り出す」をやめ、残す基準を「結果の成立条件・限界・再現を理解するのに必要なもの」にした。依頼を書き直すときに後から加わった条件を最初からあったように書かないこと、結果の評価のしかたを変えた途中の変更も残すこと、回避策を既定で暫定扱いにしないこと、余談を任意にすることを足している。Gemini は、文体の否定命令はモデルごとの語り口の差を損なうとして、ペダンティックの禁止を外し、「意図と環境の具体的な摩擦に焦点を当てる」に置き換えた。

同じ対話を読んでも、揃ったところと割れたところがある。4 節の並び、因果の散文、反省で締めないこと、回避策を条件付きで書くことは三者で揃った。割れたのは次のところだった。

| | `--claude` | `--gpt` | `--gemini` |
| --- | --- | --- | --- |
| 残す代替案 | 実際に検討して進路を変えたもの | 結果の条件・限界・再現に関係するもの。三分類 | 退けられるたびに、環境の制約を書く |
| 後付けの候補への歯止め | あり | あり（理由不明なら不明と書く） | なし |
| ペダンティックの禁止 | 理由ごと戻した | 一般論や鋭さの披露をしない、として残す | 外して「摩擦」に置き換えた |
| 余談 | 必須 | 任意 | 必須 |

ペダンティックの禁止が割れたのは、対話の同じ一言（「investigation-notes でペダンティックにならなければよいが」）を、Claude Code は名前の副作用への手当てと読み、Gemini は対話の「（筆致の差は）セレンディピティ的な形で取得されるべき」と重ねて、語り口の多様性を縛る文体の指定と読んだからだった。余談は、対話の「結びのあとに別の章として置くほうがうれしいかも」を、必須にした二者は節の要求と、任意にした Codex は置き場所の好みと読んでいる。

## 割れたところを比べて、一本に取り出した

割れたところのどちらを取るかを決めるために、依頼した人は Claude Code と Codex に互いの比較を書かせた。

代替案の基準については、Codex の比較が「進路を変えたもの」では、すぐに見送ったため進路が変わらなかった案が落ちると指摘し、Claude Code が比較の中でそれを TTS の件に当てはめた。ホスト側のドライバ更新は範囲外としてすぐに外れ、作業の進路は変えていない。それでも、この件の追試の記事はまさにその案から始まっていた。Claude Code の基準ではこの案が落ち、Codex の基準なら残る。

実線の枠が `--gpt` の基準、その内側の破線の枠が `--claude` の基準、点線の枠はどちらにも入らない案。点線の枠の VOICEVOX や Fish Speech は、対話の中で AI がシミュレーションした「捨てた案」に挙がっていたが、元は依頼に添えた Grok の候補リストにあったもので、作業中に検討された記録はない。こういう案を後から並べないための歯止めは `--claude` と `--gpt` にあって、`--gemini` の「退けられるたびに」にはない、というのも両方の比較が挙げていた。

一本にするときは `--claude` をベースにすることが依頼で決まっていたので、取り出す作業は「`--claude` に何を足すか」になった。最初は Claude Code の総評の推奨に沿って `--gpt` の項目をまとめて取り込み、推奨にない `--gpt` の文も五つ一緒に入れていた（表で条件を比べてよい、関係のない条件は書かない、一度の成功を互換性の保証にしない、部分的な結果も答えになる、余談にしか答えがない状態にしない）。これを外すことになったのは、Codex の比較にあった「すべての条項を足すと、両方の調整で減らそうとした義務を再び増やす危険がある」という一文による。三者が対話を受けて減らす方向に動いていたのに、合わせるとまた増える。Claude Code の比較も、`--gpt` の作業手順の項目は入れないほうがよいと書いていた。

ペダンティックの禁止は、比較では決めず依頼した人に預けられていて、答えは「残す」だった。禁止を残すなら、`--gemini` が代わりに置いた「意図と環境の摩擦」の一文は役割が重なるので、入口として分かりやすいという Codex の評価はあったが入れていない。余談は「不要なものを必須にしない」に合わせて任意にし、置くなら答えのあと、とした。`AGENTS.md` からスキルへの案内も一度入れたが、技術的な備忘録を書かせたいときは依頼した人がスキルを名前で指定するので外した。試作三つは `--claude`、`--gpt`、`--gemini` の名前で本文を残し、名前で指定されたときだけ使う、という description にしている。

できたスキルは [.agents/skills/write-slops-investigation-note/SKILL.md](../../.agents/skills/write-slops-investigation-note/SKILL.md)。`--claude` に比べて、残す代替案の基準が「進路を変えたもの、または結果の条件・限界・再現を説明するもの」に広がり、代替案の三分類、記録にない理由は不明と書くこと、回避策を既定で暫定扱いにしないこと、結果の判断を変えた途中の変更と後から加わった条件の扱い、余談を任意にすることが `--gpt` から入っている。ペダンティックの禁止、依頼を変形してよい理由、範囲外の選択肢を環境の境界として書くこと、sketch との分担は `--claude` のまま。`--gemini` から文面として入ったものはない。

三つの試作も一本にしたスキルも、題材はどれもスキル作りで、技術調査のあとに使ったことはまだない。

## 余談: 元の記事にあったこと

- Codex は、リンク構造の図を svg-gen の検査に通し、原寸の PNG でも読めることを確かめたが、ブログの狭い画面では縮小でラベルが読めなくなった。縦向きの小さな配置に直し、[SVG の落とし穴](../2026-10-27-writing-slops.md/03-svg-pitfalls.md)に記録している。
- Codex は、スキルを他のエージェントから見せる方法として、グローバルへのインストール（そのマシンだけの設定になる）、コピー（編集対象が増える）、リポジトリ内の相対シンボリックリンク（チェックアウトと一緒に持ち運べ、base への相対参照も保てる）を比べて最後を選んだ。のちに実体を `.agents/skills/` に置いて `.claude/skills` をリンクにする構成（`cadb3df`）になった。
- Gemini は、`.agents/skills` 自体を `.claude/skills` へのリンクにする案と、スキルごとにリンクを置く案を比べて後者を選び、単数形の `.agent` へのリンクも足した。svg-gen にラベルを `\n` 入りの文字列で渡すと幅の計算が崩れ、`labelLines` の配列で渡すと通った。
- Codex のスキル検査は、システムの Python に PyYAML がなかったので、その依存だけを入れた uv の環境で走らせている。
- Claude Code は、書く段階で読まれるスキルでは、作業中に代替案が記録されたことまでは保証できない、と書いていた。対話のシミュレーションは「事後に代替案を書く前提があるので、作業中に除外した選択肢をメモに残すようになる」と予測していたが、スキルが読まれるのは書く段階になる。調査の依頼の側で「捨てた選択肢を sketch に一行ずつ残す」と頼めば残るが、作業を縛る側の指定になる。
- 三つの記事には、#133 で依頼した人が楽しみたいと言っていた筆致の差がはっきり出た。Claude Code は何をなぜ直したかを順に書く日記に近く、Codex は確かめた範囲と確かめていない範囲を何度も区切る PR の説明に近く、Gemini はスキルの 4 節を番号付きの見出しにそのまま写し、「真に必要としているのは」「こそが」のような言い切りが多かった。
- 同じ下書きから Devin が作ったスキルの [PR #137](https://github.com/podhmo/html-sandbox/pull/137) が開いたまま残っている。トーンの指定を外し、write-slops の写しを持たず、sketch へのリンクを足した点は、`--claude` の一回目と近い。
- 比べるなら、次に技術調査をしたセッションから fork を起こし、一本にしたスキルと `--claude` で同じ材料から書かせることになる。図に置いたドライバ更新のような案が残るかどうかを見る。
