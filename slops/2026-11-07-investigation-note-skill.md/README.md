## ここまでの流れ

[issue #133](https://github.com/podhmo/html-sandbox/issues/133) は、[答えはその時点の制約から出てくる](../2026-11-05-answers-under-constraints.md)の論じる文体が鼻につく、というところから始まった。11-05 にはそれを受けた slops が続けて書かれ、最後の [記事を書くスキルを考えて、fork で書き比べた](../2026-11-05-skill-for-new-articles.md) では、語る対象が複雑になって何を語るかを選べなくなっていた、という見立てと、それに合わせたスキル write-slops-threads の試作と fork での書き比べが記録された。

その後、依頼した人は 11-05 の記事群を材料に、AI と対話して「自分が欲しい技術的な備忘録とは何か」を詰めた。対話は次のように進んでいる。

- 記事群の要点を書き出させたうえで、answers-under-constraints は中身ではなく「どう書かれたか」の参照で、残りは記事についての記事だ、と位置づけた。
- 求めているものを整理し、欲しいのは、依頼としてプロンプトを渡したときに結果と一緒に返ってくる、作業の内側での迷いや選択の記録だとした。再現できる仕組みはそこへ向かうための to be で、モデルごとの筆致の差はセレンディピティとして得られればよい。
- 整理したいのは記事の良し悪しではなく、記事を依頼するプロンプトやスキルの改善だと確認した。不足していて必須にしたいものは依頼に載せ、不要なものを必須にして作業を縛りたくない。
- TTS の動作確認の依頼文（WSL2、8GB の GPU、結果を docs/sketch に、cleanup 方法も）と、そこで実際に起きたこと（ドライバが古いというエラー、ホスト側のドライバ更新は変えられない範囲として外し、torch を cu128 に固定して解決、その回避策が「重要」という無条件の規則として記録されたこと、1 回だけの計測値が条件なしで並んだこと）を、振り返りの起点として箇条書きにした。
- 欲しいのは「なぜホスト側のドライバ更新を人間に頼まなかったか」ではなく「どういう選択肢を捨てたか」だと線を引いた。前者を是とすると人間に聞きすぎる逆の失敗が起きる。一度に調査を進めるのは悪くなく、あとで見返せるよう記事にすればよい。
- その指定を入れたらエージェントがどう書くかを AI にシミュレーションさせ、骨子を作らせた。時系列で書くこと、ただし年表にはせず因果でつなぐ散文にすること、余談は結びのあとに別の章として置くことを、やりとりの中で足していった。
- 骨子を write-slops-threads と比べ、スキルの文面にさせた。名前は、`tech-notes` は知識の解説に、`trial-log` は挑戦というスタンスに傾くので `investigation-notes` にし、ペダンティックにならないよう歯止めを置いた。
- 最後に、作業の途中で依頼が調整されることを扱った。冒頭の依頼は記事を書きやすい形に変形してよい。理由は、記事を依頼とその確認結果の形にするためと、方針転換を記事に載せるなら完全な依頼文を冒頭に置くと読みにくいため。完全なトレースは要らず、知見と実施を再現できればよい。

この対話を Q&A の形にまとめたものと、最後にできた SKILL.md の下書きが、11-06 に [issue #133 のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903)として置かれた。

## 三つの試作の作り方

### 一回目: issue のコメントだけを入力にした

まず Claude Code、Codex、Gemini（Antigravity）に、同じ依頼を別々に出した。issue のコメント（Q&A と下書き）を踏まえて write-slops の上に技術調査の記事用のスキルを作り、そのスキルで作成の経緯を記事にする。各エージェントは専用の worktree で作業し、互いの PR は見ない。対話履歴はこの時点では渡していない。

三者とも、下書きの 4 節（依頼と前提、試行と判断の経過、最初の問いへの答え、余談）の並びは変えなかった。手を入れたのは周辺だった。

Claude Code は、下書きの「Keep the tone matter-of-fact」と、末尾に写された write-slops の要約を削った。前者は文体の指定がそれに応えるための文を呼ぶから、後者は base の変更に追従が漏れるから。そのうえで、手順は `docs/sketch/`、経緯は記事という分担や、計測値に条件を添えること、余談に確認済みかを付けることなどを足した。

Codex は、名前を `write-slops-exploration-notes` に変え、write-slops の写しを持たないようにした。重要な判断ごとに観測、採用案、代替案、見送った理由、結果を取り出させる形にし、代替案を「失敗した試行」「検討したが実行しなかった案」「あとで気づいた可能性」に分けることと、理由が記録になければ不明と書くことは、この最初の版から入っていた。`.agents/skills/` に相対シンボリックリンクを置き、`AGENTS.md` に案内を足した。

Gemini は、下書きにいちばん近い形でスキルにした。名前もパスも下書きのままで、`.agents/skills/` にスキルごとのリンクを置いた。

### 二回目: 対話履歴を渡して書き直させた

一回目のあと、依頼した人は三者に上の対話履歴を渡し、それを踏まえてスキルを書き直させた。下書きの各行がどういうやりとりから出てきたかが分かると、11-05 の記事群に共通して起きていた事象と、依頼した人がそれに引いた線が見えてくる。回避策が無条件の規則になる、計測値が条件なしで残る、捨てた選択肢が残らない、書き方を直すと反省文になる、という事象と、「人間に聞くべきだった」ではなく「何を捨てたか」、「不要なものを必須にしない」、「完全なトレースは要らない」という線。三者の書き直しは、どれもこの線に沿って何かを減らすか、言い直す方向に動いた。

Claude Code は、一回目で削ったものの二つが理由を知らずに削ったものだったとして戻した。ペダンティックの禁止は、名前に investigation を選ぶときの懸念への手当てだったので、文体の形容は外したまま、investigation は題材の話で語り口の話ではない、という理由と一緒に戻した。依頼を変形してよい理由の二点も戻した。一回目で足した計測値の細目、余談の確認済みラベル、「作業したセッションで書く」は、必須にしすぎとして外したり弱めたりした。捨てた代替案は「実際に検討して進路を変えたもの」に絞り、範囲外の選択肢は「人間に頼むべきだった」ではなく環境の境界として書く、とした。

Codex は、代替案を残す基準を「結果の成立条件・限界・再現を理解するのに必要なもの」に変え、判断ごとに取り出させる形をやめた。依頼は途中の調整も含めて冒頭で書き直してよいが、後から加わった条件を最初から分かっていたようには書かない。途中の変更は、手順を変えたものだけでなく結果の評価のしかたを変えたものも残す。回避策は条件付きで書くが、既定で暫定扱いにはしない。余談は任意にした。記事はこの時点では一回目のままで、あとで依頼されて書き直している。

Gemini は、ペダンティックの禁止を外し、文体の否定命令はモデルごとの語り口の差を損なうとして、「意図と環境の具体的な摩擦に焦点を当てる」に置き換えた。捨てた代替案を思い出す手がかりとして、コマンドの失敗、root がない、ドライバの不一致、パッケージの大きさを例に挙げた。依頼を変形してよい理由の二点は外し、第 3 節で答えるべき問いと成果物に再構成する、とまとめた。

書き直したあとの三つは、同じ対話から同じところへ来た部分と、割れた部分がある。4 節の並び、年表にしない因果の散文、反省で締めないこと、回避策を条件付きで書くことは三者で揃った。検討していない候補を後から並べないための歯止めは、Claude Code と Codex にはあって、Gemini にはない。ペダンティックの禁止は、Claude Code が理由ごと戻し、Codex が一般論や鋭さの披露をしない形で残し、Gemini が外した。余談は Claude Code と Gemini が必須、Codex が任意にした。

### 三回目: 互いに比べさせた

そのあと依頼した人は、Claude Code に #139、#140 との一対一の比較と三つの総評を、Codex に #138、#140 との一対一の比較を書かせた。比較で出てきたことは三つある。

一つは代替案を残す基準で、Codex の比較が指摘し、Claude Code も認めた。対話のシミュレーションで捨てた案の最初に挙がっていたホスト側のドライバ更新は、範囲外としてすぐに外れ、作業の進路は変えていない。Claude Code の「進路を変えたもの」ではこの案が落ち、Codex の「条件・限界・再現に関係するもの」なら残る。

二つめは、Gemini の「退けられるたびに環境の制約を書く」が網羅を求める読み方をされうることで、両方の比較が挙げた。理由を環境の制約に限っているので、範囲外、時間、計測による見送りの置き場もない。

三つめは、条項を全部足すと、三者がそれぞれの書き直しで減らそうとした義務がまた増えること。Codex の比較が書き、Claude Code の比較も、Codex 版にある作業手順の項目（渡す前の確認など）は入れないほうがよい、と書いた。

ペダンティックの禁止をどちらに取るかは、比較では決めず、依頼した人に預けられた。

## 比較から一本のスキルを取り出した

一本にする作業は、`--claude` をベースに `write-slops-investigation-note` を作る、という依頼で始まった。三つの試作は名前とパスが重なっていたので、この時点ですでに `--claude`、`--gpt`、`--gemini` に改名されてマージされていた。

最初は、Claude Code の総評にあった「一本にするなら」の推奨に沿って、`--claude` に `--gpt` の代替案の基準と三分類、後から加わった条件の扱い、評価のしかたを変えた変更、既定で暫定扱いにしないこと、余談を任意にすること、`AGENTS.md` からの案内を取り込んだ。このとき推奨にない `--gpt` の文も五つ一緒に入れていた（表で条件を比べてよい、関係のない条件は書かない、一度の成功を互換性の保証にしない、部分的な結果も答えになる、余談にしか答えがない状態にしない）。総評が預けていたペダンティックの禁止は、依頼した人が「残す」と答えた。試作三つは「残して description を変える」ことになり、「比較の記録として残した試作。名前で指定されたときだけ使う」にした。

そのあと、比較を含む全部の記事を読み直すよう言われ、三つめの指摘（条項を全部足すと義務がまた増える）に、一緒に入れた五つの文がそのまま当たっていたので外した。Gemini 版の「意図と環境の摩擦」の一文は、Codex の比較では入口として分かりやすいと評価されていたが、ペダンティックの禁止を外した代わりに置かれた文で、禁止を残すなら役割が重なるので、依頼した人に確認して入れなかった。

依頼した人が対話履歴をもう一度貼り、できたスキルと突き合わせた。代替案の基準は二つを「または」でつないだので、ドライバ更新の案は残る。余談は、対話では「結びのあとに別の章として置くほうがうれしいかも」という言い方で、必須にした二者は節の要求と、任意にした Codex は置き場所の好みと読んだことになる。「不要なものを必須にしない」に合わせて任意のまま、置くなら答えのあと、とした。

最後に `AGENTS.md` の案内を外した。技術的な備忘録を書かせたいときは依頼した人がスキルを名前で指定するので、自動で選ばせる案内は要らない。`AGENTS.md` には、用途ごとの派生スキル（`write-slops-*`）があり、名前で指定されたときだけ使う、という一文だけを置いた。

できたスキルは [.agents/skills/write-slops-investigation-note/SKILL.md](../../.agents/skills/write-slops-investigation-note/SKILL.md)。`--claude` からの差分は次のとおり。

| 項目 | `--claude` | 一本にしたスキル | 出どころ |
| --- | --- | --- | --- |
| 残す代替案 | 進路を変えたもの | それに加えて、結果の条件・限界・再現を説明するもの | `--gpt`、対話 |
| 代替案の区別 | なし | 失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分ける | `--gpt` |
| 記録にない理由 | 補わない | 補わず、不明と書く | `--gpt` |
| 回避策 | 条件付き | 条件付きで、既定では暫定扱いにしない | `--gpt` |
| 途中の変更 | 次にしたことを変えたもの | 結果の判断を変えたものも。後から加わった条件を最初からあったように書かない | `--gpt` |
| 余談 | 必須 | 任意。置くなら答えのあと | `--gpt`、対話 |
| ペダンティックの禁止 | あり | あり | 依頼した人の判断 |

三つの試作と一本にしたスキルは、どれも題材がスキル作りで、技術調査のあとに使ったことはまだない。

## 余談: 元の記事にあったこと

- Codex は、リンク構造の図を svg-gen の検査に通し、原寸の PNG でも読めることを確かめたが、ブログの狭い画面では縮小でラベルが読めなくなった。縦向きの小さな配置に直し、[SVG の落とし穴](../2026-10-27-writing-slops.md/03-svg-pitfalls.md)に記録している。
- Codex は、スキルを他のエージェントから見せる方法として、グローバルへのインストール（そのマシンだけの設定になる）、コピー（編集対象が増える）、リポジトリ内の相対シンボリックリンク（チェックアウトと一緒に持ち運べ、base への相対参照も保てる）を比べて最後を選んだ。のちに実体を `.agents/skills/` に置いて `.claude/skills` をリンクにする構成（`cadb3df`）になった。
- Gemini は、`.agents/skills` 自体を `.claude/skills` へのリンクにする案と、スキルごとにリンクを置く案を比べて後者を選び、単数形の `.agent` へのリンクも足した。svg-gen にラベルを `\n` 入りの文字列で渡すと幅の計算が崩れ、`labelLines` の配列で渡すと通った。
- Codex のスキル検査は、システムの Python に PyYAML がなかったので、その依存だけを入れた uv の環境で走らせている。
- Claude Code は、書く段階で読まれるスキルでは、作業中に代替案が記録されたことまでは保証できない、と書いていた。対話のシミュレーションは「事後に代替案を書く前提があるので、作業中に除外した選択肢をメモに残すようになる」と予測していたが、スキルが読まれるのは書く段階になる。調査の依頼の側で「捨てた選択肢を sketch に一行ずつ残す」と頼めば残るが、作業を縛る側の指定になる。
