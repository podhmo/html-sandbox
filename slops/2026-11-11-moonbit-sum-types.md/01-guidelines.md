# 指針: どの構造を sum type にするか

> [!NOTE]
> 執筆: Claude Code。本文の基準（#158 の点検コメント）を一般化し、草稿を `moonbit/` のコードに照らして直した版。照らし合わせた結果は末尾の表にある。

本文の7項目は「Go の形を写していないか」を点検するための基準だった。ここではそれを、新しく型を書くときにも使える形に組み直す。問いは3つ。どの構造を sum type にするか、sum type にしない方がよいのはいつか、enum を超えて state machine に移した方がよいのはいつか。

## どの構造を sum type にするか

共通する兆候は「値の意味を、型ではなく呼び出し側が再解釈している」こと。次のどれかがあれば候補になる。

1. 排他な状態を複数の変数で表している。Bool が2つで4通り表現できるのに、意味のある組は3通り以下。あるいは「同時に1つしか非空にならない」バッファが並んでいる
2. 1つの状態が、型の違う2か所に分かれている。Bool と別の enum の variant、あるいは2つの enum の組で、直積に起こりえない組がある。1 と同じ問題だが、片方がすでに enum なので見落としやすい
3. ある状態のときだけ意味を持つフィールドがある。その状態でないときにダミー値（`""`、`0`、空の構造体）を入れている
4. 「無い」を値の領域の一部で表している。`""`、`-1`、`0` を返し、呼び出し側が `== ""` で分岐する
5. 閉じた語彙を文字列で持っている。取りうる値をコードの作者が列挙でき、増えるときはコードの変更を伴う
6. 性質を持ち主でない場所に置いている。リスト全体の性質を各項目に置き、「先頭項目で決まる」という規則を利用側が繰り返す
7. match に `_ =>` のフォールバックが要る。型が実際に取りうる値より広い

判断の要は 4 と 7 の「再解釈」で、`""` や `-1` があること自体ではない。値としての意味（空の文字列、ソートキーとしての -1）を持つなら残してよい。再解釈が1つの関数の中で閉じていて、外に漏れないなら優先度は低い。

置き換え先は兆候で決まる。

| 兆候 | 置き換え先 |
| ---- | ---- |
| 排他な状態、状態依存のフィールド | enum の variant と、その payload |
| 2か所に分かれた1つの状態 | 一方を他方の variant の payload に入れる。組で起こる値だけが残る |
| 欠落 | `T?` |
| 閉じた語彙 | payload のない enum。文字列への変換は出力の境界で |
| 性質の置き場所 | 持ち主の型へ移す。sum type の問題ではないが、移すと sum type の置き場所ができることが多い |

## sum type にしない方がよい状況

1. 範囲のある数値。見出しの level 1..5 を5 variant にしても値の写しになるだけで、算術（`level + 1`）が書けなくなる。構築時の検査で足りる。その代わり、数値で分岐する match には `_ =>` が残る。これは7の例外として受け入れる
2. 外部入力そのもの。front matter の生の値や URL 文字列は文字列のまま受け取り、パースした結果を型にする。境界より内側だけを型で守る。front matter の `title: ""` を「指定なし」として扱うのは、境界で行う変換なのでここに当たる
3. 開いた集合。利用者やデータが新しい値を持ち込む（タグ名、ファイル拡張子、HTTP ヘッダ名）なら enum は閉じすぎる。既知の値に variant を与えて `Other(String)` を残す形もあるが、既知の値で分岐する処理が無いなら文字列のままでよい
4. データが増えて操作が固定のとき。variant を足すたびに全 match を直すことになる。操作の方が増えるなら enum、データの種類の方が増えるなら trait や関数の記録が向く（expression problem の二択）
5. 真の2値で、他の状態と組み合わさらない Bool。`at_line_start` のようなトグルは enum にしても名前が変わるだけ。名前付き引数の ON/OFF も同じ
6. 呼び出し側が存在を保証している API。ルータが一致を保証した後の `param` を `String?` にすると、全呼び出し側に到達しない unwrap が増える
7. 空のコレクション。空配列は `is []` で素直に分岐できる。`Option` が要るのは、空を作るために必須フィールドの値を捏造しないといけない型（`ItemList` の `kind`）だけ
8. 計算の中で使う番兵。API は `Int32?` で受け取り、関数の中で比較の下限として `-1` に直すのは構わない（`nest_items` の `parent.unwrap_or(-1)`）。番兵が関数の外に出ないなら、型が守るべき不変条件は無い
9. フラグはあるが、そのフラグのときだけ意味を持つフィールドが無い。variant にしても名前が明瞭になるだけなら優先度は低い。ただし先に「どの構造を」の 2 を確かめる。フラグが別の型の variant と排他なら、それは同じ状態の片割れで、この項には当たらない

## state machine に移した方がよい状況

enum で「今の状態」を表せても、遷移の規則がループ本体に散っていれば読みにくさは残る。次のときは遷移を関数として切り出すことを考える。

1. 状態が時間とともに変わり、遷移の順序に規則がある。「未ロード → ロード済み」のように後戻りしない、あるいは特定の入力でだけ遷移する
2. 複数の mutable 変数が共同で「今どのモードか」を表している。本文の `scan` がこれで、まず enum に畳み、その次の段階として遷移を切り出す
3. 「この入力はこの状態でしか起きない」という規則がある。例: コードフェンスの中では見出しを見ない
4. 同じ遷移が複数の場所に書かれている。典型は「閉じる入力が来たとき」と「入力が尽きたとき」の2か所に同じ後始末がある形。入力の終わりも1つの入力として扱い、`close(state)` に寄せる
5. 遷移そのものをテストしたい。`step(state, input) -> state` の形にすると、入力列を与えずに1遷移ずつ検査できる

逆に、enum にした段階で止めてよいのは次のとき。

- 遷移が一度きり、または「キーが変わったら作り直す」だけ。遅延初期化は `T?` か Lazy で足りる
- 遷移の規則がループ本体の1つの match に収まっていて、各 arm が短い
- 状態の外から観測されない。関数内のローカルな状態で、テストは入出力で取れる

## MoonBit で書くときの道具

- variant の payload を更新するには、`mut` ラベル付きフィールドと `as` 束縛を使う。`Details(..) as d` と束縛して `d.depth -= 1`。これを知らないと enum 化を諦めて mutable 変数に戻しがち
- variant の payload だけを触る処理は、その variant の match arm の内側に置く。外に置くと「ここでは必ずこの variant」が型に言えず、到達しない `else` を `abort` か `continue` で埋めることになる
- `is` パターンで「この variant のときだけ」を式の中に書ける（`if it.children is Some(sub)`）
- 文字列への変換は enum のメソッド（`name()` など）に1か所だけ置く
- JS や JSON への出力は内部の型に従わせる。ワイヤ形式のために内部の型を崩さない

## 点検の手順

1. `Bool` フィールドと `let mut` の Bool、`== ""`、`-1`、`_ =>` を検索する
2. 見つかった箇所ごとに、値が「欠落・状態」を表しているのか「値そのもの」なのかを判断する
3. 状態なら、同じ状態を表している他の変数や他の型の variant を探す。組で1つの状態なら enum の候補
4. 上の「しない方がよい状況」に当たらないかを確かめる
5. 遷移の規則が散っている、または同じ遷移が2か所にあれば、state machine への切り出しを検討する

草稿から直したのは次の3点で、どれも照らし合わせて初めて見えたもの。

- 「どの構造を」に 2（2か所に分かれた1つの状態）を足した。草稿の 1 は「複数の変数」だけを見ていて、片方がすでに enum の場合を拾えなかった。router と `scan` の2件はどちらもこの形だった
- 「しない方が」の 9（旧 8）に、先に排他性を確かめるという但し書きを付けた。本文が router の `subtree` を見送った理由はこの項そのもので、但し書きがあれば判断が変わっていた
- 「しない方が」に 8（計算の中の番兵）を、state machine に 4（同じ遷移が2か所）を足した。前者は #162 で `Option` にした `nest_items` が中で `-1` に戻していることを、後者は `scan` の終端処理を読んで書いた
