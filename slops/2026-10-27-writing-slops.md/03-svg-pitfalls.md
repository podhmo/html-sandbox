# skill に沿って図を作り直したときの落とし穴

[posts の AI 小説の記事](../../posts/2026-10-27-why-ai-novel-is-bored.md)にある9枚の SVG を、write-slops の skill の「位置・大きさ・重なりに意味を持たせる」という方針で描き直した。そのときにつまずいたところを残す。

元の9枚は、どれも本文の要点を箱に入れて矢印でつないだ図だった。たとえば文字列の類似度の図は「類似度：極めて低い」「読者の認知：同じ場面」という2行を箱に入れただけで、本文を読めば済む。作り直しでは、各図の主張をひとつの視覚的な性質に結びつけた（作中の時間を縦の位置に、分量を帯の長さに、段落同士の似かたを行列の塗りに）。落とし穴はその先で出てきた。

## 位置の意味が軸と逆になる

「再描写を削ると、直後の台詞が軽くなる」を、横軸を本文の位置、縦軸を読者に溜まる重みにした曲線で描いた。最初の版では、削った場合の台詞を元の台詞より右に置いていた。

削れば本文は短くなるので、台詞は手前に来るはずだ。縦の高さ（重みが低い）だけを見て置き場所を決め、横軸が何を表すかを忘れていた。描画した画像を見ても形としては自然なので気づきにくい。点を置くたびに、両方の軸についてその位置が正しいかを確かめる。

## ひとつの塗りに二つの意味を持たせてしまう

段落を並べた帯で「削る前」と「削ったあと」を比べる図では、上の段の濃い塗りが「再描写の段落」、下の段の濃い塗りが「直しが要る段落」になっていた。同じ見た目が別のことを指している。削る段落を点線の枠に変え、塗りは「直しが要る」だけに使った。

同じことは図をまたいでも起きる。作中の時間の線グラフに「期待される動き」として灰色の太い帯を入れたところ、前からあった「再描写の区間」の網掛けが帯と同じ灰色で、区別がつかなくなった。網掛けは消した。線が帯から落ちるだけで、再描写の区間は読み取れた。

逆に、記号をそろえると得をする。記事1の線グラフと記事4のジャンル比較の図で「太線＝本文が描いている時点」「灰色の帯＝読者が期待する動き」を共通にしたので、記事4の図は記事1の読み方のまま読める。束の記事では、記号の意味を記事をまたいで固定しておくとよい。

## currentColor の図で色の名前を書く

`currentColor` で描いた図は、ダークテーマでは線と文字が白になる。凡例に「黒線：本文が描いている場面」「濃いほど大きく」と書いていたので、ダークテーマでは説明が見た目と食い違った。

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 420 150" width="420" height="150" role="img" aria-label="同じ図でも、ダークテーマでは線が白くなり、黒線と書いた凡例が合わなくなる">
  <rect x="10" y="10" width="190" height="100" rx="6" fill="#ffffff" stroke="#888888"/>
  <rect x="220" y="10" width="190" height="100" rx="6" fill="#13171f" stroke="#888888"/>
  <path d="M25 80H75V50H125V30H185" fill="none" stroke="#000000" stroke-width="2.5"/>
  <path d="M235 80H285V50H335V30H395" fill="none" stroke="#ffffff" stroke-width="2.5"/>
  <text x="105" y="100" font-size="11" text-anchor="middle" fill="#000000">黒線：本文の位置</text>
  <text x="315" y="100" font-size="11" text-anchor="middle" fill="#ffffff">黒線：本文の位置</text>
  <g fill="currentColor" font-size="11" text-anchor="middle">
    <text x="105" y="132">ライトテーマ</text>
    <text x="315" y="132">ダークテーマ：線は白い</text>
  </g>
</svg>
```

色の名前ではなく、テーマに左右されない性質で呼ぶ。「太線」「塗りの強さ」「点線の枠」なら、どちらのテーマでも同じものを指す。

## 図の id はページ全体で一つ

斜線の `<pattern>` やグラデーションの `<linearGradient>` には `id` が要る。svg フェンスは中身がそのまま HTML に入り、束はすべてのメンバーが一つのページに並ぶ。そのため、別々の図に書いた `id` も同じ文書の中でぶつかる。同じ `id` で中身の違う定義があると、後の図が先の図の定義で塗られることがある。

今回は実際に崩れる前に気づき、`novel-hatch`、`novel-hatch-split` のように図ごとに別の名前にした。単体の SVG ファイルとして確認していると、この衝突は見えない。

## 右寄せのラベルが viewBox の外へはみ出す

行の見出しを `text-anchor="end"` で左端の帯の手前に置いたところ、「削ったあと」だけが長くて viewBox の左端で切れた。文字幅はフォントで変わるので、座標から確実には読めない。描画して見て見つけ、viewBox を左に広げた。

## 模式図が測ったデータに見える

線グラフや行列、分量の帯は、数値のグラフのように見える。今回の図はどれも説明のための模式図で、実際の小説を測ったものではない。特に分量の帯は、比率に根拠があるように読めてしまう。本文で模式図だと断る必要がある。差し替えた直後は断りがなかったので、あとから各記事の最初の図の近くに一文ずつ足した。表の数字も同じで、架空の例だと書いておく。

## 図を差し替えると、本文の言い回しが古い図に残る

記事1の図の直後には「描写のかたまりが、あちこちにいくつもぶら下がっている」という一文があった。これは、出来事の箱から描写の箱が枝分かれしていた古い図に合わせた言い方だ。新しい線グラフには「ぶら下がる」形がない。図だけを差し替えると、本文の「この図では」「こうやって図にしてみると」が古い図を指したまま残る。この一文は、あとから新しい図の見え方（線が何度も「裏切り」の高さへ落ちて戻る）に合わせて書き直した。

## SVG でなくてよい箇所もある

図のない節に何かを足そうとしたとき、記事3の「プロファイラにならざるを得ない」という節は、本文そのものが「出来事ごと・話ごとの分量の分布を見せる」と書いていた。プロファイラの出力はもともと集計表なので、ここは SVG ではなく markdown の表にした。セルに■を並べれば分量の大小も見える。表にしておくと、「第3話と第5話の欄が同じ■■で見分けがつかない」ことが、そのまま「合否を判定できない」理由として読める。

形や位置の関係を見せたいときは SVG、行と列で比べたいときは表、というように、先に何を見せたいかを決めてから形式を選ぶ。

## 確認の経路

- `rsvg-convert` で PNG にすると、形や文字のはみ出しは確認できる。ただし背景は白で、ブログの CSS もダークテーマも効かない。上の「黒線」の食い違いは、これでは見つからなかった。
- `/preview` はブラウザの中で wasm を動かすページなので、コマンドラインからは結果を取り出しにくい。
- 今回は、`make -C go watch` で動いているブログから記事ページの HTML を取得し、本文の部分だけ図に差し替えたファイルを作った。それを headless Chrome で、ダークテーマとライトテーマの両方で撮影した。ブログの CSS が当たった状態で、テーマごとの見え方を比べられる。
- watch のサーバーは、ファイルを保存した直後だとまだ古い内容を返すことがあった。少し待ってから取得し直すと反映されていた。

## 追記: データ図 (fig-chart-*) で見つけた落とし穴

[chart-gen の記事](../2026-11-01-chart-gen.md)の実験（seed 固定の仮想データから ECDF・時系列・散布図を生成）で、概念図とは別の失敗が出た。

## 系列ラベルを線の端に置くと衝突する

「凡例より直接ラベル」のつもりで系列名を折れ線の右端に置く設計にしたが、ECDF では 2 系列とも右端が同じ位置（累積割合 1.0）に収まるため、ラベル同士が重なった。端でなく、2 つの曲線が離れている分位点（今回は p80 付近）を選んでラベルを置いた。直接ラベルは「端に置く」のではなく「系列同士が十分離れた場所に置く」が正しい。

## 推定した線は実測の線と同じ記法で描かない

散布図に最小二乗の回帰線を足した。これは実測値ではなくフィットしたモデルなので、実線のままだと「計測された系列」に見える。破線に変え、さらに「単回帰（説明用）」とラベルを書いた。誤差棒・信頼区間の帯も同じで、推定は推定と分かる記法にする（色が使えるなら色でも分ける）。

## lint は小さな点を「ラベルの容器」と誤認する

check.ts の「テキストが中に収まるべき形状からはみ出す」検査は、テキストの基点が入っている形状を全部コンテナ扱いする。散布図の r=1.8 の点の上に回帰線のラベルが乗ったところ、「ラベルが楕円からはみ出ている」と FAIL になった。データ図では点は容器ではなく目盛り上の印なので、テキストが収まる最小寸法（今回は min(w,h) < 12）未満の形状は容器に数えないように直した。図の種類が増えると lint の仮定もずれる。

## 仮想データ・模式データは毎回断る

seed 固定の疑似乱数で作った計測値でも、軸・n・期間・イベント線まで揃った図は本物のレポートに見える。模式図の項と同じ失敗が、今度は「正直なメタデータを揃えた図」で起きた。タイトルか脚注に毎回「仮想データ」と書くことにした。

## 点の数だけ頂点が増える

n=600 の ECDF を 2 系列そのまま描くと、ステップの頂点が 1200 個になって SVG が 90KB あった。統計量は同じまま描画の頂点だけを間引いて 150 個に落とした（27KB）。inline 埋め込みにする図では、サンプル数と描画頂点数は別に考える。

## currentColor だけでは系列は実質 2〜3 本まで

色なしだと太さ・破線・不透明度の組み合わせで識別できるのは 2〜3 系列。ガイドラインの「折れ線 5 本まで」より手前で限界が来る。多系列は色を足すかスモールマルチプルに逃がす。colorful 用に両テーマで読める色を選んだパレット（Okabe-Ito 系を調整）を足したが、ダーク地に黒に近い色・ライト地に黄色系は使えないので選びは絞られる。

## 同じ seed の乱数ストリームを2本作ると系列が相関する

`gauss(rng(seed))` と別途 `rng(seed)` を立てると、同じ系列の乱数を2つの目的で使うことになる。一見無関係に見える量同士に相関が出る。ストリームは1本だけ作り、そこから一様乱数と正規乱数の両方を取る。

## 箱ひげは多峰性を隠す（規約どおりの失敗を再現した）

ガイドラインが「箱ひげは多峰性を見せられない」と警告していたので、わざと二峰の群（速い経路と遅い経路が混ざった cached）を入れてみた。箱はひとつの広い分布に見えるだけで、谷があることは分からない。同じデータをヒストグラムにすると二つの峰がはっきり出る。箱ひげの項に書いてある「n < 30 なら点を重ねる MUST」は小標本への規定だが、n=160 でも間引いた点を重ねると分布の形が透けて見えて助かる。「箱ひげで比較したあと、怪しい群はヒストグラムか ECDF で確認する」が実務の動作になる。

## ヒートマップの凡例ラベルはセルの外に置く

凡例のランプをプロット上端のすぐ上に置き、ラベルをその下に書いたら、ラベルの基点が最上段のセルの中に入ってしまい、check.ts に「セルからはみ出ている」と FAIL された。セルも矩形なので、中のテキストは容器判定の対象になる。凡例はまとめてプロットの外（上側の空き、あるいは下側）に置く。ヒートマップの中に値の注記を入れたくなったら、セルが容器になることを思い出す。

## プロット領域をはみ出す図は lint では拾えない（→ chart.ts 側で解消済み）

ヒストグラムの山と散布図の外れ値が、軸の上限（ydom）より大きな値でプロット領域の上端を突き抜けていた。viewBox はキャンバス全体から計算されるので、はみ出た要素も「viewBox の内側」であり check.ts は拾えない——「描画エリアと図の境界が一致しない」系の失敗は意味側のチェックになる。

現在は chart.ts 側で構造的に解決済み。マーク生成が emit 時にドメイン内かを `inside()` で検査して外なら生成を止め、`p.data(() => ...)` で囲んだマークは `<g data-plot="x0 y0 x1 y1">` に入って check.ts がプロット矩形で検査する。残る注意は 2 つ: `p.data()` の外や `c.raw()` 直書きの要素は対象外（概念図など）、そしてドメインの選び方そのもの（0 起点か、切り詰め方）は引き続き人の判断。

## 検査を通った横長SVGでも、縮小すると読めなくなる

[探索ノート用スキルの記事](https://github.com/podhmo/html-sandbox/tree/96f82be97a99a71ff0998f40a4670dbb9adead01/slops/2026-11-07-exploration-notes-from-issue-133.md)で、幅約680の実体とリンクの図は、境界・ラベルの検査を通り、原寸のPNGでも読めていた。しかしブログの狭い画面では、記事幅に収める縮小によってラベルが読みにくくなった。小さな配置に変え、共通・探索用という短いラベルと縦向きのリンクの矢印を使い、正式名は本文に残した。原寸だけでなく記事内の表示幅でも確認する必要がある。座標の検査を通ることは、CSSで縮小したあとも文字が読めることを保証しない。

## 実体参照をそのまま文字数として数える lint の偽陽性

`check.ts` の「テキストが中の形状からはみ出す」検査は、`<text>` の中身を生の文字列のまま `textWidth` で見積もる。しかし `esc()` が `<` を `&lt;` に変えて出力するので、`<ol start="3">` のようなラベルは、表示される文字列より実体参照ぶん長く見積もられ、実際には収まる箱でも overflow で FAIL になった。`<ol>` というタグ名をラベルに使う図（[番号付きリストの記事](../2026-11-07-numbered-lists.md)のもの）で出た。テキストを取り出すときに `&lt;` `&gt;` `&quot;` `&amp;` をデコードするように check.ts を直した。`esc()` がエスケープするのはこの4種なので、これで表示幅と見積もりが一致する。
