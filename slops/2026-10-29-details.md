# <details> と <summary> で記事の中身を折りたためるようにした

[issue #74](https://github.com/podhmo/html-sandbox/issues/74)「detailsタグとsummaryタグで余分な解説を隠したい」を Go と MoonBit の両方に実装した（[PR #103](https://github.com/podhmo/html-sandbox/pull/103)）。記事に Q&A の「答えを開くまで隠す」が書けるようになった。下の折りたたみがそのデモで、この記事のソースの一部でもある。

<details>
<summary>この折りたたみ自体がデモ</summary>

中身は普通の Markdown として書ける。`code` スパンも [リンク](https://github.com/podhmo/html-sandbox) も効く。リストやコードブロックも入る。

</details>

## 「details,summary のみサニタイズされなければ良いのか?」

実装を始めるときに受けた問いがこれだった。答えは「範囲としてはその通り。ただし仕組みは少し違う」だった。

このブログには、タグごとに通す・落とすを決めるサニタイザーという部品が存在しない。記事の本文はすべて Text ノードとしてエスケープされるだけなので、`<details>` と書くとタグが消えるのではなく、そのまま `<details>` という文字列として見える。「allowlist に details と summary を足す」という発想の立つ場所が、そもそもなかった。

だから実装は「2 つのタグを素通しにする」ではなく「パーサーに新しいブロック構文を教える」になった。tinymarkdown に `Details` ブロックを足し、行全体が `<details>` の行から対応する `</details>` の行までをひとつのブロックとして読む。最初の空でない行が `<summary>...</summary>` の形なら summary として取り出し、残りをもう一度 `Parse` にかける。引用 (`Quote`) が中身を丸ごと再帰的に読むのと同じ仕組みなので、中には段落、リスト、コードブロック、入れ子の details も入る。

## 厳密一致にしたら、安全性がおまけで付いた

開くタグも閉じるタグも「その行だけがタグ」でなければ認めない、という形に決めた。

- `<details open>` → 段落テキストのまま
- `<details onclick="...">` → 段落テキストのまま
- 行の途中にある `</details>` → 閉じない
- `<summary>...</summary>` として拾うのは、details の中の最初の空でない行だけ

属性を受け付けないので、`<details onclick>` も `<summary onfocus>` も入り込む経路がない。これは「raw HTML を通さない」という既存の方針を守ったまま機能を足せる、というだけの話だが、「タグを通す」ではなく「構文を足す」にしたことで、注入の面が増えなかったのは素直に良かったと思う。

一方で `<details open>` で最初から開いた状態にはできない制限が残った。必要になれば `Details` に `open` フラグを持たせるのが拡張点だけれど、issue の用途は「答えを隠す」なので要らないと判断して入れなかった。

## 集める段階と、もう一度読む段階

パーサーの scan が `<details>` を見ると、以降の行をそのまま（trim も dedent もせず）集めるモードに入る。集めている間に見ている状態は 2 つだけだ。

- `<details>` の行で深さを +1、`</details>` で -1。0 になったところでブロックを吐く。これで入れ子が正しく閉じる
- `` ``` `` で始まる行が来たらフェンスの中と見なす。details の中のコードフェンスに `</details>` と書いても、外側を早く閉じない

閉じタグが来ないまま文末に着いたら、閉じない `` ``` `` フェンスと同じく「そこまで」をブロックにする。

集めた行は `parseDetails` が summary を剥がしてから残りを `Parse` に投げる。「まず行を集めて、あとで再帰的に読む」という形は Quote と Alert と同じなので、実装の型は既にあった。新しいのは深さの数え方とフェンスの扱いくらいだ。

## summary は inline で読む

`Summary` は文字列として持ち、描画のとき `Inlines` にかける。だから `<summary>答えは `42`</summary>` のようにコードスパンやリンクが効く。summary がないか空なら `<summary>` 要素は出さず、ブラウザーのデフォルトのラベルに任せる。

ひとつ小さな判断を入れた。記事の description に使う `firstParagraph` は `Section` の子には降りるが `Details` の子には降りない。折りたたみは「畳んで隠した情報」なので、記事の先頭段落を拾うロジックが畳まれた中身を description に使うとおかしい。意識した非対称なので、検証用の記述として残しておく。

## ミラーするコスト

このリポジトリは Go と MoonBit の 2 言語で同じ機能を持つ方針なので、ブロックを 1 つ足すと `Block` を網羅する match が全部新しい variant を要求する。今回動いた面は次の通り。

- `go/pkg/tinymarkdown` と `moonbit/pkg/tinymarkdown`（本体 + テスト 15 ケースのミラー）
- ブログの描画（`views.go` / `views.mbt`）
- `pkg/tinymarkdown/js`（JS ブリッジ、`{"kind":"details", ...}` を吐くようにした）
- `examples/parse-markdown` の dump
- `experiments/browser-render` と `experiments/wasm-pair`（Block の網羅 match がコンパイルエラーになったので対応）
- `preview.wasm`（コミット対象の成果物なので再生成）

構文をひとつ足すとこの全部が動く。テストケースは Go 側で組んで MoonBit 側にそのまま写すので、「両実装で同じ入力が同じブロックになる」は機械的に確かめられる。ただ、新しい構文を足すたびにこのミラー全体が増えるので、拡張にはそこそこの重さがあるのも事実だ。

## 残っている制限

- `**太字**` はこの tinymarkdown が強調を持たないので、issue の例にある `**正解：c**` は `**` ごと出る。details とは別の未実装で、今回は手を付けなかった
- `<summary>` は 1 行限定。複数行にわたる summary や、`<summary>` の後ろに同じ行で本文が続く形は認めていない
- 認めるのは小文字の `<details>`、`</details>`、`<summary>`、`</summary>` だけ。大文字や属性つきは段落テキストになる

「サニタイズされなければ良いのか」という問いに対する実装上の答えは「サニタイズがない場所に、新しい構文を足す」だった。素通しの穴を開けるより、そちらのほうが残る面が小さい。
