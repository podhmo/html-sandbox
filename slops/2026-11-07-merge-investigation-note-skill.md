# 技術調査のあとに書く記事のスキル write-slops-investigation-note を作った

> [!NOTE]
> 執筆: Claude Code（Opus 5.5）。統合の作業をしたセッションではなく、記録から書いている。材料は issue #133 の本文とコメント、三つの試作の記事とその比較、統合のときに書いたこの記事の初稿、下書きの元になった対話。
>
> 三つの試作の記事は [PR #144 の削除コミット](https://github.com/podhmo/html-sandbox/pull/144/commits/e09565dd4e85eb5d0c1c0454a36071645507b69d)で消し、その文脈はこの記事に移した。試作の経緯はそれぞれの PR に残っている。Claude Code の [PR #138](https://github.com/podhmo/html-sandbox/pull/138)、Codex の [PR #139](https://github.com/podhmo/html-sandbox/pull/139)、Gemini（Antigravity）の [PR #140](https://github.com/podhmo/html-sandbox/pull/140)。消す前の記事は、コミット `96f82be` の [Claude Code 版](https://github.com/podhmo/html-sandbox/tree/96f82be97a99a71ff0998f40a4670dbb9adead01/slops/2026-11-07-investigation-notes-skill.md)、[Codex 版](https://github.com/podhmo/html-sandbox/tree/96f82be97a99a71ff0998f40a4670dbb9adead01/slops/2026-11-07-exploration-notes-from-issue-133.md)、[Gemini 版](https://github.com/podhmo/html-sandbox/blob/96f82be97a99a71ff0998f40a4670dbb9adead01/slops/2026-11-07-write-slops-investigation-notes.md)で読める。

## 依頼と、できたもの

できたのは [write-slops-investigation-note](../.agents/skills/write-slops-investigation-note/SKILL.md) で、環境構築、実現性の確認、追試、デバッグのような技術調査のあとに slops を書くとき、write-slops の上に重ねて読むスキルだ。記法、図、バンドルの扱いは write-slops に任せ、記事に何をどの順で書くかだけを決めている。依頼と前提、試行と判断を起きた順に因果でつないだ経緯、最初の問いへの答え、任意の余談、の順になる。

起点は [issue #133](https://github.com/podhmo/html-sandbox/issues/133) で、本文は、11-05 の [答えはその時点の制約から出てくる](2026-11-05-answers-under-constraints.md) を読んで論じる文体が鼻についてきた、というもの。コメントには好みが並ぶ。視点の鋭さをアピールしない、論じるテーマを決めてディベートの一部のようにしない、起きたことの記録と解釈はあってほしい。11-06 の [最後のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903) は「一つの体裁として技術的な備忘録をユースケースとして置いてみると良いかもしれない」で、Q&A 形式の整理と、`write-slops-investigation-notes` という名前の SKILL.md の下書きが付いていた。

この下書きを踏まえて write-slops の特殊化スキルを作り、そのスキルで経緯の記事を書く、という同じ依頼を、Claude Code、Codex、Gemini が別々に実行した。そのあと三つを一本にするよう依頼され、Claude Code 版を土台にして今の形になった。

## 下書きに載っていたのは、対話の結論だった

下書きは、依頼した人と AI の対話から作られていた。対話の途中で依頼した人は、整理したいのは記事に書くべき重要な点ではなく、記事を頼むときのプロンプトやスキルの改善だ、と念を押している。そのうえで「不足していることを補い必須としていることを依頼に載せたい。一方で不要なものを必須にして作業を縛りたくない」と線を引いた。

下書きの行の多くは、この対話で依頼した人が出した線引きの結論にあたる。

| 下書きの行 | 対話の中の理由 |
| --- | --- |
| 捨てた代替案と理由を書く | 欲しいのは「どういう選択肢を捨てたのか」で、「なぜホスト側のドライバ更新を人間に頼まなかったのか」ではない。前者を是とすると、逆に人間に聞きすぎる |
| 起きた順を骨にし、因果の散文でつなぐ | AI の骨子案の「時系列または論理順」に「論理的に述べるのではなく時系列」と返し、続けて「時系列を強調しすぎると年表的な出力を返してしまう」 |
| 余談は結びのあとに別の章で | 短い余談を個別に挟むより、別の可能性の示唆として最後に章を立てるほうが「うれしいかも」 |
| ペダンティックな分析をしない | 名前を tech-notes、investigation-notes、trial-log から選ぶとき、investigation-notes で「ぺだんてぃっくにならなければよいが」 |
| 依頼を変形してよい | 依頼とその確認結果という体裁をとるため、途中の方針転換を載せるなら完全な依頼文を冒頭に置くと読みにくいため。この二点を理由として一緒に書くとよい |
| 途中の調整は経緯の中に書く | 「完全なトレースは必要ない。知見や実施の再現さえできればよい」 |

依頼した人は、この種の依頼で一番重要なのは再現性とそのための記録だ、とも言っている。また、issue の起点になった answers-under-constraints は、依頼した人にとって「何が書かれているかより、どう書かれているか」の参照だった。

SKILL.md の下書きで理由が付いていたのは、依頼を変形してよいという行だけだった。Q&A は名前の選び方やドライバ更新の線引きを説明しているが、どの行がどの発言の結論なのか、「うれしいかも」くらいの好みなのか必須なのかは、対話の側にしか書かれていない。

4 節の並びそのものは、11-05 の [記事を書くスキルを考えて、fork で書き比べた](2026-11-05-skill-for-new-articles.md) の結果ともつながっている。そこで試した write-slops-threads では、二つの試作が自分の間違いの振り返りで終わって当初の問いへの答えが抜け、筋を一本に絞る指定で有用な余談まで落ちた。依頼した人がそのとき示した形（本筋、余談、最後にまとめ）と下書きの並びはほぼ同じで、三つの試作は並びを変えていない。

## 下書きだけを渡すと、理由の見えない行が削られ、必須が増えた

三つの試作は、最初は issue のコメントと直近の記事だけを材料に作った。コメントに付いていた Google Drive と AI Studio のリンクは認証が要り、Claude Code も Codex も開いていない。

Claude Code の最初の版は、下書きの各行に直近の記事から理由を探し、見つからない行を削った。「Keep the tone matter-of-fact」は、[記事を書く目的で分けて、依頼をテンプレートにする](2026-11-05-slops-use-case-templates.md) に、文体の条件に応えるために観察ではない文が入ったことが表になっていたので、同じことを起こすと考えて削り、隣のペダンティックの禁止も一緒に落とした。依頼を変形してよいという許可は残したが、付いていた二つの理由は落とした。

同じ版は、理由を見つけた行をそれぞれ必須に足した。計測値に回数やウォームかどうかの条件を付けさせたのは、answers-under-constraints で cu128 の固定が「重要」という無条件の規則として残り、Piper の RTF 0.13 が測り直すと 0.07 だった件から。作業したセッションで書くこと、余談の各項目に確かめたかどうかを付けること、捨てた道は「For every dropped path」で書くこと、原因が変えられない場所にあったならどこにあったかを書くこと、も足した。

Codex の最初の版も、同じ向きに増やしていた。重要な判断ごとに、観測、採用案、代替案、見送った理由、結果を取り出させ、余談には未検証であることと試す条件を付けさせ、冒頭で要約するのは初期の依頼に限った。

対話を受け取ったあと、二つの試作は自分で増やした分をこう評価している。Claude Code は、計測値の細目は TTS の具体例に寄りすぎで、answers-under-constraints は書かれ方の参照だった、余談の確認済みラベルは write-slops 本体の「試したことと試していないことを区別する」と重なる、作業したセッションで書くことはスキルを読み込んだエージェントの側では守りようがない、とした。原因の場所を書かせる行は、書き方次第で「人間に頼むべきだった」に滑る、とも書いている。Codex は、判断ごとに取り出させる指定が判断を網羅する帳票に寄る、とした。

## 対話を渡すと、三つの試作で揃うところと割れるところが見えた

三つの試作は、下書きの元になった対話を受け取ってスキルを直した。Claude Code の総評によれば、三つとも、4 節の並び、年表にしない因果の散文、反省で締めないこと、回避策を条件付きで書くことは揃っている。Claude Code と Codex は、依頼を書き直してよいこと、完全なトレースは要らないこと、検討していない候補を並べて網羅的に見せないこと、確認を挟まずに進めたことを欠点にしないこと、でも揃った。

候補を並べないことについては、対話の中のシミュレーションが一つの材料になった。シミュレーションは、事後に代替案を書く前提があれば、エージェントは作業中に除外した選択肢をメモに残すようになる、と予測していた。Claude Code は、このスキルは書く段階で読み込まれるので作業中の振る舞いは変えられず、起こりうるのは代替案の節を埋めるために後から候補を並べるほうだ、と読んだ。シミュレーションが捨てた案に挙げた VOICEVOX や Fish Speech は、対話に貼られた Grok の候補リストにあったものだった。Codex は、記録に理由がなければ不明と書き、欠けた判断を後付けで埋めない、と指定した。

割れたのは、同じ発言をどう読むかだった。Claude Code の総評の表を縮めると次のようになる。

| | Claude Code | Codex | Gemini |
| --- | --- | --- | --- |
| ペダンティックの禁止 | 名前の副作用への手当てと読み、理由ごと戻した | 名前を exploration に変え、一般論や鋭さの披露の禁止は残した | 語り口の多様性を損なうとして外し、「意図と環境の具体的な摩擦」に焦点を置いた |
| 残す代替案 | 実際に検討して進路を変えたもの | 結果の条件・限界・再現に関係するもの。失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分ける | 候補が退けられるたびに、迂回を強いた環境の制約を書く |
| 途中の変更 | 次の手順を変えたもの | 選択か、結果の評価のしかたを変えたもの。後から加わった条件を最初からあったように書かない | 転換点として書く |
| 依頼を変形してよい理由 | 二つとも書く | 理由は書かず、後から加わった条件の扱いを足す | 理由は外し、答えと対応させる形にまとめる |
| 余談 | 必須 | 任意 | 必須 |
| docs/sketch との分担 | 手順は sketch、どう辿り着いたかは記事 | なし | なし |

ペダンティックの禁止は、Claude Code の総評の言葉で三者三様だった。Gemini の記事は、文体の否定命令を重ねるとモデルごとの語り口の多様性（依頼した人が期待するセレンディピティ）を損なうから、と理由を書いている。対話で依頼した人は、モデルごとの筆致の差のような面白さは「セレンディピティ的な形で取得されるべきもの」と言っており、issue にも、自由に書けという表現自体が命令として機能してほしくない、とある。Claude Code の比較は、それを読めばありうる解釈だとしたうえで、同じ対話からこちらは名前の懸念を読んだ、と書いている。

余談の必須と任意について、統合の初稿は、必須にした Claude 版と Gemini 版は「うれしいかも」を節があることの要求と読み、任意にした GPT 版は置き場所の好みと読んだ、と整理していた。

## 割れたところを比べさせ、その比較から一本を取り出した

依頼した人は、それぞれの試作に、ほかの試作と一対一で比べるよう頼んだ。Claude Code は #139 と #140 との比較と三つの総評を、Codex は #138 と #140 との比較を書いた。一本にするときに使ったのは、この比較で互いに指摘されたことだった。

Codex の比較が指摘したのは、Claude Code 版の代替案の基準の弱さだった。「進路を変えたもの」だと、関連する案をすぐ見送ったために進路が変わらなかった場合、その案が落ちる。Claude Code はこれを認め、TTS の件で言えば、ホスト側のドライバ更新は範囲外としてすぐ外れた案で進路は変えていないが、追試の記事はまさにその案から始まった、と書いた。統合版は二つの基準を「または」でつなぎ、進路を変えた案に加えて、結果の条件・限界・再現を説明する案も残す。

実線の枠が GPT 版の基準、その内側の破線の枠が Claude 版の基準で、点線の枠はどちらにも入らない案。案は対話のシミュレーションと Grok の候補リストから取ったもので、位置は二つの基準で読んだときの位置にすぎず、実際に記事を書かせて確かめたものではない。点線の枠の案を後から並べないための歯止めは、Claude 版と GPT 版の両方にあり、統合版にも残っている。

同じ比較の中で Codex は、すべての条項を足すと、両方の調整で減らそうとした義務を再び増やす危険がある、統合するならまずその調査で必要な差を選びたい、とも書いていた。Claude Code の比較はこれを受け、GPT 版の「渡す前の確認」や「新しい実験や公開を許可しない」のような作業手順の項目は入れないほうがよい、とした。

統合の最初の版は、Claude Code の総評の推奨に沿って、GPT 版から代替案の基準と三分類、後から加わった条件を最初からあったように書かないこと、結果の評価のしかたを変えた変更も残すこと、回避策を既定で暫定扱いにしないこと、余談を任意にすること、を取り込んだ。このとき、推奨に入っていない GPT 版の文も一緒に持ち込んでいた。表で条件を比べてよいこと、関係のない条件は書かないこと、一度の成功を互換性の保証や最善の解にしないこと、部分的な結果や否定的な結果も答えになること、余談の節にしか答えがない状態にしないこと。三つの試作の記事を全部読んだあと、この五つは Codex の警告にあたるとして外した。余談だけに答えがある状態を避ける文は、GPT 版では渡す前の確認の一項目だった。部分的な結果の文は Claude 版の「答えられていない部分があればどこかを書く」とほぼ重なり、互換性の保証の文は既定で暫定扱いにしないことの言い足しだった。

Gemini 版から取り込んだ文はない。Claude Code の比較と Codex の比較は、どちらも Gemini 版の代替案の書き方に二つの穴を見ていた。「たびに」は網羅を求める書き方で、後から候補を並べることへの歯止めがない。理由を環境の制約に限っているので、範囲外だった、時間がなかった、測って外した、のような判断による見送りの置き場がない。一方で Codex の比較は、冒頭の「意図と環境の具体的な摩擦に焦点を当てる」を入口として分かりやすいと評価し、Claude Code の総評は、Gemini 版から文面として取り込みたいものは短さ以外にない、とした。この一文は Gemini 版がペダンティックの禁止を外したときに代わりに置いたもので、禁止を残すなら役割が重なる。

比較で割れたままだった点は、依頼した人に聞いた。ペダンティックの禁止は残す。Gemini 版の摩擦の一文は入れない。三つの試作のスキルは消さず、description を「比較の記録として残した試作。名前で指定されたときだけ使う」に変えて、スキル一覧に調査記事用のスキルが四つ並んでも、どれが選ばれるかが曖昧にならないようにする。Codex と Gemini が足していた `AGENTS.md` からの案内は、一度は統合版を既定として案内する形で入れたが、技術的な備忘録を書かせたいときは依頼した人がスキルを直接指定するので要らない、と言われて外した。`AGENTS.md` には、用途ごとの派生スキル（`write-slops-*`）があり、名前で指定されたときだけ使う、という一文だけが残っている。

統合版を対話と突き合わせると、余談の扱いはこうなった。対話には「うれしいかも」と「不要なものを必須にして作業を縛りたくない」の両方があるので、統合版は余談を任意のまま、置くなら結びのあと、とした。ペダンティックの禁止は名前の懸念から、依頼を変形してよい理由の二点は依頼した人が挙げたものとして、Claude 版から引き継いでいる。

## できたスキル

スキルは [.agents/skills/write-slops-investigation-note/SKILL.md](../.agents/skills/write-slops-investigation-note/SKILL.md) にあり、`.claude/skills` は `.agents/skills` へのシンボリックリンクなので Claude Code からも同じものが見える。試作に合わせて `agents/openai.yaml` も付けた。Claude 版からの差分は次のとおり。

| 項目 | Claude 版 | 統合版 | 出どころ |
| --- | --- | --- | --- |
| 残す代替案 | 実際に検討して進路を変えたもの | それに加えて、結果の条件・限界・再現を説明するもの | Codex の比較、GPT 版 |
| 代替案の区別 | なし | 失敗した試行、検討したが実行しなかった案、あとで気づいた可能性を分ける | GPT 版 |
| 記録にない理由 | 補わない | 補わず、不明と書く | GPT 版 |
| 回避策 | 条件付きで書く | 条件付きで書き、既定では暫定扱いにしない | GPT 版 |
| 途中の変更 | 次にしたことを変えたもの | 結果の判断のしかたを変えたものも。後から加わった条件を最初からあったように書かない | GPT 版 |
| 余談 | 必須 | 任意 | GPT 版、対話 |
| ペダンティックの禁止 | あり | あり | 対話、依頼した人の判断 |
| docs/sketch との分担 | あり | あり | Claude 版 |
| 案内 | description だけ | `AGENTS.md` は派生スキルがあることだけを書き、使うのは名前で指定されたとき | 依頼した人の判断 |

三つの試作の記事と同じく、このスキルも題材がスキル作りの記事でしか使われておらず、環境構築や追試のあとの記事では試していない。この記事も統合版の節の順で書いたが、経緯にあたる部分の「捨てた道と理由」は、権限やバージョンではなく、比較の指摘と依頼した人の答えになっている。

## 余談

三つの試作の記事には、本筋には入らないが残しておきたいことがいくつかあった。

図の失敗は二つあった。Gemini の記事の図は、4 節の名前と除外する書き方を箱に入れ、矢印で並べたものだった。Claude Code の比較も Codex の比較も、write-slops が避けるよう書いている「文を箱にして並べた図」にあたると見ている。Codex の比較は、SVG の静的検査を通ることと、図が説明に加える価値は別の確認事項だ、と書いた。この図を作る途中で、svg-gen にラベルを `\n` 入りの文字列で渡して幅の計算が崩れ、`labelLines` の配列に直した、という失敗もあった。Codex の図はスキルの実体とリンクの関係を描いたもので、幅約 680 の横長の版は検査も原寸の PNG も通ったが、ブログの狭い画面では縮小されてラベルが読めなくなり、縦向きの小さな配置に変えた。この件は [SVG の落とし穴](2026-10-27-writing-slops.md/03-svg-pitfalls.md) に残っている。Codex は自分の図について、ファイル配置を確かめる助けにはなるが執筆指示の良し悪しの証拠ではないので順位付けに使わない、と書き、Claude Code もそれに同意した。Claude Code の版は図を試しておらず、試さなかった理由も書いていない。

リンクの構成は、試作ごとに選び方が違った。Gemini は、`.agents/skills` を丸ごと `.claude/skills` へのリンクにする案と、スキルごとにリンクを置く案を比べ、ツールによってディレクトリリンクの走査が異なる場合があるとして後者を選んだ。Claude Code の比較は、この段落を、捨てた代替案とその理由がいちばん素直に出ているところとして挙げたうえで、理由は一般論で試した形跡はない、とした。Codex の比較は、個別の入口もディレクトリのシンボリックリンクなので、それだけでは堅牢性は確かめられない、とした。Codex 自身は、グローバルへのインストールではそのマシンだけの設定になり、コピーでは編集対象が増えるので、リポジトリ内の相対リンクにした。今は向きが逆になり、`.agents/skills` が実体で、`.claude/skills` がそこへのリンクになっている。

語り口の差は、issue #133 で依頼した人が楽しみたいと言っていたものに近い形で出た。Claude Code の総評は、Claude Code は日記に近く何をなぜ直したかを順に書き、Codex は確かめた範囲と確かめていない範囲を何度も区切って PR の説明に近い慎重さになり、Gemini はスキルの 4 節を見出しに写して「真に必要としているのは」「こそが」のような言い切りが多い、と書いた。どこまでがスキルのせいで、どこからが書き手の癖なのかは、この比較では分けていない。

書く段階で読み込むスキルでは、捨てた選択肢の材料が作業中に残っていることまでは保証できない、という点は Claude Code と Codex の両方が書いていた。調査の依頼の側で「捨てた選択肢を sketch に一行ずつ残す」と頼めば残るが、作業を縛る側の指定になる。直近の技術調査だった [PR #136](https://github.com/podhmo/html-sandbox/pull/136)（WSL2 の perf の bind mount で `apt upgrade` が失敗した件）は Devin のセッションで行われ、記事はない。三つの試作の総評はそろって、次に技術調査をしたセッションから fork を起こし、同じ材料から別々のスキルで書かせて比べる方法を挙げていた。見るのは、最初の問いへの答え、関係する代替案、条件の変化が残るか、判断の経緯を作っていないか。図に置いたドライバ更新のような案が実際に残るかどうかも、そこで分かる。
