# 技術探索後の記事を書くスキルを作り、元の対話から指定を絞り直した

このbundleの本文はスキル作成と調整の経緯である。比較は1対1ごとに記事を分けた。

- [Codex対Claudeの比較と補足総評](#01-codex-comparisonmd): PR #138との比較。初稿への評価と改稿後の補足を区別している。
- [Codex対Geminiの比較と総評](#02-codex-vs-geminimd): PR #140との比較。スキル、記事での実践、利用環境と検証の範囲を扱う。

## 依頼と、始めた時点の条件

依頼は、技術的な探索を終えたあとにslopsを書くための特殊化スキルを、既存のwrite-slopsをbaseとして作ることだった。Codexから使うためのリンクを置き、そのスキルで作成の経緯も記事にする。起点は[issue #133のコメント](https://github.com/podhmo/html-sandbox/issues/133#issuecomment-6686188903)で、別エージェントのPRは参照せず、専用worktreeで作業するという条件があった。

最初に読めたのは、コメントに載っていたQ&Aとスキルの下書き、baseの[write-slops](../../.claude/skills/write-slops/SKILL.md)、11月5日の記事群だった。コメント内のDriveやAI Studioの資料は開いていない。元の対話を受け取ったのは、スキルと初稿を作ったあとである。さらに後でPR #138との比較が許可されたため、この記事では、独立に作った段階、対話から調整した段階、比較した段階を分けて記録する。

## コメントから派生スキルを作った

開始時のチェックアウトには、同種のinvestigation-notesというスキルがすでにあった。その実装と付随する記事は読まず、別名の `write-slops-exploration-notes` を作った。作業は `codex/exploration-slops` ブランチで進めた。PRを作る際に開始時のHEADへ他の作業のコミットが含まれていると分かったため、自分のコミットだけを `origin/main` 上へ載せ直し、[PR #139](https://github.com/podhmo/html-sandbox/pull/139)にした。

baseには、問い・観測・未検証の案・決定の区別、測定値や約束を創作しないこと、記法・図・bundle・表示確認の指定があった。これらを派生側にも写すと、変更に追従する場所が増える。そこで、baseを先に読ませ、派生側には技術探索の記事で何を残すかだけを書いた。

記事の骨格は、依頼と前提、試行と判断の経緯、依頼への答え、最後に余談、という順にした。[目的別テンプレートの記事](../2026-11-05-slops-use-case-templates.md)では、語り口を調整するために中身に寄与しない文を足したことが報告されている。今回は感情や人格の指定を加えず、残す内容を決める方に寄せた。

一方、[forkで書き比べた記事](../2026-11-05-skill-for-new-articles.md)には、二つの試作記事が自己の間違いを振り返って終わり、当初求められた答えが抜けたことと、筋を一本に絞る指定で有用な余談まで落ちたことが書かれていた。その報告を受け、結びには依頼への答えを置き、余談はそのあとに残すよう指定した。時系列をコマンド一覧にせず、観測から選択と結果へつながる散文にする方針も、指定コメントから引き継いだ。

初版では、重要な判断ごとに観測、採用案、代替案、見送った理由、結果を取り出すよう求めた。また、回避策の条件をその段落のそばに書かせた。[TTSの記事](../2026-11-05-answers-under-constraints.md)や[issue #128](https://github.com/podhmo/html-sandbox/issues/128)、[調査メモ](../../docs/sketch/ja/tts-wsl2.md)を読み、環境表に条件があっても、手順だけ抜き出すと無条件の規則として伝わる問題を材料にしていた。ただし、このセッションでTTSを動かしたり、現在の互換性を確かめたりはしていない。

## 元の対話を受け取り、必須にする範囲を絞った

スキルと初稿を作ったあと、依頼した人から、issueコメントの元になった対話を渡された。そこでは、AIの整理に対して何度か修正が入っていた。欲しいのは「人間にドライバ更新を頼むべきだった」という反省ではなく、記事を読むと捨てられた代替案が分かることだった。調査を自律的に進めること自体は悪くなく、そのあとで見返せる記事にする。完全なトレースは不要で、知見や実施を再現できればよい、とされていた。

この対話から、初版の「重要な判断ごとに取り出す」は、判断を網羅する帳票へ寄る可能性があると考えた。そこで、残す基準を「結果の成立条件、限界、追試を理解するために必要な選択と代替案」へ変えた。すべての候補を列挙することは求めない。失敗した試行、検討したが実行しなかった案、あとで気づいた可能性の区別は残した。[出どころへの正直さを扱った記事](../2026-11-05-good-slops-for-requester.md)とも対応するが、ここで必要なのは、欠けた判断を後付けで埋めないことである。記録に理由がなければ不明と書く。

回避策の扱いでも、条件付きであることと暫定解であることを分けた。ある環境に依存していても、その条件では適切な最終解かもしれない。必要なのは、それを選んだ観測と適用条件であり、すべてを暫定解と呼ぶことではない。そのため、条件を添える指示は保ち、環境依存の選択を一律に暫定とは扱わないと明記した。

### 冒頭でまとめる依頼と、途中で変わった条件

初版は「初期の依頼を要約する」と書いていた。しかし対話では、途中の調整も含めて一つの依頼としてまとめてよいとされている。冒頭に完全な依頼文を置き、そのあとで修正履歴を重ねる必要はない。

そこで、冒頭には記事が答える問いとして依頼全体を再構成してよい、と変えた。同時に、選択や結果の評価を変えた要件は、その時点の経緯にも残すことにした。後から加わった条件を、最初から分かっていたようには書かない。次のコマンドが変わらなくても、結果の評価方法が変わることはあるため、手順の変更だけに対象を絞っていない。

余談の指定も狭かった。初版は未検証と明記させ、試す条件を付けるよう求めていたが、本筋に入らなかった確認済みの発見も余談になりうる。調整後は、確認済みの副産物、推測、未検証案を区別して置けるようにし、材料がなければ節を省くことにした。途中の誤りや訂正も、結果へ至る経緯として必要なら書いてよい。結びを自己評価で置き換えないことは、その経緯まで消すことではない。

この調整で、四部の順序と因果でつなぐ散文は維持し、網羅的な判断記録、初期プロンプトへの限定、未検証案だけの余談を必須とする形は外した。文体を揃える形容詞や、新たな確認義務は足していない。

## 比較を許可されたあとでPR #138を読んだ

その後、依頼した人から[PR #138](https://github.com/podhmo/html-sandbox/pull/138)を提示され、比較と総評をCodexからのコメントとしてbundleへ追加するよう依頼された。この時点で初めて、相手のスキルと記事を読んだ。比較はPR #138の `5c08749` と、こちらの `a2208c7` に固定し、[比較コメント](#01-codex-comparisonmd)へまとめた。[rawファイル](01-codex-comparison.md)からも読める。

両方とも、捨てた案を創作せず、選択に条件を添え、依頼への答えで本筋を閉じる点は共通していた。PR #138には、手順と事実はdocs/sketch、そこへ辿り着く経緯は記事という分担と、短い記事なら冒頭と経緯をまとめてよい指定がある。こちらは、依頼全体の再構成や評価基準の変更、環境依存でも必ずしも暫定ではない選択を詳しく扱っている。これらが出力にどう効くかは、比較実験では確かめていない。

比較時点の記事については、PR #138の方がスキルの設計経緯を追いやすいと判断した。相手の記事には元の対話を受けた二回目の調整まで入っていたが、こちらは初稿を残し、後から比較コメントを添えただけだった。本文を日本語にする依頼にも翻訳で対応し、その差は残った。そこで「記事も書き直してほしい」と改めて依頼され、今読んでいる本文を調整後スキルに沿って書き直した。初版の説明に追記を足す形をやめ、対話で何を変え、何を必須から外したかを経緯に組み込んだ。比較コメントは改稿前の対象への評価として残している。

その改稿後、GeminiによるPR #140も評価するよう依頼された。今回は1対1で考えるという指定に合わせ、Codex対Claudeの記事へ三者の比較表を足す形は取らず、Codex対Geminiを別メンバーにした。Claude比較には改稿後の補足総評を加え、以前の初稿に対する評価が現在の本文へそのまま適用されないようにした。

## できたスキルと、確認できた範囲

できたものは[write-slops-exploration-notes](../../.claude/skills/write-slops-exploration-notes/SKILL.md)である。技術探索後に、依頼への結果と、それを理解・再現するのに必要な選択を残す。成立条件と関連する代替案を示す一方、会話・コマンド・判断の完全な履歴は求めない。冒頭で依頼をまとめ直しても、途中の重要な条件変更を消さず、結びでは依頼への答えを示す。記法・図・bundleの扱いはbaseに任せている。

スキルの形式検査は、システムPythonにPyYAMLがなかったため、その依存だけを入れた分離したuv環境で実行し、通過した。Codex用の二つのリンクは実体と一致し、リンク経由でもbaseの相対参照が解決することを確認した。図は生成・検査し、狭いブラウザ表示でも修正後の配置を確認した。記事のbundle化と日本語化の段階では `make test-go` が通り、Goサーバーの結合ページ、メンバーの順序、raw取得を確認している。ブラウザには「Rendered with Wasm」と表示されていた。MoonBit全体やTypeScriptレンダラーの検査をしたという意味ではない。

今回の改稿もこの調整後スキルで行っているが、題材は引き続き執筆スキルを作る作業である。新しい技術環境の調査を終えた場面での有効性や、他モデルでの品質向上を確かめたわけではない。依頼されたスキル、Codex用リンク、そのスキルによる経緯の記事と比較コメントは揃ったが、実際の技術調査後にも必要な代替案をうまく選べるかは未確認である。

## 余談: 書く段階の指示で残せないもの

PR #138の記事には、書くときに読み込むスキルでは、それ以前の作業中に代替案が記録されたことまでは保証できない、という指摘があった。今回の「理由がなければ不明と書く」も、その不足を埋めるものではない。作業中のメモを残す依頼を別に加える方法は考えられるが、記録の義務が増える。ここでは調査時の運用までは変えていない。

以前の記事で使われたセッションのforkは、同じ技術作業の文脈から二つのスキルで書き比べる方法になりそうだ。ただし今回行ったのは指示文と既存記事の比較で、その実験ではない。試すなら、答えと必要な代替案が残るかに加え、情報がないところで判断履歴を創作していないかも見る必要がある。
