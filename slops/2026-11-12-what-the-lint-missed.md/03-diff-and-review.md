適用したのはベースラインの文の推敲パスで、yomiyasu lint パスは含めていない。初稿を初読の読み手として読み、解釈が分かれる・読みが停まる文を抜き出して書き直した。主張・重み・断定の強さ・文の役割は変えない、という制約の下での変更。

### 変えた文

1. 問い「そこで issue #169 として、yomiyasu の lint を slops の記事全体に適用してみた。」

   「として」の係り方が曖昧で、issue を名乗るのか作業の扱いを示すのかが読み分かれる。

   → 「issue #169 では、yomiyasu の lint を slops の記事全体に適用してみた。」

2. 方法「この表記自体は並行して行った別の作業（PR #170）で、本文を書いたコミットの `Co-Authored-By` トレーラーと PR 本文の 🤖 マーカーから推定したもの。」

   「別の作業で」という切断した接続詞と、「推定したもの」という終止が、表記を付けた作業と推定の根拠を一線でつなげて読みにくい。

   → 「この表記は別の作業（PR #170）で全記事に付けたもので、値は本文を書いたコミットの `Co-Authored-By` トレーラーと PR 本文の 🤖 マーカーから推定している。」

3. 方法「帰属が確定できない 2 記事は「不明」として別集計にした（後で中身から Claude Code おそらくと判断されたが、集計時の区分はそのままにしている）。」

   括弧の中身は補足ではなく後続の事実で、文を 2 つに分けるべき内容。

   → 「帰属が確定できない 2 記事は「不明」として別集計にした。この 2 記事は後で中身から Claude Code おそらくと判断されたが、集計時の区分はそのままにしている。」

4. 方法「まず全規則を含めた集計、次に「機械的に変換できる不備」（…）と「直接の訳語が分かる語」（…）の 9 規則を除外した再集計。」

   「集計」「再集計」が体言止めで、何をしたのかの述語が文の外に置かれている。

   → 「最初に全規則を含めて集計し、次に「機械的に変換できる不備」（読点・ダッシュ・コロン・絵文字・箇条書き率）と「直接の訳語が分かる語」（calque・translated_term・katakana_term）の 9 規則を除外して再集計した。」

5. 観察「前の10メンバー集計で見えた差（1.46 vs 2.57）は全集では消えた。」

   「前の」はこの記事内に先行説明がない参照で、issue の最初の集計を指す。

   → 「この issue の最初に行った 10 メンバー対象の集計で見えた差（1.46 vs 2.57）は、全集では消えた。」

6. 観察「warn の大半は Devin の機械的書式。」

   「機械的書式」は圧縮しすぎで、書式の不備なのか書式そのものなのかが一瞬ぶれる。

   → 「warn の大半は Devin の機械的な書式不備だった。」

7. 届かなかった層「基準 7 項目 → 兆候 7 項目 → しない方がよい 9 項目という番号つき分類体系の再帰と番号による相互参照、全段落が同じトーンのレジスター一様性。」

   矢印は列挙なのか順序なのかが分かれ、「レジスター一様性」は圧縮名詞で名詞句列の終わりが読み取りにくい。

   → 「基準 7 項目から兆候 7 項目、しない方がよい 9 項目へと続く番号つき分類体系の再帰と番号による相互参照、全段落が同じトーンで書かれるレジスターの一様さ。」

8. 届かなかった層「読点そのものが読みにくさなのではなく、「読点で節をつなぐ長い文の組み立て」という組み立て方の症状の末端を見ているにすぎない。」

   「組み立て」が 2 回出て修飾が入れ子になり、何の末端なのかが追いにくい。

   → 「読点そのものが読みにくさなのではなく、長い文を読点でつなぐ組み立てが生む症状の末端を拾っているにすぎない。」

9. 届かなかった層「行為者が格を外される形」

   「格を外される」は「格から外される」の誤り寄りの表現で、行為者が動詞の格枠から外れる意が取りにくい。

   → 「行為者が格から外される形」

10. 決めたこと「「直したい層」の選定と slop_vocabulary の許容判断は依頼者の評価による。」

    「による」単独の終止は「によるものだ」「に基づく」のほうが述語として成立する。

    → 「「直したい層」の選定と slop_vocabulary の許容判断は依頼者の評価に基づく。」

11. 決めたこと「語彙リストは持たない方針（kuden の「言葉尻より構造」と同じ立場）で、判定ではなく特徴量を集める設計にする。」

    括弧の中身は方針の根拠を示す立場の言明で、文に続けたほうが追いやすい。

    → 「語彙リストは持たない方針で、これは kuden の「言葉尻より構造」と同じ立場だ。判定ではなく特徴量を集める設計にする。」

12. 試していないこと「ツール選定のメモは #172 にある（形態素・係受けの両方を pip だけで取れる GiNZA 系が第一候補、n-best が取れる JUMAN++ 系は意味情報の豊かさで別の強み）。」

    括弧内が長く「別の強み」で体言止めする。

    → 「ツール選定のメモは #172 にある。形態素・係受けの両方を pip だけで取れる GiNZA 系が第一候補で、n-best が取れる JUMAN++ 系は意味情報の豊かさが別の強みになる。」

13. 試していないこと「IdeaLens 型の文書→役割付きアウトライン変換（LLM 判定層）は未検証。」

    括弧で役割を補足するより、文に組み込んだほうが判定層という位置づけが明確。

    → 「IdeaLens 型の文書→役割付きアウトライン変換を LLM 判定層に使う案は未検証。」

### 検討して残した文

- 「執筆者差は候補の量ではなく、規則の層にある。」— 「A ではなく B」の形だが、前半の予想を訂正する対比で否定が意味を担う。negative_parallelism の例としてもそのまま残す。
- 「読点そのものが読みにくさなのではなく、…」— 同じく訂正の否定。8 で後半を書き直してもこの対比構造は残した。
- 「判定ではなく特徴量を集める設計にする。」— issue の設計方針そのものの対比。
- 「slop_vocabulary（「引き継ぎ装置」「品質ゲート」「温度感」「手触り」など 11 件 vs Claude 2 件）と metaphor_verb（「性質が効いてくる」「時間を溶かす」など 3 件 vs 0 件）。」— 括弧内は用語例と件数の対応表で、補足説明ではなくデータ本体。読みにくさの実感がなかったので残した。
- 「集計は 2 段で行った。」直後の括弧 2 つは、それぞれのカテゴリに付く内訳の列挙で、離れた補足ではないので残した。

### 総評

変更は 13 箇所で、内容の追加・削除はない。効いたのは主に 2 種類だった。1 つは係り先の曖昧さの解消（1・4・7・8）で、とくに「そこで issue #169 として」と「組み立て方の症状の末端」は初読で確かに一度読み返す文だった。もう 1 つは括弧の解体（3・11・12・13）で、文の途中に別の事実を挟む形を、前後の文に分けた形に直している。

残した判断のうち対比の否定は、この記事のテーマである negative_parallelism をそのまま踏んでいる。規則を機械的に適用すると訂正の否定まで消えて主張が弱くなるので、「候補であって修正命令ではない」という lint の扱い方と一致した結果になった。

全体として、初稿は事実と区別の骨格は保てていたが、圧縮した名詞句と括弧が読点に負荷を移していた。refine-slops のパスは内容を変えずにその負荷を文の構造へ戻す方向に働いている。
