# 私にとってのブログとは何であるか？（仮）

2026-10-26 時点のリポジトリと、その読み取りについての本人の説明を材料にした、記事を書くための仮レポート。AI が構成を整理しており、この原稿全体を本人が自分の文章として採用した段階ではない。聞き取りの回答は転載せず、記事の論点として組み直している。

「普通の人」は統計的な分類ではなく、完成した読み物を届けることを主目的とするブログとの比較用の人物像とする。実装の有無と本人の優先順位は分けて考える。[根拠と留保](evidence.md)には、コードで確認できる仕組みと、意図について読み直した点を記録した。

## 記事の中心に置くこと

- 第一の用途は自分用の記録。読む相手としては現在の自分が先にいて、その先に将来の自分、知っている人、それ以外の人がいる。AI を主な読者に据える必要はない。
- 書くのは、すでにある答えを保管するためだけではない。説明してみることで考えを進め、その時点で言えるところまでを、小さな区切りで残していく。
- 後から読んで分かると嬉しいのは、判断がどう変わったか。最初に置いた制約と、それを見直すほど必要だった機能が両方残ると、自分の選択を追い直せる。
- 自分向けの記録でも、人にある一節を示したくなることはある。細かい permalink は大規模な発信のためというより、普段の会話から必要な箇所へ案内するための道具になる。
- 書く負担を増やさないことが優先される。自作する楽しさはあるが、作った技術や試したことのすべてを記事にするわけではない。

記事全体の方向は「自分用の記録を、考えの更新が分かる形で書く」。初稿で置いた「続きを始められる場所」は、その結果として生まれる連続性を説明する言葉として残せる。ただし、引き継ぎのための仕組みを作ることが最初から主目的だった、とまでは強めない。

## 普遍的に必要となる要素

ここでの「普遍的」は機能の必須リストではなく、自分向けの記録でも他人向けの解説でも、文章を使うために必要となる土台を指す。

- 意味が読み取れること。どういう場面の何について書いているのかが分かることが、文章を一旦区切れる目安になる。
- 読む・書くための負担が過大でないこと。スマートフォンでの読みやすさ、日本語の表示、長いコードや表が本文を崩さないこともここに含まれる。
- どの時点の話か分かること。タイトルや日付だけでなく、そのときの前提と、後に変えた判断を区別できること。
- 必要な箇所に戻れること。ページだけでなく、会話で示したい見出しに直接たどり着けること。現在の自動見出し ID は改題で変わりうるので、不変の識別子とまでは言わない。
- 説明の用途に見合う確かさがあること。誰にでも使える手順として出すなら、動作の裏付けが要る。個人的な問いの記録なら、何を知ろうとしていたのかを読み取れることに別の価値がある。
- 書かれている判断が誰のものか分かること。AI が整えた説明と、本人が自分の意見として採用した内容を、文章の滑らかさだけで同一視しない。

## 通常の人が望みそうだが、私には優先度が低いもの

- 画像を簡単に貼れること。本文のための一般的な画像機能は、かなり後の課題として扱う。SVG の実験や既存の表示経路があることと、画像の投稿機能を近く充実させたいことは別である。
- シンタックスハイライト。コードに色を付けることより、内容が読めて、取得やコピーができることを先に置いている。
- Markdown の広い互換性。自作しているのは、少ない記法でどこまで用が足りるかも試したいため。既存の Markdown の全機能を揃えることは、その問いへの答えにならない。
- 見た目を独自に作り込むこと。既存の CSS を使い、読みにくいところを調整する形がある。これは実装から読める傾向であり、本人が装飾全般を嫌うとまでは言わない。
- 全投稿を、同じ完成度や同じ密度に整えてから出すこと。`posts` と、途中の到達点を記録する `slops`・`docs` には、異なる区切り方があってよい。

管理画面、検索、タグ、集客、収益化などは、機能の不在から低優先度と決めない。特に入稿手段は、既存方式を守ることより書く手間を減らせるかが問題になる。

## 私が望むが、普通の人には優先度が低そうなもの

- 会話の中で一部分を指定できるリンク。Slack や Discord で話している内容に対応する箇所を渡せればよい。自分用の備忘録と、知人への共有は両立する。
- 判断が更新された経緯。何を避けたかったのか、その後どの不便を解消するために方針を変えたのかが、後から分かる記録。
- 主となる文章と、その外側に置く補足を一緒に保管できること。別の説明、もう一つの見解、本文を短くするために外した話を、主本文に混ぜずに置きたい。
- 同じ題材を異なる形で説明したものを並べられること。一つの説明に統合するより、複数の読み方を残した方が役に立つ場合がある。
- 内容を原文として取得できること。Markdown のダウンロードや個別ファイルの取得は、画面で読む以外にも扱える仕組みとしてすでにある。導入の動機をすべて AI 向けと説明する必要はない。
- 自分の考えとの距離に応じて、文章の置き場所と量を分けられること。生成された記録をすべて自分の意見として扱わず、どの文章をどの程度届けるか調整したい。

設計メモや TODO の配信、プレビュー、実験コードの保管は、これらと同じ強さの「ブログ観」として並べすぎない。それぞれに、もっと日常的で小さい理由がある。

## 書き手が AI の場合と、人間の場合

手入力の割合で区切るより、文章のどこを誰が決めているかを見る。本人が手放したくないのは題材を生む問いと、自分の文章として出すときの語り方である。`posts` では、書かれている判断や今後の行動まで自分のものとして扱えるかを確認する必要がある。

| 観点 | AI に担わせたいこと | 人間が持つ部分 |
| --- | --- | --- |
| 題材 | 調べた状況や試した結果を整理する | 何を確かめたいのかを決める |
| 実験の記録 | 当初の予定、実際に起きたこと、予定外の事情、途中の判断を残す | どの問いに進むか、結果をどう受け止めるかを選ぶ |
| 語り方 | 説明の案や異なる表現を用意する | 自分が話すときの調子に合うかを判断する |
| 主張と行動 | 資料にある事実と提案を区別する | 書かれた方針や予定を自分のものとして認められるかを確認する |
| 区切り | その時点の状況が伝わる記録を作る | `posts` として一つの文章にまとめるか、経過の記録として置くかを選ぶ |

- `slops` と `posts` の違いは、生成の有無だけでは説明しきれない。本人の考えや語り方との近さ、投稿が流れてくる量の調整という役割もある。
- AI が書いた文章でも、自分の判断として人に勧められるなら、自分の記事に近づく。手を入れた文字数だけで決まるものではない。
- 反対に、実行するつもりのない予定を AI が書き足したり、本人が使わない調子で言い切ったりすれば、そのまま `posts` として完成させられない。
- `slops` や `docs` は、実験のある時点を示す記録として続いていく。最終結論を必ず用意するより、用途や状況が伝わる程度に意味を通すことが一区切りになる。
- AI に期待する中心は、主要な読者になることより、プロトタイプや spike の経過を記録すること。計画通りだった部分だけに整えると、残したい判断が消えてしまう。

このバンドルも、本人から得た説明を材料に AI が構成した原稿である。聞き取りができたことと、最終的な文章の語り口や主張を本人が引き受けたことは分けて扱う。

## docs と TODO.md は何をするためにあるのか

- `docs` は設計や探索の記録、`TODO.md` は着手する作業、`TODO-archive.md` は完了項目の保存先、という運用上の役割がある。
- 文書に残る理由や制約と、TODO に残る次の作業は、状況を読む手掛かりになる。ただし、読者に制作の裏側を開示することを配信の主目的として説明しない。
- ブログから読めるようにした直接の理由は、書き手自身が同じ画面で読める方が楽なこと。確認のたびに GitHub に移動する手間を省ければよい。
- 記事とは別に、より細かな時点の記録を置ける。`slops` と同様、`docs` にも最終版だけを置く必要はない。
- 文書は当時の判断も含むため、現在の実装と一致するとは限らない。変化の記録として読むことと、今使える機能を調べることは区別する。

## 余興: 普通ならこうする。しかしこのリポジトリはこうなっている

比較したいのは、ブログの機能だけが欲しい場合の近道と、この場所で試している問いとの違い。自作を続けること自体を信念にはしない。必要なことが Gist で足りるなら、それでよい。

| 手早く用を済ませるなら | このリポジトリで試していること | そこで確かめたいこと |
| --- | --- | --- |
| 既存の Markdown パーサーを使う | 小さなパーサーを作り、必要な記法から扱う | 標準ライブラリと小さい機能の組み合わせで、どこまで暮らせるか |
| Workers 向けに TypeScript で書く | TinyGo や MoonBit の Wasm でも動かす | Workers の仕組み、MoonBit の出力の小ささ、実行環境の制約 |
| 制約に当たったら既存の構成へ戻す | コーディングエージェントと受け渡し方などを探る | その制約をエージェントが解けるか |
| 好きな技術だけで作り続ける | 実用性を比べるための TypeScript 版も置く | 素直に作った場合に、どれだけ楽になるか |
| 一つの文章へ補足を全部織り込む | 本文と補足・別解をバンドルに分けて置く | 本文の範囲を保ちながら、関連する説明も残せるか |
| 開発メモは GitHub で読む | docs と TODO をブログでも読む | 読みたいものを確認する際の画面移動を減らせるか |
| 汎用の Markdown プレビューで済ませる | 自作の小さな処理系を `/preview` で試す | AI の出力などを当てて、不足や崩れを直す必要があるか手軽に判断できるか |
| 実験のコードを常に最新の形へ整える | 記事に対応する時点の実験も置いておく | その記事が扱っていた状態を残せるか |

技術的に面白かったことと、ブログに書きたいことは一致しない。実験が増えるほど記事も増える、という循環を当然とはしない。楽しさが執筆の手軽さを損なうなら、書きやすさの方を優先する。

## 下書きの骨子

### 導入: 自分用なのに、細かなリンクが欲しくなる

- 読者を広く集める前に、自分が考えを整理して読み返すために書いている、というところから入る。
- それでも会話で一節を渡したくなる。記事の一番上ではなく、話している箇所へ直接案内したい。
- 個人の備忘録と他人への共有は、どちらか一方を選ぶ話ではない、と置く。

### 書くことで、その時点で言えることをはっきりさせる

- 完成した考えを文章に変換するだけではない。書く過程でも考えが動く。
- 途中の迷いをそのまま見せたいというより、小さな到達点ごとに残したい。
- 用途が見える文章なら意味を持つ。`posts` の一篇としての区切りと、`slops`・`docs` の更新途中の記録を分ける。

### 残して嬉しいのは、判断が変わった理由

- 初期に JavaScript を避けた構成と、後に追加した機能を題材にする。
- コピー機能やプレビューが便利であることを説明するだけでなく、それが元の制約より優先された事情に焦点を当てる。
- 何をいつ選んだかが分かると、後から自分の判断を読み直せる。この連続性を、備忘録の価値として書く。

### AI の記録と、自分の記事の間

- AI には、計画から実施までの状況と、予定外の出来事や判断を残してほしい。
- 一方、自分の記事として出すときは、問い、語り方、主張、書かれた予定が自分と合う必要がある。
- AI の生成文かどうかだけでなく、どのくらい自分の意見として扱えるかと、どのくらいの量を流すかで `slops` と `posts` を考える。

### 一つの記事に、全部を詰め込まなくてよい

- 本文と、補足、別の見解、異なる表現を区別したまま一緒に残したい。
- バンドルは再実行可能な実験一式を必ず作るためではなく、主本文を膨らませずに周辺の文章を置くためにも使える。
- docs や TODO の配信も大きな思想にしすぎず、自分が読むときの手間を減らす小さな工夫として添える。

### 余興: ブログで試しているが、ブログのためだけではない

- Workers と MoonBit の Wasm を題材に、サイズや実行環境、エージェントの対応力を調べる。
- tinymarkdown は、小さな構文と標準ライブラリの範囲で十分になる境目を探す題材。
- `/preview` はその境目を確かめる入口、`ts` は実用的な構成と比較するための実装、と位置付ける。
- 楽しい実験がすべて記事になるわけではないし、書くために自作を続ける義務もない。

### 結び: 大きな理念より、自分が書き続けやすいこと

- 備忘録として書き、書いた結果として考えや判断のつながりが残る、という順序に戻る。
- 一般的な手順なら動作の確認が価値を支える。個人的な問いなら、当時どこを疑問に思ったかを残す意味もある。
- 書くための道具は、その手軽さに合わせて選べばよい。使いたい技術のために、書くことを重くしない。

## 本文にするときの編集メモ

- JavaScript を許す判断を、本人が感じた具体的な不便の解消と結び付ける。コードから導入理由を勝手に補わない。
- 画像投稿を遠い課題として扱い、SVG の実験から一般的な画像機能への意欲を推し量らない。
- AI を主要な読者とする説明、公開すること自体を目的とする docs 論、実験保存の大きな理念は中心から外す。
- この骨子を完成稿にする際も、本人の言い回しを聞き取りから貼り合わせるのではなく、本人が採れる文章かを確認する。
