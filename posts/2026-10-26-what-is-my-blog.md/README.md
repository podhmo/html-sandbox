# 私にとってのブログとは何であるか？（仮）

2026-10-26 時点の記事、設計・探索メモ、TODO、Go・MoonBit・TypeScript の実装を材料にした、記事を書くための仮レポート。依頼に従い `posts` に置くが、執筆・整理は AI によるもので、本人が確認・採用した意見ではない。以下の「私」は、これから人間が書く記事の主語として仮置きしている。

「普通の人」は統計的な分類ではなく、完成した読み物を届けることを主目的とするブログとの比較用の人物像とする。機能がないことだけで、本人がそれを欲しくないとは判断しない。明記された好み、コードから確認できる事実、それらからの解釈は、[根拠と留保](evidence.md)に分けて記録した。

## 記事の中心に置けそうな仮説

- ブログは、考えが完成してから清書する場所であると同時に、試したことと判断を保存して、続きを始められるようにする場所でもある。
- 読者には、今の他人だけでなく、数か月後の自分や、次の作業を引き受ける AI も含まれるのではないか。
- 残したい単位は「文章一枚」よりも、「説明、実行可能なコード、図、採らなかった案を束ねた一つの話題」に近い。
- 人間が書く価値は、文字を人間が入力したことだけでなく、何を疑い、何を試し、何を採用し、どこまで確かめたと言えるかを決めることにありそうだ。
- ブログの仕組みを作ること自体も遊びになっている。記事のために道具を作り、その道具を試した結果が次の記事になる。

記事の冒頭に置く一文の候補:

> 私にとってブログは、試行錯誤を、あとで自分も他人も続きを始められる形で置いておく場所なのかもしれない。

「なのかもしれない」を外せるかどうかは、本人の判断に残す。

## 普遍的に必要となる要素

ここでの「普遍的」は、あらゆるブログの必須機能という意味ではなく、書き手が人間でも AI でも、読者に伝えるために必要となる土台を指す。

- 読めること。スマートフォンの狭い画面、日本語の行間や改行、長いコードや表を考慮する。装飾を減らしても、読みやすさまで減らしてよいわけではない。
- 何についての文章か分かること。タイトル、日付、見出し、一覧、短い説明が入口になる。OGP もすでにあるので、共有時の伝わりやすさを捨てているわけではない。
- 必要な箇所に戻れること。記事への URL、見出しへのリンク、関連する記事や根拠へのリンクを持つ。現在の自動見出し ID は改題で変わりうるので、「永遠に不変」とまでは言えない。
- 主張の範囲が分かること。実測と見込み、動いた環境と未確認の環境、その時点の結論と後の追試を混ぜない。過去の成功を現在の動作保証にしない。
- 説明と実物が食い違ったときに確かめ直せること。本文、コード、テスト、実験の条件に戻れる。解説記事の価値を「疎通確認」に見出した既存の人間記事ともつながる。
- 書き続け、直し続けられること。書くたびに過大な操作を要求しない。内容が壊れたら分かり、試行途中の変更で読めなくなったときも原因を追える。

## 通常の人が望みそうだが、私には優先度が低いもの

- 画像を気軽に貼ること。バンドルの記事には、画像表示より複数ファイルを束ねる機能を優先する気持ちが明記されている。ただし現在は SVG 表示があり、PNG/JPEG や画像記法は TODO にある。「画像は要らない」ではなく、実装する順番の話。
- シンタックスハイライト。コードを読む補助にはなるが、まず素のコードが読めて、取得・コピーできればよい、という順序が見える。低優先度であることは記事にも明記されている。
- Markdown の完全な互換性。既存の多機能パーサーを採用する代わりに、小さな構文の集合を自分で扱っている。これは実装上の選択からの解釈で、既存サービスへの不満が本人から語られているわけではない。
- 凝った独自デザイン。pico.css と意味のある HTML 要素を使い、必要な日本語調整などを足している。見た目への無関心とは違い、独自の見た目を一から作ることより、読める状態への到達を優先しているように見える。
- 管理画面での入稿や、ブラウザーだけで完結する公開操作。今はファイルが原本で、`/preview` も保存しない。完成した CMS の操作感より、手元のファイルと実装が直接つながることを選んでいる、という読み方ができる。
- 集客・収益化・反応の可視化を中心にした機能。調査した main のコードには、そのための専用機能は見当たらない。ただし不在から好みは断定できず、これは今回の材料では判断できない候補に留める。検索やタグも、不在だけを理由に不要と決めない。

根拠の強さは揃っていない。画像とハイライトは明記された優先順位、それ以外は主に実装から読む仮説である。

## 私が望むが、普通の人には優先度が低そうなもの

- Markdown を原文のまま持ち帰れること。記事にも文書にも `Download .md` がある。見た目を読むだけでなく、別の道具で読み直したり加工したりできる。AI への入力にも使いやすいが、それを導入目的だったとまでは断定しない。
- Gist のように複数ファイルを一つの記事にできること。本文、補足、コード、図を一緒に置き、各ファイルを個別にも取得する。説明と実物の境界を消さずに、同じ話題の下に束ねられる。
- 見出しへのリンクと、明示した前後記事へのリンク。単なる新着順とは別に、「どこを指しているか」「この話の続きはどれか」を表せる。スマホでコピーできるよう `#` は常時表示する。
- 設計メモと TODO までブログで読めること。成果だけでなく、なぜそうしたか、何が残っているかも同じ場所からたどれる。
- リポジトリとブログで、同じ相対リンクが役に立つこと。配信する記事・文書はサイト内へ、それ以外のファイルは GitHub へつながる。書いたものの居場所を二重に管理しなくてよい。
- 「このサイトの Markdown」がどう見えるか、そのサイト自身の描画処理で試せること。一般的な Markdown プレビューとの互換性より、自分が公開するものとの一致に価値がある。
- 同じブログを複数の言語・実行環境で作って比較すること。読者に同じページを返せるなら一つで足りるはずなのに、Go、MoonBit、TypeScript が並ぶ。ブログが実験の題材でもあるためだろう。
- 採用しなかった実装も、計測条件と一緒に残すこと。実験は本体から切り離し、再現の手掛かりとして保持する。「今の最善」以外にも保存する理由がある。

## 書き手が AI の場合と、人間の場合

比較したいのは、人間の手入力と AI の出力という二択だけではない。人間が題材と判断を持ち、AI の文章を監督する場合を分けて考える。

| 観点 | AI に文章を任せる場合 | 人間が判断を持つ場合（AI の監督を含む） |
| --- | --- | --- |
| 何を書くか | 依頼や資料から題材を整理する。資料にない動機まで補ってしまうことがある | なぜ今これを試したいのか、何が気に入らないのかを選ぶ |
| 何を価値とするか | 体裁の整った説明を出せても、実体験や本人の好みの根拠にはならない | 動いたもの、捨てた案、予想とのずれ、面倒だったことを選んで残す |
| 確認 | ツールを使える AI は実行・計測もできる。実行せず説明しただけの文章とは分ける必要がある | AI の実行結果も含め、何を確認済みとして引き受けるかを決める |
| 推敲 | 丁寧にしたつもりで比喩や説明、未確認のリンクを増やすことがある | 親切さと確認の手間を比べ、削ることや自分で書き直すことも選べる |
| 次の作業への受け渡し | 前提、失敗、未確認、次の手が明記されていると続きを始めやすい | どの問いを続けるか、どの実験を終えるかを決める |

- `slops` は AI、`posts` は人間という区分があり、同じスラッグも別々に持てる。だが、コードが判定するのは置き場所であり、著者の真正性や人間の確認済み状態ではない。
- 既存の人間記事の README は、本人の前置きのあとを「以下は生成された文章」と明示している。人間記事にも AI の文章が含まれる、という実例がすでにある。
- そこでは、リンクを足した瞬間に親切になる一方、確認の手間が倍増することや、最初から自分で書く方が早かったのではという感想も残っている。整った生成文の外側にある、この判断も記事の大事な材料になる。
- 「AI に書かせたから価値がない」「人間なら正しい」という分類にはしない。何を試し、どこまで確かめたかは、どちらの文章でも別に示す必要がある。
- この仮レポート自身も対象になる。「私」を上手に代弁できたことを、本人がそう考えている証拠にはしない。人間が異議を入れられる骨子として置く。

## docs と TODO.md は何をするためにあるのか

- `docs/ja/design.md` は、結果だけでなく、Node をデータにする、描画を分ける、といった選択の理由と制約を置く。
- `docs/sketch/ja/` は、問い、複数の案、環境、実験、計測、見送り、未確認を残す。古い結論のあとに追試があるので、読むときは時系列も必要になる。
- `TODO.md` は次に着手する作業を置く。詳細な説明は docs へリンクし、終わった作業の長い説明で埋めない。
- `TODO-archive.md` は完了した項目の保存先。完了の PR と整理の作業を分け、複数の作業が同じアーカイブを同時に編集しないようにする。
- これらは開発者だけの裏側ではない。`TODO.md` と `docs` は記事と同じ仕組みで配信され、原文も取得でき、一覧の読み順も指定されている。
- 解釈としては、docs が「なぜここまで来たか」、TODO が「ここから何をするか」を分担する。未来の自分や AI が、会話を最初から再現せずに再開するための足場になる。
- 意図の記録と現在の実装は別物でもある。初期の設計や、まだ完了扱いになっていない TODO を、そのまま現在の機能一覧にはしない。

## 余興: 普通ならこうする。しかしこのリポジトリはこうなっている

「普通」は、ブログを手早く作るなら選びそうな道として仮置きする。奇抜さの自慢ではなく、何に余計な手間を払って楽しんでいるかを見せたい。

| 手早く作るなら | このリポジトリで選んでいること | 楽しみや優先順位の仮説 |
| --- | --- | --- |
| 既存のブログエンジンや Markdown パーサーを使う | HTML のデータ構造と小さなパーサーから作る | 表示までの仕組みを、自分で追える大きさにする |
| Workers なら TypeScript で書く | Go/TinyGo、MoonBit/Wasm を試し、比較用の Hono 版まで作る | ロマンに払っている費用を、素直な実装と比べて知る |
| 静的なブログなら HTML を事前生成する | 文章を Static Assets に出しても、HTML は Wasm で組み立てる | リクエスト時に Wasm が働くこと自体が目的の一部 |
| 一記事を一つの Markdown ファイルにする | `.md` という名前のディレクトリに複数ファイルを置く | 記事の完成形より、残したい資料のまとまりを優先する |
| 記事を読む機能と開発メモを分ける | docs と TODO も同じサイトで公開する | 完成品と、作りかけの理由をつなげて読む |
| 一つ動けば実装を一本に絞る | Go を比較基準にも使い、MoonBit と出力を比較する | 中身を変えても外に何が出るか確かめるのが面白い |
| エディター付属のプレビューで済ませる | 本文の描画処理を Wasm にしてブラウザーへ運ぶ | 作った部品が別の場所でも同じ仕事をする楽しみ |
| 成功した最適化を紹介する | 遅くなった案、採らなかった案、profiler 自体の不調も記録する | うまくいくまでを調べることが、次の題材になる |

特に面白いのは、ロマンだけで判断を止めていないこと。`/preview` の JS フォールバックは動作確認後に捨てているし、profiler の改善案も遅くなれば採っていない。実験を広げる楽しみと、面倒を見る経路を減らす判断が同居している。

## 下書きの骨子

### 導入: 画像より先に複数ファイルを置きたかった

- 「ブログにまず欲しいもの」を並べると、自分の順番が少し変だと気づいた、という話から始める。
- 画像やハイライトより、Markdown のダウンロード、見出し ID、前後リンク、Gist のようなバンドルを先に欲しがった。
- 問いを置く。「それなら、私は何をブログと呼んでいるのだろう？」

### 読み物として必要なことは共通している

- スマホで読めること、タイトルと日付、必要な場所へのリンク、確かめた範囲の明示を土台にする。
- 機能を減らすことと、読者の手間を増やすことを混同しない。日本語の行間や常時表示の `#` を小さな例にする。

### 保存したいのは、文章より少し大きいもの

- 人間向け手順と開発者向け補足を束ねた既存記事を例にする。
- コードを記事に貼るだけでなく、別ファイルとしてそのまま持ち帰れることを説明する。
- Markdown の原文や相対リンクが、次の利用につながる、という仮説を出す。

### AI が書ける時代に、どこを自分の文章とするか

- AI が説明を整える部分と、人間が題材や採否を決める部分を分けて考える。
- 生成文にリンクを足す手間、比喩を直す手間、「自分で書く方が早かったかも」という既存の感想を置く。
- 人間が監督していても、実行・確認の証拠が必要であることに戻る。文章の流暢さで代用しない。

### docs は理由、TODO は次の手

- 本文の完成度とは別に、やめた案や未確認の点を置ける場所が必要だった、とつなぐ。
- docs、TODO、archive の分担を説明する。
- それらも読めるブログなら、試行錯誤の現在地まで残せるのではないか、と問う。

### 余興: ブログを作るだけなら要らない寄り道

- Workers なら Hono で済むのに、Wasm で動かす。
- ABI の文字列の受け渡しを何通りも比べ、同じページを返すことも確認する。
- ブログの文書をパーサーのベンチマーク入力にし、重い文書を読む道具を、その文書で鍛える。
- ただし、試したものを全部本体に積むわけではない。実験の保存と保守する機能を分ける。

### 結び: 続きを始められる場所

- 冒頭の優先順位に戻る。欲しかったのは、豪華な記事より、手元の試行錯誤を失わずに読み返し、渡し直せる場所だったのかもしれない。
- 読者に、未来の自分や AI を含める、という仮説を置く。
- 技術的な楽しみも隠さない。「ブログを作ると書く材料が増え、書くとブログに欲しいものが増える」という循環で閉じる。

## 本人が書く段階で決めたいこと

- 自分にとっての第一の読者は誰か。未来の自分、他の開発者、AI のどこに最も重心があるか。
- `slops` と `posts` の境界は、生成した主体、編集する主体、内容を引き受ける主体のどれで考えたいか。
- 「疎通確認が価値」という既存記事の感想を、今回のブログ観の中心に据えてよいか。
- ロマンと維持の手間がぶつかったとき、何を残すと楽しいか。本人しか語れない具体的な一場面を足したい。
- この仮レポートで、本人なら絶対に使わない言葉や、持っていない動機を取り除く。
