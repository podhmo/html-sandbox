# 私にとってのブログとは何であるか？（仮）

この本文は、リポジトリの記録と本人への聞き取りを材料に AI が代筆した草稿です。一人称で書いていますが、語り口や主張を本人が最終確認した文章ではありません。

## 自分用の記録にも、リンクは欲しい

ブログを作っていると、一般的なブログにありそうな機能と、自分が欲しがっている機能の順番が少し違うことに気づく。

画像を簡単に貼る機能は、まだずっと後でよい。シンタックスハイライトも急いでいない。その一方で、Markdown の原文をダウンロードする機能や、見出しごとのリンク、複数のファイルを一緒に置く機能は欲しくなる。

何のためのブログなのかと考えると、まず自分が読むためのものなのだと思う。今の考えを文章にして、後から必要になったら読み返す。誰にも読まれなくても、その用途はなくならない。

ただ、自分用なら他人に渡すことを考えなくてよい、というわけでもない。Slack や Discord で話しているときに、以前書いた一節を指したくなることがある。ページ全体を渡して探してもらうより、その見出しに直接飛べる方がよい。細かな permalink は、そういうところで役に立つ。

読む相手を考えるなら、まず今の自分、それから後の自分。その次に知っている人、さらにその先に知らない人がいる。自分向けに書いたものが、会話の途中で誰かに渡せれば、それで十分な場面は多い。

## 書くときにも、考えは動く

備忘録というと、分かったことを忘れないように保存するものに聞こえる。もちろんそれもあるが、書く前に全部分かっているわけではない。

何を試したかったのか、何が起きたのかを書こうとすると、説明の足りないところが見える。うまく動いたという話なのか、仕組みを理解できたという話なのか、まだ単に動かしただけなのか。文章にすると、自分でも区別しないといけなくなる。

その時点でどこまで分かっているかを、小さく区切って置いておきたい。迷っていた時間を全部そのまま載せたいわけではないが、最後の結論が出るまで何も書けないのも困る。

後から読み返して面白いのは、判断が変わっているときだ。

このブログの[最初のスケッチ](../../docs/sketch/ja/blog.md)には、JavaScript を使わないという制約がある。今はコードをコピーするボタンがあり、Markdown を試すプレビューもある。コピー用のスクリプトは通常の記事でも読み込んでいる。

プレビューがあれば、AI の出力がこのブログでどう見えるかを、ビルドやデプロイを待たずに試せる。対応していない記法が見つかっても、必要な機能を足すか、表示されたままで済ませるかを、その場で考えられる。機能が増えたというだけでなく、確かめる手間が減っている。

この二つの状態が残っていると、最初に何を避けたかったのかと、その後何が必要になったのかを考えられる。制約を守れたかどうかだけでなく、それを変えてまで欲しくなった便利さが何だったのかを振り返れる。

今の実装だけを見ても、そこまでの事情は分からない。記事が残っていて嬉しいのは、そういう変化を追えるときだと思う。

## 何があれば、ひとまず足りるか

自分向けでも、文章として意味が通ることは必要になる。どんな場面で、何をしたくて、その話を書いているのか。使い道が見えていると、その文章をどこで読めばよいかも分かる。逆に、そこが曖昧なままの文書も、このリポジトリにはある。

読みにくさで考えが途切れるのも嬉しくない。スマホで読めて、日本語の行間が窮屈でなく、長いコードや表があっても本文の幅が崩れない。そのあたりは、個人用だから省いてよいものでもない。

一方、機能を一般的なブログに揃えることには、あまり関心がない。管理画面、タグ、集客や収益化は、自分がここでやりたいことの外にある。画像を投稿する機能も、当分先でよい。

ブログ内検索は、それらとは別に[実験している](https://github.com/podhmo/html-sandbox/pull/62)。文書を読む場所に検索があったらどうなるか、という題材で、2026-10-26 時点では Go 版だけの未マージの実装になっている。試していることと、本体の機能として採用することは、分けておく。

少ない機能で十分かどうかも、最初から答えがあるわけではない。使ってみて、ここが足りないと思うこともあれば、その程度ならそのままでよいと思うこともある。

## AI に記録してもらうことと、自分の記事にすること

このブログには、AI の記事を置く `slops` と、人間の記事を置く `posts` がある。とはいえ、後者の文章を一文字ずつ人間が入力する、という区別でもない。[すでにある記事](../2026-10-19-wsl-opencode.md/README.md)にも、AI が書いた部分が含まれている。

AI にやってほしいことの一つは、試している間の状況を記録することだ。小さなプロトタイプや spike では、始める前に考えていたことと、実際にやって分かったことがずれる。その途中で、予定になかった事情が出てきたり、別の案を選んだりする。

最後にできたものだけを説明されると、その部分がなくなってしまう。最初の計画と、実際の経過と、途中で変えた判断が分かるようにしてほしい。

ただ、それがそのまま自分の記事になるかというと、もう一段ある。

何を疑問に思って試したのかは、自分の中にある。それを説明する調子も、自分のものとして出すなら気になる。AI が丁寧に説明してくれていても、自分ならしない話し方だと、そのままでは出しにくい。

さらに困るのは、実行するつもりのないことを、今後の予定として書かれることだ。話として収まりがよくても、自分が決めていない予定まで増やされては困る。

修正した文字数よりも、その文章に書かれていることを自分の判断として扱えるかどうかが大きい。誰かと話すときに自分の考えとして説明できるところまで来ているなら、AI が下書きした文章でも、自分の記事にできると思う。

`slops` と `posts` を分けるのは、そうした自分との距離を分けるためでもある。生成される記録と、自分の文章としてまとめたものを、同じ流れに全部並べたくない。投稿の量を調整する意味もある。

## 終わる記事と、終わらない記録

`posts` には、一つの文章として書き終えたと思うところがあるかもしれない。`slops` や `docs` は、もっと途中の状態で置いてある。次を試せば、また続きが出てくる。

いつまでも完成しないから無意味ということではなく、今の時点で何の話か分かれば、一旦置ける。すべてに最終結論を用意しなくてもよい。

ただ、記事の価値を全部同じようには考えていない。

一般的なインストール手順を知りたいだけなら、その環境で動くことが大事になる。動作が確かめられない説明をきれいに整えても、その用途には役に立たない。以前の解説記事で、疎通確認に価値があると思ったのは、そういう話だった。

それに対して、自分がある仕組みの何を知りたかったのかは、手順がそのまま動かなくなっても残しておきたい。ツールの使い方が知りたかったのか、特定の制約を越えられるか知りたかったのか。後から試す方法が変わっても、当時の疑問を読み返す意味はある。

## 本文の外に置いておきたい文章

説明を一つにまとめようとすると、補足が本文より長くなることがある。別の説明を添えたいだけなのに、それを全部本文に混ぜると、何の話をしているか分かりにくくなる。

そこで、Gist のように複数のファイルを置ける形が欲しかった。

実際に読んでもらう文章と、その補足。別の見方からの解説。同じ題材を違う調子で説明したもの。本文には入れなかったが、捨てるほどでもない話。そういうものを、本文とは区切ったまま近くに置いておきたい。

このバンドルでも、[骨子](README.md)と[根拠のメモ](evidence.md)、この本文は別にしている。[レビュー](review.md)も別のファイルに置く。レビューの説明まで本文に織り込む必要はないが、一緒にたどれると便利だ。

`docs` と TODO をブログで読めるようにしているのも、自分が読むときに楽だからだ。設計や調査の話と、残っている作業を、確認のたびに GitHub へ見に行かずに済ませたい。読者に開発の裏側を見せるため、というほどの理由はない。

## ブログを作るだけなら、寄り道している

ここまでの用途だけなら、既存の仕組みでもかなり足りると思う。Gist で済むものは、それでよい。

それでもこのリポジトリに Go、MoonBit、TypeScript が並んでいるのは、ブログとは別に試したいことがあるからだ。

Cloudflare Workers で何が動き、どんな制約があるのか。MoonBit の Wasm は、実際のブログを動かしても小さいのか。引っかかった制約を、コーディングエージェントが解いていけるのか。そういうことを確かめる題材として、ブログを使っている。

Go で HTML を組み立てる部品や tinymarkdown を標準ライブラリだけで作るのも、小さな仕組みでどこまで足りるか、試しているところがある。

`/preview` は、その小さな Markdown でどこまで困らずに済むかを確認するのに便利だ。AI の出力を入れてみると、表示が崩れるところや、解釈されない書き方が分かる。それを直したいのか、別に今のままでよいのかを、手軽に判断できる。

実用的に書くならどうなるかは、[`ts` の実装](../../ts/README.md)が比較相手になる。Workers の上で素直に TypeScript と Hono を使えば、自分で用意せずに済むものも多い。Wasm のために払っている手間を、それと比べられる。

実験のコードを残していることにも、あまり大きな意味を載せなくてよい。その記事を書いたときに試していた形が、そこに置いてある。そのくらいの記録でも役に立つ。

ただ、技術的に面白かったことが全部記事になるわけでもない。試していて楽しかったが、記事にはしていないものもある。ブログを作るのが楽しいからといって、書く方まで面倒にしたくはない。

## 今のところのブログ

自分のために書いているが、書いたものを誰かに渡すこともある。考えがまとまってから書くこともあれば、書きながら何を考えていたのか分かってくることもある。以前の文章と並べると、考えが変わったところも見える。

そういうものが少しずつ残っていれば、備忘録としては嬉しい。

そうした記録を並べて読むと、考えのつながりも分かる。「続きを始められる場所」という説明も、そのくらいの意味なら、たしかにそうだと思う。自分が読めて、必要なところを人に渡せて、書くのが面倒にならない。今のところは、そのくらいのブログでよいと思っている。
